2. Understanding AWS Regions

A Region is a separate geographic area containing multiple Availability Zones. Example Region identifiers include us-east-1, eu-central-1, and ap-southeast-1. AWS service availability, price, quotas, and applicable data-handling requirements differ by Region.

PropertyMeaning for architects
Region isolationResources and data generally stay in the selected Region unless replication, transfers, or a service-specific behavior moves them elsewhere.
Region identifiersUse stable programmatic codes in CLI, SDK and IaC; the human-readable name is descriptive.
Service availabilityDo not assume every service or feature is offered in every Region.
Pricing and transferRegional rates and inter-Region data-transfer charges can affect architecture.
Important: AWS Regions are not interchangeable with Availability Zones. A multi-AZ application survives certain AZ failures; it does not automatically survive an entire Region outage.

3. Availability Zones and fault isolation

An Availability Zone (AZ) consists of one or more discrete data centers with redundant power, networking and connectivity. AZs within a Region are physically separated but interconnected. Architects use multiple AZs to reduce dependence on one failure domain.

Practical example: highly available Orders API

  • Deploy an internet-facing Application Load Balancer across public subnets in at least two AZs.
  • Run ECS/Fargate tasks in private application subnets spanning at least two AZs.
  • Use a supported Multi-AZ deployment for Amazon RDS, with backups and recovery plans.
  • Use security groups and routing to restrict traffic; distributing instances across AZs is not an authorization control.

AZ naming: us-east-1a in one AWS account need not represent the same physical AZ as us-east-1a in another account. AZ IDs (such as use1-az1) identify the same physical AZ across accounts.

4. Edge locations, Local Zones and the AWS global network

InfrastructurePrimary purposeTypical service or example
CloudFront edge locationCache/deliver content closer to end users; route selected requests toward originsAmazon CloudFront
Regional Edge CacheIntermediate caching layer for supported CloudFront requestsCloudFront architecture
Local ZonePlace selected compute/storage closer to large population centers while associated with a parent RegionEC2 or supported services in a Local Zone
Wavelength ZoneSupported edge deployment integrated with telecommunications networksLow-latency mobile applications
Global acceleratorAnycast static IP entry and traffic optimization over the AWS global networkAWS Global Accelerator

Edge locations are not general-purpose Regions or AZs. A CloudFront cache is not a substitute for a resilient regional origin, and a Local Zone has different service availability and failure characteristics from its parent Region.

5. Regional and global service scopes

Service scope determines where resources are configured and where their data or control plane operates. Always review service-specific documentation rather than assuming a global service stores no regional data.

Example serviceTypical scopeImportant nuance
Amazon EC2, VPC, RDSRegionalSubnets and compute instances have AZ placement inside the Region.
Amazon S3Regional bucket placementSpecific features support cross-Region replication when explicitly configured.
AWS IAMGlobal identity service within a partitionPermissions apply to scoped regional resources; IAM Identity Center has its own regional considerations.
Amazon Route 53 public DNSGlobal DNS serviceDNS routing does not itself make regional workloads highly available.
Amazon CloudFrontGlobal edge deliveryOrigins can be regional or external, with separate failover considerations.

6. Multi-AZ versus Multi-Region resilience

PatternProtects againstWhat must be designed
Single AZLimited localized component failuresBackups and recovery; AZ outage can interrupt service
Multi-AZ, single RegionMany AZ-level failuresLoad balancing, capacity, healthy targets, replicated/managed data tiers
Multi-Region active/passiveRegional outage with recovery timeData replication, failover, DNS/traffic, recovery tests
Multi-Region active/activeSome regional failures with continued servingConsistency, routing, conflict resolution and complex operations

Define RTO (recovery time objective) and RPO (recovery point objective) before choosing a pattern. Multi-Region is not automatically the best choice; it increases cost and operational complexity.

7. Choosing the right AWS Region

  1. Business geography: locate primary users and measure realistic network latency.
  2. Data residency: identify legal, contractual, and organizational constraints.
  3. Services: verify all required services/features and instance types.
  4. Continuity: examine AZ diversity and cross-Region DR options.
  5. Cost: compare compute, storage, inter-AZ and inter-Region transfer.
  6. Governance: establish account guardrails, deployment regions, logging and encryption standards.
Decision exercise: An EU financial services application serves users in Germany and has EU data residency requirements. Evaluate eu-central-1 and a compliant DR Region against service availability, latency, replication and regulatory requirements. Do not assume selecting an EU Region alone guarantees compliance.

8. Hands-on CLI lab — inspect AWS Regions and AZs

Prerequisites: AWS CLI v2 installed, a sandbox account, an authenticated internship profile, and permission for EC2 DescribeRegions/DescribeAvailabilityZones. These read-only calls may still be governed by your account policies.

aws --version
aws sts get-caller-identity --profile internship

# List enabled/opted-in Regions visible to this account
aws ec2 describe-regions --all-regions \
  --query 'Regions[*].[RegionName,OptInStatus]' \
  --output table --profile internship --region us-east-1

# Describe AZ names and stable AZ IDs for one Region
aws ec2 describe-availability-zones \
  --region us-east-1 --profile internship \
  --query 'AvailabilityZones[*].[ZoneName,ZoneId,State]' \
  --output table

# Confirm the configured caller profile
aws configure list --profile internship

Intern deliverables

  1. Record two candidate Regions and compare service availability using AWS documentation.
  2. Record the AZ names and AZ IDs returned for one Region.
  3. Draw two-AZ public, private application and private data subnet tiers.
  4. Explain the traffic path from a user through Route 53, CloudFront (if used), ALB, application, and RDS.
  5. Describe what fails when an AZ becomes unavailable and what fails when the entire Region is lost.

Read-only CLI commands do not create resources. Any optional infrastructure deployment may incur charges and should be performed only in an approved sandbox.
