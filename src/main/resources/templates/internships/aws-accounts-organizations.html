1. Reference architecture

How to read the diagram

The top of the diagram shows the Management Account, which owns the AWS Organization. Under it is the Organization Root, then multiple Organizational Units (OUs) such as Security, Infrastructure, Sandbox, Non-Production and Production.

Each OU contains one or more member accounts. These accounts isolate workloads, permissions, quotas, logs and billing boundaries. Enterprise teams then apply governance controls consistently across the organization.

Key architectural ideas

  • Use separate accounts for separate environments and responsibilities.
  • Use SCPs to define the maximum permissions allowed in an OU or account.
  • Use IAM Identity Center for workforce access, permission sets, and centralized sign-in.
  • Use centralized logging and security accounts for CloudTrail, Config, Security Hub, and backups.
  • Use a shared services account for networking, DNS, artifact repositories, and reusable platform services.

2. Why enterprises use multiple AWS accounts

A single AWS account is fine for experimentation, but enterprises quickly need stronger separation. Multiple accounts provide isolation for security, operations, billing and change management.

Need Why multiple accounts help
Security isolation Compromise in one account is less likely to affect all workloads. Blast radius is reduced.
Environment separation Production, test, development and sandbox accounts can have different policies and approval controls.
Cost management Each account has clean billing visibility, while consolidated billing rolls costs up to the organization.
Quota and service limits Limits are often account-scoped, so account separation prevents contention.
Operational ownership Different teams can own their own accounts while platform teams still enforce guardrails.

3. AWS Organizations operating model

Core components

  • Management Account: The organization owner account. It should be heavily locked down and not used for daily workloads.
  • Organization Root: The top-level hierarchy node under which all OUs and accounts reside.
  • Organizational Units (OUs): Containers that group accounts by function, environment or risk posture.
  • Member Accounts: Individual AWS accounts where applications, shared services and security tooling run.
  • Delegated Administration: Lets certain AWS services be administered from designated member accounts rather than only from the management account.

A practical OU layout

  • Security OU: Log archive, security tooling, audit and compliance.
  • Infrastructure OU: Shared services, DNS, networking and CI/CD utilities.
  • Sandbox OU: Low-risk experimentation for engineers and interns.
  • Non-Production OU: Development, integration, QA and performance testing accounts.
  • Production OU: Production application and data accounts with stronger change control.

This layout aligns people, risk and control boundaries with account boundaries.

4. Identity, access and cross-account design

Modern AWS enterprises should avoid long-lived IAM users for workforce access. Instead, use centralized identity and short-lived role-based access.

Recommended approach

  • Integrate the enterprise identity provider with IAM Identity Center.
  • Create permission sets such as ReadOnly, Developer, PlatformAdmin and SecurityAudit.
  • Assign users and groups to target AWS accounts and roles from one control plane.
  • Use cross-account IAM roles when automation or shared services need controlled access into workload accounts.

What to avoid

  • Using the management account for routine engineering work.
  • Creating many permanent IAM users in every account.
  • Embedding long-lived access keys into scripts or applications.
  • Granting AdministratorAccess broadly when narrower roles are enough.

5. Governance guardrails with SCPs

Service Control Policies do not grant permissions. Instead, they define the outer boundary of what identities in member accounts are allowed to do.

Example guardrail Purpose
Deny leaving the organization Prevents member accounts from detaching from the organization.
Deny disabling CloudTrail or Config Protects audit and compliance visibility.
Deny use of unapproved regions Supports compliance and cost management.
Deny root-user risky actions Reduces the likelihood of high-impact configuration mistakes.
Require encryption controls Reinforces organizational security standards.

Important mental model

Effective permissions in AWS are the intersection of identity-based policies, resource-based policies, session policies, permission boundaries and SCPs. If an SCP denies an action, the action stays denied even if an IAM policy allows it.

6. Centralized logging, security and operations

Log archive account

Collect organization-wide CloudTrail logs, Config snapshots, VPC Flow Logs and backup copies in a dedicated account with tight retention and access control.

Security account

Centralize Security Hub, GuardDuty, detective investigations, findings review and security reporting.

Shared services account

Host reusable platform services such as Transit Gateway, Route 53 private DNS, artifact repositories, CI/CD or shared containers.

7. Consolidated billing and cost control

AWS Organizations supports consolidated billing. That means the organization can receive a single bill while still preserving per-account cost allocation and visibility.

  • Track costs by account, environment, team, or application.
  • Apply tags and cost categories for business reporting.
  • Use AWS Budgets and Cost Explorer from central governance accounts.
  • Reserve production purchasing decisions for approved finance or platform teams.
