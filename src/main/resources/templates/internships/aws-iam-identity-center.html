1. Enterprise identity reference architecture

  1. Identity source: Employees authenticate using an external IdP such as Entra ID or Okta, or a supported directory. SAML-based identity federation is separate from SCIM-based provisioning of users and groups.
  2. IAM Identity Center: Centralizes workforce access and defines permission sets that translate into account access.
  3. AWS Organizations: Accounts and OUs establish administrative, billing and governance boundaries; SCPs can bound permissions.
  4. Member accounts: Provisioned IAM roles receive access based on assignments. AWS services authorize requests by evaluating applicable IAM and resource policies.
  5. Workload identity: EC2, ECS, Lambda and other services typically obtain temporary credentials through service roles, independently from workforce SSO.
Important: The diagram represents control relationships, not a literal synchronous request chain. Identity Center does not sit in the network data path between an application and an AWS resource.

2. IAM fundamentals: principals, policies, roles and STS

ConceptWhat interns need to know
PrincipalAn AWS identity making a request, such as an IAM role session or federated principal.
IAM userLong-term IAM identity within one account. Avoid IAM users for ordinary workforce access where federation is available.
IAM roleAssumable identity with policies and a trust policy; produces temporary sessions.
Trust policyDefines which principals may assume a role, with any required conditions.
Identity-based policyDefines permitted or denied API actions and resources for identities.
Resource-based policyAttaches permissions directly to resources, such as S3 buckets or KMS keys.
STSIssues temporary AWS credentials for sessions and role assumption.

Example: bounded S3 read access

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::internship-training-data/*"
  }]
}

This policy is illustrative. It does not grant permission to list the bucket or access other buckets. Never use wildcard administrative permissions for a simple read-only use case.

3. IAM Identity Center: workforce SSO

IAM Identity Center provides a central user access portal and multi-account access assignments. It supports an identity source, users and groups, permission sets and account assignments.

ComponentResponsibility
Identity sourceIAM Identity Center directory, external identity provider, or supported Active Directory configuration.
Permission setReusable desired permissions for AWS account access; provisions corresponding account IAM roles.
AssignmentConnects a user/group, an AWS account and a permission set.
Access portalOffers users assigned account/role access and supported applications.

Example: Assign group Cloud-Developers the DeveloperSandbox permission set in the sandbox account, and assign Security-Auditors the ReadOnlyAudit permission set in target accounts.

4. Federation: SAML 2.0, provisioning and OIDC

  • SAML 2.0: Common protocol for workforce federation between an external enterprise IdP and IAM Identity Center.
  • SCIM: Supported automated user/group provisioning; its lifecycle role differs from SAML sign-in.
  • OIDC: IAM Identity Center also provides OAuth 2.0/OIDC functionality for supported application integrations; do not confuse this with AWS CLI workforce SSO or assume arbitrary application login flows are configured automatically.
  • Authorization: Authentication at the IdP does not itself grant access to an AWS account. Account assignments and policies still govern authorization.
Boundary: Use IAM Identity Center for workforce AWS access. For a public-facing customer application, separately evaluate an appropriate customer identity solution such as Amazon Cognito or another configured IdP.

5. Effective permissions and explicit deny

Identity policies, resource policies, permission boundaries, session policies and Organizations SCPs can all affect requests. Exact evaluation varies by principal, resource, account boundary, service and policy type. An applicable explicit deny wins over an allow.

SCPs do not grant access: they specify an organization's maximum permissible actions for affected principals in member accounts. Permissions must still be granted through an applicable IAM or resource policy.

Design policies around specific actions, specific resources and constrained conditions, and validate every authorization path using least privilege.

6. Multi-account permissions and governance

Use separate sandbox, development, test, security and production accounts. Grant teams distinct permission sets and require additional controls for production administration.

7. Workload identity vs human identity

Humans use federation and Identity Center account assignments. Workloads should use temporary credentials attached to managed compute rather than embedded access keys.

  • EC2: An instance profile provides credentials for an IAM role.
  • ECS/Fargate: The task role provides application authorization, while an execution role supports platform operations.
  • Lambda: An execution role controls permissions available to the function.
  • EKS: Use supported pod identity mechanisms to associate workloads with least-privilege IAM roles.

Remember to separately authorize your Spring Boot application's end users. An application task role does not replace business-level authorization checks.

8. Hands-on labs: observe, design and verify

Lab A — Observe your current AWS identity

Prerequisite: an approved AWS sandbox and an IAM Identity Center permission set assigned by the instructor. Do not create organization-wide resources for this lab.

aws --version
aws configure sso --profile internship
aws sso login --profile internship
aws sts get-caller-identity --profile internship
aws iam list-account-aliases --profile internship

Record the account ID and ARN returned by STS. Identify whether the ARN corresponds to an assumed role. The account-alias command requires permission and may be denied in a restricted sandbox.

Lab B — Design permission sets

  1. Define groups for interns, developers, auditors and production operators.
  2. Map each group to accounts and narrowly scoped permissions.
  3. Document which operations require approval, elevation and audit evidence.
  4. Explain why an SCP deny overrides an IAM allow in affected member accounts.

Lab C — Optional administrator-led review

# Requires Organizations read permissions
aws organizations describe-organization --profile internship
aws organizations list-accounts --profile internship

# Requires IAM Identity Center read permissions
aws sso-admin list-instances --profile internship

These read-only commands may be denied by design. That is a valid security control, not a reason to broaden an intern's permissions.

9. Common failures and troubleshooting

SymptomWhat to check
User can authenticate but sees no AWS accountCorrect identity source, group membership, account assignments and permission-set provisioning.
AccessDenied on an API callIdentity/resource policies, permission boundary, session policy, SCPs and service-specific conditions.
Wrong AWS accountSelected SSO account/role/profile; verify aws sts get-caller-identity.
Session expiredRenew the SSO session with the correct profile; do not substitute long-lived keys.
Missing group or stale membershipSCIM provisioning state, group sync, federation mappings, and assignment propagation.
