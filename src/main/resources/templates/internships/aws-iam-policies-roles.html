IAM Policies, Roles & STS

Learn how AWS authenticates identities, evaluates permissions, issues temporary credentials through STS, and enables secure cross-account access using IAM roles in multi-account enterprise environments.

1. Reference architecture

How to read this diagram:

  • Principals on the left are the requesters: workforce users, applications/services and external identities.
  • Identity & Access Controls in the middle define who can do what using policies, roles, MFA and permission boundaries.
  • STS issues temporary credentials when a role is assumed.
  • Target AWS resources on the right are accessed only if all applicable controls allow the request.
  • Governance controls at the top, such as Organizations, SCPs and IAM Identity Center, apply enterprise-wide guardrails.

2. Core concepts interns must master

Identity side

  • Authentication proves identity: sign-in, federation, MFA, SSO.
  • Authorization decides allowed actions after identity is known.
  • IAM users are legacy-style named identities inside an account; limit their use.
  • IAM groups help manage permissions for IAM users.
  • IAM roles are preferred for applications, services and cross-account access.
  • Trust policies specify who may assume a role.
  • Permission policies specify what the role may do once assumed.

Credential side

  • STS = Security Token Service. It issues short-lived credentials.
  • Temporary credentials include access key ID, secret access key and session token.
  • Session duration is time-bounded and safer than long-lived keys.
  • AssumeRole is used for cross-account and application access.
  • AssumeRoleWithSAML and AssumeRoleWithWebIdentity support federation.
  • Least privilege means granting only the permissions needed.
  • MFA reduces the risk of stolen credentials for human users.

3. AWS policy evaluation logic

Whenever an AWS API call is made, AWS evaluates all relevant controls together. Interns should memorize this order of thinking:

1. Explicit deny wins

If any applicable policy explicitly denies the request, access is denied immediately.

2. Allow must exist

The request must be explicitly allowed somewhere after authentication succeeds.

3. SCPs limit max permissions

Service Control Policies set outer guardrails for what member accounts can ever do.

4. Resource policies matter too

S3, KMS, Lambda and others may use resource policies to further allow or restrict access.

Common policy types

Policy / controlMain purposeIntern takeaway
Identity-based policyAttached to user, group or roleMost common way to grant permissions.
Trust policyDefines who can assume a roleWithout correct trust, AssumeRole fails.
Permission boundaryCaps the maximum permissions for a principalUseful for delegated administration.
Resource-based policyAttached to resource such as S3 bucket or LambdaOften required for cross-account access.

4. Cross-account access pattern

  1. A user or application authenticates in a source account or via IAM Identity Center.
  2. The requester calls sts:AssumeRole against a role in the target account.
  3. The target role’s trust policy must allow that source principal or source role.
  4. STS returns temporary credentials for the target role session.
  5. The session can now call target AWS services, subject to identity policies, resource policies, SCPs and boundaries.
  6. CloudTrail logs the role assumption and the subsequent actions for auditability.

5. Hands-on labs

Lab A — Create a least-privilege S3 read role

  • Create an IAM policy allowing only s3:GetObject on a chosen bucket path.
  • Create a role and attach the policy.
  • Use STS AssumeRole and verify the bucket is readable but not writable.

Lab B — Cross-account RDS / admin visibility role

  • Source account users assume a monitoring role in a target account.
  • Trust policy restricts the source account and optional MFA conditions.
  • Validate CloudTrail logs and session behavior.

7. Internship completion checklist

  • Explain the difference between authentication and authorization.
  • Describe IAM users, groups and roles.
  • Explain why roles are preferred over long-lived access keys.
  • Explain what STS returns and why temporary credentials are safer.
  • Read a trust policy and identify who may assume a role.
  • Explain how SCPs differ from IAM permission policies.
  • Troubleshoot a simple AccessDenied error.
  • Demonstrate a safe cross-account role-assumption workflow.
