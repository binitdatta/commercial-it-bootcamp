Reference architecture — AWS enterprise Spring Boot application

The diagram maps an internet-facing Orders application to AWS networking, compute, database, identity, event processing, monitoring and cost management. Follow the flow from the browser on the left through the VPC, then inspect the supporting services on the right.

Primary request flow: Browser → Route 53 DNS resolution → HTTPS connection to Application Load Balancer (certificate from ACM) → ECS/Fargate running Spring Boot Orders API in private application subnets → Amazon RDS/Aurora MySQL in private data subnets.

How to read each architectural component

1. Users / Browser, Route 53 and ACM

Route 53 resolves the application hostname to the load-balancer endpoint. AWS Certificate Manager provisions and manages the TLS certificate used by the HTTPS listener. DNS resolution and TLS establishment are separate operations; traffic does not literally traverse ACM as a proxy.

2. AWS Region and Virtual Private Cloud (VPC)

The VPC defines the network boundary and CIDR space (diagram: 10.0.0.0/16). Subnets are scoped to individual Availability Zones. Route tables, security groups, network ACLs and gateways determine connectivity.

3. Public subnets, ALB and NAT Gateway

For the illustrated internet-facing design, the Application Load Balancer belongs in public subnets spanning at least two Availability Zones, even though the graphic draws it to the left for readability. A NAT Gateway in a public subnet provides outbound access for private workloads when required; it does not accept unsolicited inbound application traffic.

4. Private application subnets — ECS/Fargate

Amazon ECS orchestrates the Spring Boot Orders API containers; Fargate provides managed compute capacity. Tasks remain without public IP addresses and the ALB forwards requests to registered task targets. Configure task roles, execution roles, security groups and health checks.

5. Private data subnets — RDS / Aurora MySQL

The relational database uses private connectivity, a database subnet group, restrictive security groups, encryption, backups and (when required) Multi-AZ availability. Only approved application security groups should connect to its database port.

6. IAM / IAM Identity Center

IAM policies and roles grant permissions to workloads, while IAM Identity Center can federate workforce sign-in to AWS accounts. Enforce least privilege, short-lived credentials, role separation and regular access review.

7. Secrets Manager

Stores and optionally rotates database credentials and other application secrets. Fargate tasks can retrieve authorized secrets using IAM roles; avoid embedding passwords in container images, application source or version control.

8. S3 and Lambda

Amazon S3 holds objects such as uploads and reports, outside the VPC subnet layout. S3 events can trigger Lambda processing for thumbnails, metadata or malware scanning. Control access using IAM, bucket policies and encryption; VPC endpoints can enable private S3 access.

9. CloudWatch and CloudTrail

CloudWatch collects application logs, metrics and alarms. CloudTrail records supported AWS API activity for audit and investigation. Configure retention, alert thresholds and account-wide audit coverage deliberately.

10. AWS Budgets / Cost Explorer

Use Budgets to set cost thresholds and notifications; use Cost Explorer to understand usage and spending trends. Tag resources, estimate Fargate/RDS/NAT costs, and clean up training environments.

Architecture clarification: The infographic simplifies several service relationships. ACM is certificate management rather than a request hop; the internet-facing ALB is logically placed inside public VPC subnets; AWS IAM, Route 53 and S3 are not deployed as resources inside those subnets. NAT serves outbound egress, not the incoming ALB-to-task request path.

1. Shared cloud architecture

Cloud platforms provide on-demand infrastructure and managed services. The shared responsibility model separates provider infrastructure obligations from customer workloads, data and access decisions.

Service model Customer typically manages
IaaS Guest OS, runtime, application, data, identities
PaaS Application, data, identities and configuration
SaaS Data, user permissions, identity and tenant configuration

2. Networking and IAM fundamentals

Learn virtual networks, subnets, routes, firewalls/security groups, load balancers, public versus private endpoints, DNS and certificates. Identity policies must follow least privilege.

  • Choose a region and documented network boundaries.
  • Use short-lived workload credentials and managed identities instead of static access keys.
  • Separate development and production environments.
  • Enable audit logs, monitoring and budget alerts before deploying resources.

3. Cloud-native Spring Boot architecture

An enterprise pattern is browser → TLS ingress/load balancer → Spring Boot workload → managed database, with IAM-bound service identity, secrets manager, logs, traces and metrics.

Make authorization enforcement explicit at the API and the database boundary; a browser login alone does not secure services.

In this reference architecture the entry point is Route 53 and an HTTPS Application Load Balancer; the application executes on ECS/Fargate across private application subnets and accesses RDS/Aurora MySQL in private data subnets. S3/Lambda provide an independent event-driven upload path, while CloudWatch, CloudTrail and Budgets provide operations, audit and cost oversight.

4. AWS account setup and CLI

Enable MFA on the root account, avoid using root for daily activity, use IAM Identity Center where appropriate and set up a budget. Install AWS CLI v2.

aws --version
aws configure sso
aws sso login --profile internship
aws sts get-caller-identity --profile internship

Use a dedicated sandbox account and bounded permissions; commands may require preconfigured Identity Center access.

6. Lab: serverless object upload

Create a sandbox S3 bucket with default encryption, Block Public Access and a limited IAM role. Upload a test file using a temporary IAM Identity Center profile.

aws s3 ls --profile internship
# Replace with a unique bucket you already created in the sandbox:
aws s3 cp sample.txt s3://YOUR-SANDBOX-BUCKET/sample.txt --profile internship
aws s3 ls s3://YOUR-SANDBOX-BUCKET/ --profile internship

Delete test objects and bucket afterward to avoid costs. Do not disable public-access controls.
