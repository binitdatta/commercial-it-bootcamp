1. Why Kubernetes exists — the enterprise problem

Suppose your Spring Boot Orders API runs as a single Java process on one virtual machine. If that VM fails, the service is unavailable. If sales traffic triples, someone must provision new VMs, start additional processes, distribute traffic, and monitor failures. In a large organization, repeating this by hand for dozens of services is slow and error-prone.

Kubernetes is a container orchestration platform. You describe the desired state of your applications; Kubernetes controllers continuously compare it with the observed state and work to close the gap. It schedules Pods, restarts or replaces failed workloads, handles internal service discovery, and coordinates controlled updates.

Plain-English analogy: think of Kubernetes as the operations management team of a large apartment complex. The control plane makes placement and operational decisions; worker nodes are apartment buildings; Pods are occupied apartment units; the applications inside them are residents. An operations team notices a failed unit and arranges a replacement without asking every resident to coordinate it.

2. Kubernetes architecture — two major planes

Control plane — makes decisions

Maintains cluster state, accepts API requests, schedules pending Pods, and runs reconciliation loops. It does not ordinarily run your customer-facing app containers.

Main pieces: kube-apiserver, etcd, kube-scheduler, kube-controller-manager; optional cloud-controller-manager.

Worker nodes — run applications

Virtual or physical machines that host application Pods, provide networking and storage connections, and report health to the control plane.

Main pieces: kubelet, container runtime, networking components; often kube-proxy or an equivalent dataplane.

USER / CI-CD / kubectl → KUBERNETES API SERVER → SCHEDULER + CONTROLLERS → WORKER NODES → PODS → APPLICATIONS

Critical distinction: the control plane manages cluster behavior; worker nodes provide the compute capacity where your Java application actually executes.

3. Kubernetes control plane — each component in detail

ComponentResponsibilitiesExample in the Orders API
kube-apiserverThe front door of the Kubernetes control plane. Authenticates and authorizes API requests; validates resources; exposes declarative state.Your deployment pipeline submits a Deployment manifest via kubectl apply.
etcdConsistent distributed key-value store containing Kubernetes cluster state and configuration. Backups and availability are fundamental.Stores the declared Deployment, Service and other API objects.
kube-schedulerFinds appropriate worker nodes for unscheduled Pods based on requests, constraints, affinity, taints/tolerations and available resources.Places three Orders API replicas across eligible nodes.
kube-controller-managerRuns controllers that reconcile resources, such as Deployments/ReplicaSets (via their respective controllers), Nodes and other controllers.Detects when the desired replica count differs from reality and initiates corrections.
cloud-controller-managerIntegrates Kubernetes with cloud-provider APIs for cloud-specific resources. Functionality can vary by provider/integration.Coordinates cloud-aware node and load-balancer operations.
On Azure Kubernetes Service (AKS), Microsoft operates the managed Kubernetes control plane. You still configure and secure workloads, access, networking, and node-pool behavior according to the service model.

4. Worker nodes, kubelet, runtime and networking

Node componentWhat it actually does
kubeletNode-level agent that observes assigned Pod specifications and ensures their containers run and are monitored.
Container runtimeRuns OCI-compatible container images; Kubernetes uses the Container Runtime Interface (CRI). AKS commonly uses containerd.
Network dataplane / CNIProvides Pod connectivity and enforces network behavior based on the selected network implementation.
kube-proxy or replacement dataplaneImplements or replaces Kubernetes Service traffic forwarding; specifics depend on cluster networking mode.
Node poolsGroups of nodes with a common VM configuration and scheduling characteristics. AKS supports multiple pools for system and application workloads.

A node can be healthy while an application is unhealthy. Kubernetes therefore uses both node-level health and Pod/container-level readiness and liveness information.

5. Kubernetes building blocks — Pod, Deployment, ReplicaSet, Service and Namespace

Pods are ephemeral. Kubernetes can replace them at new IP addresses. Services provide stable discovery and routing so consumers do not need to track individual Pods.

6. Desired state and reconciliation — the Kubernetes operating model

  1. A developer submits a Deployment declaring replicas: 3.
  2. The API server validates and persists the resource specification.
  3. Deployment/ReplicaSet controllers create the required Pod objects.
  4. The scheduler binds unscheduled Pods to suitable worker nodes.
  5. Each node's kubelet asks the runtime to start the necessary containers.
  6. If a Pod disappears, controllers create a replacement to restore the declared replica count.
Key idea: Kubernetes does not promise that every Pod stays alive forever; it works to keep the required number of healthy workload instances available as resources permit. Readiness and failure handling still require correct application configuration.

7. Kubernetes networking and inbound HTTP request flow

The networking model allows Pods to communicate through their assigned network identities, while Services provide discovery and distribution across matching Pods. External HTTP access usually involves additional components.

LayerResponsibility
Azure Front Door / WAF (optional)Global HTTP entry, edge protections, traffic routing, and web application firewall policies.
Ingress controller or Gateway implementationReceives HTTP(S) traffic, applies host/path routing, and forwards to an appropriate Kubernetes Service.
Service (ClusterIP / LoadBalancer)Provides stable routing to eligible Pod endpoints; the exact public exposure depends on Service type and Azure integration.
EndpointSliceTracks backend endpoints used to route Service traffic.
Pod and Spring Boot REST APIProcesses the HTTP request; talks to downstream services such as a database.
NetworkPolicyRestricts permitted communication where supported by the selected CNI/dataplane.
Do not conflate these layers: Azure Front Door, Azure WAF, an NGINX ingress controller, and a Kubernetes Service are distinct technologies. An ingress controller is not automatically included in every AKS cluster; it must be selected and configured.

8. Stateless vs stateful workloads and persistent storage

Spring Boot REST APIs are commonly designed to be stateless: the same request can be handled by any available Pod, while durable data lives in a database or persistent service.

WorkloadStorage design
Stateless Orders APIContainer filesystem is disposable; application state belongs in managed data stores or distributed infrastructure.
File-processing workloadUses Azure Files or Azure Disk through a CSI driver and a PVC where suitable.
Managed MySQL / PostgreSQLOften hosted outside AKS to reduce database operations inside the cluster.
Prometheus / GrafanaMonitoring components may require persistent storage depending on deployment design.

Persistent Volumes are not the same thing as ordinary container image layers or temporary Pod filesystems.

9. Scaling, resilience, rolling releases and health probes

CapabilityWhat it changesImportant detail

Cluster AutoscalerAdjusts eligible node-pool capacity as Pods need more or fewer nodes.Cannot fix an application that is inherently non-scalable.
Rolling updateReplaces application Pods gradually with a new image.Configure readiness and rollout strategy to minimize downtime.

Liveness probeSignals when a failed container should be restarted.Avoid making liveness depend on transient external service outages.

PodDisruptionBudgetLimits voluntary disruptions during maintenance.Does not prevent all outages or involuntary failures.

10. Kubernetes security and identity boundaries

Kubernetes security is layered. A successful login to your Spring Boot application does not automatically grant administrative permission to the cluster, and cluster administrator privileges do not substitute for end-user authorization in the API.

ControlWhat it protects
Microsoft Entra ID / Kubernetes RBACCluster management authorization for operators, service accounts, and workloads as configured.
AKS workload identityFederates Kubernetes ServiceAccount identity with Microsoft Entra for access to supported Azure APIs without embedding secrets.
Azure Key VaultStores and governs keys, secrets and certificates; can integrate through CSI drivers or application SDKs.
Network policies / private network designLimits east-west traffic and public ingress as required.
Pod security controlsRestricts privileged containers, capabilities, filesystem permissions, and other risky settings.
Azure Policy / Defender for CloudGovernance, posture checks and security findings when enabled.
Azure Container Registry (ACR)Private image distribution with explicit image-pull authorization.
Principle of least privilege: the Orders API should have only the permissions it needs to retrieve its own secrets, communicate with its database and use its required services. It should not run as cluster administrator.

11. What AKS manages vs what your team manages

AKS is Azure's managed Kubernetes service. Its managed control plane reduces the work of operating Kubernetes masters, but it does not eliminate application, cluster configuration, networking and security responsibility.

LayerAzure AKS serviceYour application/platform team
Control planeManages hosted API-server and control-plane operation.Configures access, cluster version/upgrade strategy and integrations.
Worker nodesSupplies cloud infrastructure; platform offers node-pool management interfaces.Selects VM sizes, node pools, autoscaling, upgrades, capacity and workload placement.
ApplicationsProvides orchestration platform.Builds images, writes manifests, handles probes, observability and app security.
Traffic/securityIntegrates with Azure network and identity services.Chooses ingress, WAF, network policies, secrets and RBAC controls.
Data and resilienceProvides platform storage and zone integration options.Plans databases, backups, failover and recovery procedures.

Costs commonly include worker nodes, networking, storage, monitoring and optional AKS tier/add-ons. Choose features and regions based on current Microsoft documentation and your service-level objectives.

13. End-to-end request flow — web user to MySQL

Browser → DNS/TLS → Azure Front Door (optional) → WAF (optional) → AKS ingress → Kubernetes Service → Ready Spring Boot Pod → Database
  1. A customer sends an HTTPS request to api.retail.example.
  2. Azure Front Door may terminate TLS, apply configured WAF rules, and route to a protected origin.
  3. An ingress controller in/alongside AKS receives the request and selects the correct Service by host/path.
  4. The Kubernetes Service forwards traffic to an eligible Ready Pod.
  5. The Spring Boot controller authenticates/authorizes the request, invokes services, and accesses the database securely.
  6. The API returns its response and application telemetry flows to configured observability tools.

For multi-tenant applications, tenant authorization must be enforced at the API and data boundaries; choosing a namespace is not sufficient for data isolation.

14. CI/CD — how source code reaches production

  1. Commit: engineers push reviewed code to the source repository.
  2. Build: Maven compiles Spring Boot and runs automated tests and quality gates.
  3. Image: the pipeline creates and scans a versioned OCI image.
  4. Publish: the image is pushed to Azure Container Registry with appropriate permissions.
  5. Deploy: Helm, GitOps or Kubernetes YAML applies the required workload changes.
  6. Roll out: Kubernetes creates new Pods and checks readiness before shifting traffic.
  7. Observe/rollback: monitoring alerts on regressions and operators or automation restore an earlier version when needed.
Build and deployment jobs should use workload federation or other short-lived identities rather than hardcoded Azure credentials.

15. Minimal Spring Boot Kubernetes manifest — read every field

The following teaching example defines a Deployment and an internal Service. It assumes your Spring Boot application exposes Actuator readiness/liveness endpoints and an image already exists in ACR. Replace example placeholders before deployment.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: dev
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: orders-api
          image: myregistry.azurecr.io/orders-api:1.0.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: '1'
              memory: 1Gi
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            failureThreshold: 30
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 20
---
apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: dev
spec:
  type: ClusterIP
  selector:
    app: orders-api
  ports:
    - port: 80
      targetPort: 8080
YAML propertyMeaning
replicas: 3Three desired Pods.
selector / labelsAssociates Deployment/Service with intended Pods.
requests and limitsResource scheduling baseline and usage bounds.
startupProbeGives Java time to initialize.
readinessProbeControls whether Pod should receive traffic.
livenessProbeDetects when container needs restarting.
ClusterIPInternal-only Service; an ingress/Gateway or other exposure method is needed for public access.

18. Capstone lab — production-style Spring Boot deployment

Scenario: deploy an Orders API with a secure development and production workflow. Your deliverables are a diagram, manifest files, validation screenshots and a concise operational checklist.

  1. Choose an Azure region and explain availability-zone requirements.
  2. Design node pools, namespaces, application identity and the container registry.
  3. Define Deployments, Services and a chosen ingress/Gateway implementation.
  4. Explain API-level authentication/authorization and Key Vault integration.
  5. Configure CPU/memory requests, readiness/liveness/startup probes and scaling.
  6. Document TLS, WAF, network policies and private database connections.
  7. Describe how CI/CD builds and deploys versioned images and how to roll back.
  8. Plan metrics, logs, traces and actionable alerts.
