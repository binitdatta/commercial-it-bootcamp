Highly Available Azure App Service Across Two Regions

1. Read the architecture diagram

The diagram shows browsers and mobile clients on the left, Azure Front Door as the global HTTPS entry, primary and secondary Azure regions in the center, and supporting messaging, secrets, monitoring and observability services. Solid blue arrows denote normal traffic; a dotted blue arrow represents failover routing; and the red dotted arrow illustrates asynchronous database geo-replication.

Important diagram qualifications: This is a conceptual design, not an implementation-ready deployment. The arrows from Event Hubs and Service Bus toward SQL are not automatic connections: application or worker code must deliberately process messages and write to databases. SQL replication and App Service failover are separate mechanisms. Primary East US and secondary West Europe are illustrative regions, not an optimized region pairing.

2. Simple analogy: two offices serving the same customers

Imagine an online retailer operating two regional offices. A global receptionist (Front Door) sends customers to the active office. Each office has multiple clerks (App Service instances), a work-order box (Service Bus), and a continuous activity log (Event Hubs). The company’s transaction ledger (Azure SQL Database) has one authoritative writable copy and another copy in the backup office.

The backup office can answer customer requests only when its clerks, ledger and necessary services are ready. If the primary office is unavailable, an authorized recovery process may promote the backup ledger and redirect customers. Changing the receptionist’s routing alone does not promote the ledger.

3. What Azure App Service provides

Managed platformAzure App Service runs web applications and REST APIs without the customer managing the web-server operating system or underlying hosts.
App Service planSpecifies compute resources, pricing tier, instance count, OS, deployment region and scale capabilities; an App Service app runs on a plan.
Scale outMultiple worker instances of the same application support concurrent requests. Use autoscale rules and health checks in supported tiers.
Availability zonesZone redundancy is available only in supported plans/regions with appropriate configuration and instance counts; a regionally redundant app is not automatically multi-region.
DeploymentsDeploy with CI/CD, slots where supported, health probes, managed identities, structured logs and separate application settings per environment.

4. Two independent Azure regions

Primary regionThe example uses East US, hosting an App Service deployment and a writable primary Azure SQL Database.
Secondary regionThe example uses West Europe with a separate App Service deployment and a geo-secondary SQL database. This is an illustrative pair, not a recommended low-latency pairing.
Failure isolationApplication compute and critical dependencies must be independently available in each region; simply cloning the web app is insufficient.
Active-passive applicationNormally only the primary region handles production traffic while the secondary is deployed, configured and ready to receive failover traffic.
CapacityPre-provision sufficient capacity in the secondary region or account for cold/warm scaling during disaster recovery.

5. Azure Front Door: global entry and traffic switching

One public endpointClients use a single HTTPS hostname that resolves into Azure Front Door’s globally distributed service.
WAF policyA Web Application Firewall can block known Layer 7 exploit patterns, malicious bots or abusive request rates when correctly configured.
Origin groupsFront Door defines primary and secondary origins with priorities and health probes; healthy origins receive requests according to the configured strategy.
Failover nuanceFront Door can switch HTTP(S) requests when an origin becomes unhealthy, but it does NOT promote a database or guarantee transactional consistency.
Origin securityProtect App Service origins against Front Door bypass using approved origin access controls, TLS, and applicable private connectivity features.

6. Highly available SQL: primary and standby

Primary databaseIn the primary region, a writable Azure SQL Database handles transactions and typically already benefits from service-managed local availability.
Geo-secondaryAn asynchronous readable geo-secondary in another region provides disaster-recovery capability; possible data loss depends on replication lag at failover.
Failover groupFor Azure SQL Database, configure a failover group to manage a primary/secondary relationship and provide stable read-write/read-only listener endpoints.
Planned failoverA planned failover is coordinated when both sides are healthy and can minimize data loss; an unplanned/forced failover may lose the latest transactions.
Promotion and recoveryThe former standby becomes writable after promotion, and applications must reconnect through the listener; recovery and failback require deliberate operational planning.

7. Coordinate web failover with database promotion

Dependency awarenessThe secondary App Service must not accept write traffic to a read-only secondary database before SQL failover completes.
Health endpointApplication health probes should reflect critical backend readiness, not merely whether the process is alive.
Failover sequenceDetect outage → assess database state → promote standby if necessary → validate database connectivity → route traffic to healthy secondary origin → monitor.
Read/write endpointUse the failover group read-write listener for the transactional datasource so the application follows the writable database.
RPO / RTORecovery Point Objective measures acceptable lost data; Recovery Time Objective measures restoration time. Test both; neither is guaranteed to be zero.

8. Azure Event Hubs: telemetry and event streaming

Best fitHigh-volume clickstreams, inventory telemetry, application events and device messages sent by producers and read by independent analytics applications.
Partitioned logEvents append to partitions and remain readable for the configured retention period; readers use offsets and consumer groups.
Regional serviceAn Event Hubs namespace is regional; a namespace deployed in each region is not automatically a single active-active, fully replicated stream.
Resilience strategyDecide whether to provision independent regional namespaces, use supported geo-disaster-recovery/replication capabilities, and define producer/consumer reconnection and recovery semantics.
Ordering and duplicatesGuarantees are per partition, not global; downstream analytics should handle retries and duplicates.

9. Azure Service Bus: durable asynchronous messaging

Best fitEnterprise commands and workflows: create shipment, reserve stock, fulfill order, invoice payment, send notification.
Queue and topicQueues decouple one set of workers from publishers; topics and subscriptions enable fan-out routing to multiple subscribers.
Message processingPeek-lock, retries, dead-letter queues, duplicate detection and sessions (when configured) support more controlled workflow messaging.
Regional serviceService Bus namespaces are regional; failover across regions requires explicitly designed secondary namespaces and a supported recovery strategy.
Not the same as Event HubsService Bus is optimized for reliable enterprise message handling, whereas Event Hubs is optimized for event-stream ingestion and replay.

10. Choosing between streams and queues

Analytics eventA SaleCompleted event can be published to Event Hubs and consumed by independent real-time analytics processes.
Business commandA FulfillOrder command belongs in a Service Bus queue so a worker can complete the business task with retry/error handling.
IdempotencyBoth downstream consumers and workers must avoid duplicate business effects; define stable message IDs and appropriate deduplication strategies.
TransactionsWriting SQL and publishing to a broker do not form one atomic transaction by default; consider a transactional outbox and reliable publisher.

11. Key Vault, managed identity and secrets

Managed identityGive each App Service its own managed identity and grant only required access to Key Vault, Service Bus, Event Hubs or other resources.
Vault resiliencyThe infographic shows a shared Key Vault conceptually; a single regional dependency can be a recovery risk. Evaluate service resilience and regional recovery requirements.
Separate configurationKeep region-specific endpoints and settings independently deployable; do not store passwords in application source code.
Private networkingUse supported VNet integration, private endpoints, DNS, and firewall rules where required for defense in depth.

12. Monitoring and observability

Front DoorTrack origin health, 4xx/5xx rates, routing, latency, WAF matches and failover outcomes.
App ServiceCapture application response time, exceptions, instance health, CPU/memory signals and deployment errors.
SQL databaseWatch connectivity failures, geo-replication lag, failover status, errors and transaction performance.
MessagingTrack Event Hubs incoming/outgoing messages and consumer lag; track Service Bus active/dead-letter messages and processing failures.
AlertingDesign alerts tied to owner/on-call, severity, runbooks, synthetic transactions and repeatable disaster-recovery exercises.

13. CI/CD and deployment strategy

Two deploymentsProvision each regional App Service, SQL configuration, identity, messaging namespace and network settings from versioned IaC.
Same versionKeep both regional application builds compatible with the current database schema and messages.
Safe releaseTest in a nonproduction environment; use slots, gradual rollout or approved release strategy where applicable.
RollbackInclude database migration compatibility, deploy rollback and message-consumer compatibility in the runbook.

14. Three failure scenarios and their outcomes

Primary web app fails, SQL healthyFront Door can route to secondary App Service, but its connectivity to the primary writable SQL must be designed and tested for latency and network access.
Whole primary region failsSecondary App Service needs a writable SQL primary after promotion plus functional messaging, identity, secrets and monitoring before serving transactions.
Messaging outageKeep the core application behavior explicitly defined: queue writes may be retried; events may need buffering/outbox; avoid silent data loss.

15. Capstone: an order management system

Architecture deliverableDraw two regions and one Front Door, with regional App Service and SQL, plus clearly labeled Service Bus queues and Event Hubs streams.
Traffic matrixDocument hostname, origin, network paths, ports, identity and each dependency.
Failover runbookWrite the primary-region outage detection, SQL promotion, app-readiness validation, Front Door origin switching, failback and data-reconciliation steps.
Design reviewState a realistic RPO, RTO, expected failover cost and which services remain regional dependencies.

16. Trace normal operation and full-region failure

Normal purchase flow

  1. A browser connects through HTTPS to Azure Front Door.
  2. WAF and configured Front Door policies inspect/rout the HTTP request to the healthy primary App Service origin.
  3. Spring Boot validates authorization and writes order data to the current writable SQL primary through a stable endpoint.
  4. An outbox-based publisher or other reliable mechanism emits a business command to Service Bus and analytical events to Event Hubs.
  5. Workers process queued commands and analytics consumers handle streaming events; Application Insights records traces, metrics and exceptions.

Primary region outage

  1. Health probes and operational alerts identify that the primary application and/or regional dependencies are unavailable.
  2. Operations or supported automation verifies primary database state and initiates appropriate Azure SQL failover-group recovery.
  3. Secondary App Service verifies writable SQL connectivity, secrets, queues, streams and regional readiness.
  4. Front Door routes new requests to a healthy secondary origin under its configuration.
  5. Teams monitor data reconciliation, retries, duplicate messages, business continuity and later failback.
Front Door, SQL failover groups and messaging disaster recovery each have their own detection, sequencing and service-specific controls. Test them as one coherent application recovery process.

17. Review: critical design decisions

Design questionRecommended approach
Should secondary App Service be warm?For tight RTOs, deploy and verify sufficient regional capacity before failure.
Who selects the writable database?Azure SQL failover-group listener and application connection strategy, not Front Door.
Are Event Hubs and Service Bus multi-region by default?No. Design recovery and replication/movement semantics explicitly based on the services and tiers selected.
Can a regional database backup replace HA?No. Backup, zone redundancy, geo-replication and disaster recovery solve related but different risks.
What makes the application truly HA?Redundant compute, database, identity, messaging, networking, capacity, monitoring and regularly tested recovery.
