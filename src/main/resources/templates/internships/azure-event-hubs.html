2. What is Azure Event Hubs? A simple analogy

Imagine a huge railway station receiving streams of information instead of passengers. Thousands of stores, websites, vehicles and sensors continuously send events into the station. The platform accepts the arriving events, stores them temporarily in ordered tracks called partitions, and lets different teams read the same incoming stream independently.

One team tracks sales trends; another detects fraud; another archives data. They do not need each producer to communicate separately with every downstream system.

Important: An event hub is not a relational database. It is designed for high-volume event ingestion and sequential consumption, not ad hoc SQL queries or transactional updates.

4. How partitions, partition keys, and ordering work

Azure Event Hubs distributes events across partitions to allow ingestion and consumption in parallel. A producer may supply a partition key to consistently direct related events to the same partition. An event's offset identifies its location in that partition's append-only sequence.

ExamplePartitionProcessing implication
Store ID 108 → sale #1001, #1002, #1003Consistent partition chosen from key 108The store's events preserve their order within that partition.
Store ID 205 → sale #4001, #4002May map to another partitionCan be processed in parallel with store 108.

Ordering guarantee: ordering is per partition, not globally across every partition. Partition count and capacity configuration should be planned before production deployment.

5. How independent consumer groups work

One event can be processed by multiple applications without being removed when the first application reads it. Each application uses its own consumer group and maintains its own checkpoints.

Consumer groupReadsAction
fraud-detectorSales and refund eventsFlags suspicious transaction patterns.
inventory-analyticsSales eventsUpdates stock forecasts.
lake-archiverSales eventsWrites records for historical reporting.

Inside a processing application, consumers coordinate partition ownership so that one consumer in the group normally processes a given partition at a time. Checkpointing helps processing resume after a failure. Applications should still be designed to handle repeated delivery safely.

6. Retention, replay and long-term archiving

Event Hubs keeps ingested events for a configurable retention period. During that period, consumers can start reading from an earlier offset or timestamp to replay data. After events age out, the Event Hubs stream no longer provides them.

CapabilityPurposeLimitation
RetentionTemporary durable event streamDuration varies with tier/configuration.
ReplayReprocess previously ingested eventsOnly possible for still-retained events.
CaptureAutomatically archive batches to Blob Storage or ADLSRequires configuration and additional storage.
CheckpointingRemember consumer progressManaged by consumer application/framework, not an acknowledgement-based queue.
The diagram shows an example of one to seven days by default and up to 90 days. Do not treat these as universal limits: verify the supported retention range for your chosen Event Hubs tier before planning recovery or compliance requirements.

8. End-to-end retail event-streaming example

  1. Produce: a retail store records a purchase in its POS application.
  2. Publish: the POS backend sends a SaleCompleted event to an Azure Event Hub using an authenticated SDK or supported protocol.
  3. Partition: Event Hubs appends the event to a partition, using the store ID as a partition key where appropriate.
  4. Consume: Azure Functions, Stream Analytics, Databricks or a Spring Boot consumer application reads the event.
  5. Process: the consumer validates/enriches data and updates the dashboard, alerts or downstream services.
  6. Archive: Capture or a downstream archiving consumer stores events in Azure Blob Storage / ADLS for later analytics.
  7. Recover: after a failure, a consumer restarts from its checkpoint or replays from an earlier retained offset when needed.

9. Practical Spring Boot and Java integration concepts

Spring Boot services can publish to Event Hubs using the Azure Event Hubs Java SDK. A receiving application can use a processor client with checkpoint storage, or a supported Spring Cloud Azure integration.

Illustrative event payload

{
  "eventType": "SaleCompleted",
  "eventId": "sale-1001",
  "storeId": "108",
  "orderId": "ORD-90210",
  "amount": 129.95,
  "currency": "USD",
  "occurredAt": "2026-10-13T14:20:00Z"
}

Conceptual integration design

Application componentResponsibility
Spring Boot REST APIAccepts/validates the incoming order; stores the transaction reliably.

Azure Event HubIngests and retains the event stream across partitions.
Fraud consumerProcesses sale data and triggers high-risk alerts.

Architecture principle: publishing an event is not the same as committing a database transaction. Consider the transactional outbox pattern where consistency between committed business data and emitted events is critical.
