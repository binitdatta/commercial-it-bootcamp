How Azure Front Door Protects Applications from DDoS Attacks

2. Azure Front Door in simple English

Imagine a large office complex with many entrances. The building places security staff and visitor screening stations outside the offices, then directs legitimate visitors to the correct office. Suspicious visitors are blocked before they reach the employees. Front Door performs a similar function for public HTTP and HTTPS traffic: it provides a global edge entry point, applies configured controls and routes requests to healthy application origins.

Office-complex analogyAzure architecture
Visitors arriving at a public entranceWeb browsers, mobile apps and API clients
Worldwide security checkpointsMicrosoft global edge points of presence
Visitors screened for suspicious behaviorWAF managed/custom rules, bot protection and rate limiting
Reception directs visitors to available officesOrigin groups, health probes, and routing rules
Office doors remain locked behind receptionOrigin hardening and restricted direct access

Key message: Front Door is not your application server. It sits in front of application origins and is part of a defense-in-depth design.

3. What is a DDoS attack, and what does Front Door stop?

A Distributed Denial of Service (DDoS) attack floods a service with malicious traffic from many sources, trying to exhaust network capacity, connections or application resources. Attackers may also send carefully crafted HTTP requests that target expensive application endpoints or known vulnerabilities.

ThreatTypical symptomRelevant defense
Volumetric floodsExtremely high traffic aimed at overwhelming network pathsMicrosoft's large global edge/network mitigations; origin exposure reduction
Layer 7 HTTP request floodsExcessive requests to login, search or API endpointsWAF custom rules, rate limits, bot controls and application-level protections
SQL injection / XSS probesMalicious payload patterns in HTTP requestsWAF managed rules plus secure application coding
Direct-to-origin attacksRequests bypass Front Door and hit a backend directlyPrivate Link where supported, access restrictions and origin verification
Not a magic firewall: edge protection reduces risk but cannot guarantee that every malicious request is blocked. Strong authentication, server-side authorization, secure coding, capacity planning and incident response still matter.

5. Spring Boot API
Business logic
  1. A customer opens https://api.example.com/orders.
  2. DNS directs the customer toward the Front Door endpoint through its configured custom-domain routing.
  3. The client connects to an appropriate Microsoft edge location using HTTPS.
  4. A WAF policy, when associated with the request's domain/path, evaluates it. Rules may allow, block, log, or otherwise act according to configuration.
  5. Front Door selects an origin from an origin group based on route settings, origin priority/weight and health information.
  6. The healthy backend handles the request and Front Door returns the HTTP response to the client.

Request behavior depends on whether caching is enabled and eligible for the resource. Dynamic API responses are normally handled differently from cacheable static content.

6. WAF, OWASP rules, bot protection and rate limits

Managed rule sets

Managed WAF rules detect classes of common web attacks, such as injection attempts and cross-site scripting probes. They are a mitigation layer, not a substitute for validating data inside Spring Boot.

Custom rules

Security teams can add rules for selected IP ranges, countries/regions, request paths, headers and other supported conditions. Rate-limit rules help protect expensive endpoints like authentication, checkout and search.

RequestExample evaluationPossible action
Legitimate customer requesting product listNo rule matchAllow and route
Automated malicious SQL injection stringManaged rule detectionBlock or log, depending on policy mode
Thousands of login requests from a sourceRate limit threshold reachedBlock or other configured handling
Expected search-engine crawlerBot rules and custom policyEvaluate using selected rules and configuration
Production practice: deploy WAF rules in detection mode first where practical, evaluate false positives, tune exclusions narrowly, then enable prevention mode with alerts and a rollback plan.

7. Origin groups, health probes and failover

The diagram shows two backend groups: a primary region and one or more failover regions. Front Door can route requests to appropriate origins using configured routes, origin priorities, weights, latency-related behavior and health probes.

OriginPurposeExample
Primary regionNormally handles active application trafficAzure App Service / AKS / API Management in Region A
Failover regionServes traffic if preferred origins become unavailableSeparate regional deployment in Region B
Health probe endpointIndicates origin responsiveness/actuator/health/readiness when safely configured

Healthy routing requires a viable regional architecture. Front Door cannot replicate databases, synchronize sessions or make a broken application automatically stateless. Those responsibilities belong to your workload design.

8. Origin Shield concept and preventing bypass attacks

The purple Origin Shield box in the infographic conveys a design goal: keep backends insulated from unnecessary or hostile public traffic, and reduce repeated origin requests using appropriate edge caching. This is an architectural concept in the illustration, not necessarily a separate Azure product that you must deploy.

The more important security question is: can an attacker reach the origin directly without going through Front Door? If yes, the attacker may evade your WAF policy entirely.

Origin hardening optionWhat it achievesCaution
Azure Front Door Premium Private Link (supported origins)Private connectivity from Front Door to approved originsSupport depends on the origin type and configuration
Origin access restrictions / network controlsReduces routes that bypass Front DoorDo not rely on easily spoofed headers by themselves
Origin request verification / host settingsHelps ensure requests are routed and authenticated as expectedMaintain correct DNS, host-header and TLS settings
Cache static resources when appropriateOffloads repeat requests from the backendNever publicly cache user-specific responses containing private data

9. HTTPS, TLS termination and certificates

Front Door can terminate the client-side TLS connection at the global edge. It can then establish another secured connection to the backend origin using HTTPS. That means TLS is managed on two distinct network hops.

ConnectionParticipantsImportant controls
Client → Front DoorBrowser/mobile/API client and Microsoft edgeCustom-domain certificate, HTTPS enforcement, supported TLS versions
Front Door → OriginAzure edge and origin backendHTTPS origin protocol, valid certificate/hostname, correct origin host

TLS termination does not perform user authentication for your business APIs. Spring Security/Keycloak or Microsoft Entra ID remains responsible for validating application access tokens and authorization.

Operational principle: use consistent trace/request IDs across the edge and Spring Boot logs where possible. Correlating edge diagnostics with origin telemetry is essential to incident response.

12. Front Door vs Azure Application Gateway vs Azure DDoS Protection

ServicePrimary scopeTypical role
Azure Front DoorGlobal HTTP/HTTPS edgeGlobal application acceleration, WAF, origin routing and availability
Azure Application GatewayRegional application deliveryRegional Layer 7 load balancing and optional WAF
Azure DDoS ProtectionNetwork-layer protection for eligible public IPs/VNetsProtects supported network resources against volumetric/network attacks
Azure FirewallNetwork traffic controlCentralized network filtering across cloud network environments

These products solve related but not identical problems. A well-designed system may combine Front Door with regional services and network security controls depending on its deployment requirements.
