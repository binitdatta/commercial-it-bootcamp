Azure Global Cloud Architecture

From the global cloud down to the application running on a server: learn the physical and logical layers of Microsoft Azure in simple English.

Learning outcome: identify nine infrastructure layers, distinguish a region from an availability zone, and explain how your application runs on Azure resources.

1. Understand the nine layers

1 Azure Global Cloud

Microsoft operates a worldwide cloud infrastructure: networks, facilities, and supporting technology. Think of it as a huge international property portfolio connected by a private backbone network.

The global cloud is the broadest scope; your application is deployed to a much smaller, explicitly selected location.

2 Cloud Environment

Azure Public Cloud is an environment in which organizations create subscriptions and resources. The illustration also names Azure Government, Azure China, and Microsoft 365 to show that Microsoft offers different cloud environments and cloud services.

Important distinction: Microsoft 365 is a SaaS suite—not an Azure infrastructure environment that you would select when deploying an Azure VM. Azure Government and Azure China have separate operational and access considerations.

3 Geography

A geography is a broad geographic grouping of Azure regions, used in discussions of residency, compliance, and service placement. Examples in the image include North America, Europe, Asia, South America, Australia, Africa, and the Middle East.

A geography groups regions; it is not itself a single datacenter or an application deployment target.

4 Region

An Azure region is a named location where Azure services are available—for example, East US, West US 2, or Central US. When creating many resources, you select a region to determine where they run.

A region comprises one or more datacenters, and some regions provide multiple availability zones. Not every Azure service or VM size is available in every region.

5 Availability Zone

An availability zone is a physically separate location within a supported Azure region, with independent power, cooling and networking infrastructure. Deploying redundant workloads across zones can reduce the chance that one localized failure takes down everything.

Zones are not separate regions; they are distinct fault domains within a region. Zone support varies by region and service.

6 Datacenter

A datacenter is a physical facility containing servers, network equipment, storage, security systems, power, and cooling. Microsoft operates the facility. You ordinarily do not choose a particular building or rack when creating an Azure VM.

7 Cluster / Stamp / Rack / Server

Inside datacenters, physical machines are organized into racks and larger hardware groupings. A server supplies CPU, memory, disks, and network hardware. Azure's control plane and virtualization systems allocate that underlying capacity to services and customers.

You request a VM size or managed service; Azure handles the underlying hardware assignment.

8 Azure Service

Azure services turn infrastructure into usable capabilities. Examples shown include Virtual Machines, Azure SQL Database, Azure Storage, Azure Functions, Azure Kubernetes Service (AKS), Azure App Service, Cosmos DB, and analytics services.

9 Customer Workload

Your workload is the application and data that deliver a business result: a web application, mobile backend, REST API, analytics job, machine-learning model, IoT service, or backup process.

Example: a Spring Boot Orders API deployed on Azure App Service calling an Azure database. The application is your workload; App Service and the database are Azure services.

4. Availability: region vs. zone vs. server

One server failure

A VM or application instance can fail. Redundant instances help prevent a complete outage.

One availability-zone failure

Zone-redundant designs spread suitable resources across independent zonal locations.

Entire region outage

For stricter continuity goals, consider cross-region recovery or active-active designs, balancing complexity and cost.

Multiple zones improve fault tolerance, but availability is not automatic just because your application uses Azure.

6. Classroom exercise

Using the Azure Portal in a sandbox subscription, explore the hierarchy without provisioning chargeable resources:

  1. Open the portal and identify your current subscription.
  2. Open Resource groups and find an existing test resource group.
  3. Inspect the Location of a sample resource and identify its Azure region.
  4. Open the resource's documentation and determine whether it supports availability zones in that region.
  5. Write down what Azure operates and what your development team must still secure.

Deliverable: a one-page architecture sketch showing Region → Service → Workload, plus a simple responsibility table.

7. Knowledge check

Is an availability zone the same as a region?

No. An availability zone is a distinct physical location within a supported region.

When deploying an Azure VM, do you choose an exact rack or server?

No. You choose supported Azure configuration options, such as region, size, and relevant availability settings; Azure manages the physical placement.

Are Azure App Service and your Spring Boot API the same thing?

No. App Service is the hosting service; your Spring Boot API is the business workload running on it.

Does hosting in Azure automatically make my API highly available?

No. You still need an appropriate resilience design, supported service configuration, operational monitoring and recovery procedures.
