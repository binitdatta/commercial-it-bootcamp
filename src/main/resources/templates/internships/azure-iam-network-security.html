1. Understanding the architecture diagram

The infographic combines identity and governance on the left, global edge and regional infrastructure through the center, and network security controls on the right. Read the numbered layers from region through Front Door/WAF, availability zones, VNet subnets and compute instances.

Architecture clarification: The diagram is a teaching model rather than a literal packet path. Azure Front Door is a global edge service, not deployed inside each customer's region, and Microsoft Entra ID, Azure RBAC, NSGs and WAF govern different security boundaries. The services shown are not all mandatory for every application.

2. Microsoft Entra ID: Azure's identity foundation

What it doesMicrosoft Entra ID is the cloud identity platform for users, applications, service principals and managed identities. It authenticates identities and issues tokens; it does not, by itself, decide every application's business permissions.
Users, groups and devicesEmployees and guests can belong to groups, register devices and satisfy Conditional Access requirements such as multifactor authentication. Device trust and sign-in risk can influence access decisions.
Workload identityAn application may authenticate as a service principal or with an Azure managed identity. Managed identity avoids distributing long-lived application credentials.
ExampleAn administrator logs into the Azure portal; Entra ID authenticates them and an Azure RBAC assignment determines whether they can modify a virtual machine.

3. Azure RBAC, identity scopes and privilege management

Role assignmentsAzure role-based access control combines a security principal, a role definition and a scope. Scopes include management group, subscription, resource group and individual resource.
Built-in and custom rolesReader can view resources, Contributor manages most resources but cannot grant access, and Owner can manage resources and role assignments. Prefer narrowly scoped built-in or custom roles.
PIM and Just-in-TimePrivileged Identity Management can provide eligible, time-bounded elevation with approval, justification and auditing for privileged roles.
Network access is separateAn identity allowed to administer a database is not automatically allowed to connect to it over the network; NSGs, firewalls, routing and private endpoints are independent controls.

4. The five infrastructure layers in the infographic

Layer 1 — Azure regionA region is a geographic grouping of datacenters. Regions provide locations for workloads and data-residency decisions, and paired-region relationships differ by geography/service.
Layer 2 — Front Door and WAFAzure Front Door is a globally distributed application entry point. Its WAF filters HTTP(S) requests, while routing rules and origin groups forward accepted traffic to healthy backends.
Layer 3 — Availability zonesWhere supported, zones represent physically separate datacenter groupings inside a region. Spreading compute and data across zones mitigates some facility failures.
Layer 4 — VNet and subnetsAzure Virtual Network provides a private IP address space; subnets divide it into segments. NSGs, route tables and service-specific rules control permitted paths.
Layer 5 — ComputeVirtual machines, scale sets and applications run inside the network boundaries. Examples include Nginx, IIS, Java, .NET, Kafka, PostgreSQL and SQL Server.

5. Azure VNet, subnets, NSGs and routing

Address spacesA VNet such as 10.0.0.0/16 may contain subnets 10.0.1.0/24 through 10.0.6.0/24. Subnets must use non-overlapping ranges within the VNet.
Network Security GroupsNSGs use stateful allow/deny rules, priorities, direction, protocol, source and destination addresses, and ports. NSGs can be associated with a subnet or NIC.
Route tables (UDRs)User-defined routes override appropriate system routing decisions and can send traffic through a firewall or network virtual appliance.
Zero trust principlePlace workload types in distinct network segments; authorize identities separately; require authenticated, encrypted communication and do not assume that internal traffic is trustworthy.

6. Front Door, WAF and DDoS mitigation

Global edgeFront Door can accept HTTP(S) requests close to users and route them across Microsoft’s edge infrastructure.
WAFWAF policies protect web-facing routes through managed and custom application-layer rules, rate limits and bot rules according to configured capabilities.
DDoSAzure DDoS Network Protection and Front Door serve different traffic protection scenarios. Edge HTTP request filtering is not a substitute for every origin/network-layer control.
Origin securityProtect application origins against bypass using supported origin access restrictions, private connectivity where available, TLS, identity controls and monitoring.

7. Availability zones and resilience

Fault domainsSeparating replicas across availability zones helps reduce the blast radius of datacenter-level problems.
Zone-redundant designA zone-redundant service or carefully deployed redundant resources may span several zones. Support and configuration depend on the Azure service and region.
Recovery choicesZones protect against some localized faults; multi-region architectures address broader outages. Neither eliminates the need for backup, tested recovery and resilience engineering.

8. Azure Firewall, Private Link and private endpoints

Azure FirewallA managed, stateful network firewall providing centralized network/application rules, threat intelligence options and logging.
Private EndpointA private endpoint gives supported Azure PaaS services a private IP interface in a VNet, helping keep service access off public endpoints when properly configured.
DNS mattersPrivate DNS resolution must point clients to the private endpoint; otherwise an application may still resolve a public service address.
Layered protectionUse NSGs for subnet/NIC controls, Azure Firewall for central inspection, WAF for web attack patterns and private endpoints for PaaS reachability.

9. Tracing one browser request and one management action

Application trafficBrowser → Azure Front Door → WAF inspection → healthy origin → VNet/subnet → protected web/application tier → backend data service.
Administrative actionEngineer → Entra ID authentication and Conditional Access → Azure RBAC check → Azure Resource Manager operation → audited resource change.
Key distinctionHTTP request routing and infrastructure administration are different planes. Front Door does not replace Entra ID, application authentication or resource authorization.

10. Monitoring, audit and compliance

Identity telemetryReview Entra sign-in and audit logs for authentication, conditional-access outcomes and tenant changes.
Cloud control planeAzure Activity Log records many management operations. Azure Policy evaluates/enforces applicable resource rules.
Network telemetryUse Azure Monitor, diagnostic settings, NSG flow logs or their current supported successor, firewall logs, WAF logs and Defender for Cloud insights as applicable.
Operational disciplineDefine alert ownership, retention, investigation procedures, least-privilege access and periodic access reviews.

11. Spring Boot enterprise example

DeploymentRun a Spring Boot Orders API in an application subnet or managed hosting environment, with a separate database subnet or private database endpoint.
AuthenticationUse Spring Security as an OAuth2 resource server to validate Entra ID or Keycloak-issued JWTs and enforce permissions for order APIs.
Network rulesOnly expose the intended HTTPS entry point; restrict east-west and database connections to required ports and sources.
SecretsUse managed identity and Key Vault where possible. Never embed secrets or signing keys in application source code.
AvailabilityDeploy multiple instances and use health probes, autoscaling and tested regional or zonal failover appropriate to workload requirements.

13. Internship lab: secure an enterprise Spring Boot system

Scenario: A retailer runs a Spring Boot REST API backed by a managed SQL database. Staff access the application globally; only the application tier should communicate with the database.

  1. Define a VNet with separate public-entry, web, application, data, private-endpoint and management subnets.
  2. Draw an ingress path through Front Door and WAF to a healthy API origin.
  3. Design subnet/NIC NSG rules limiting API and database ports to approved sources.
  4. Assign managed identity to the workload and narrowly scoped RBAC assignments.
  5. Store secrets in Key Vault, with private endpoint connectivity where justified.
  6. Define zone or regional redundancy and the failover testing approach.
  7. List diagnostic logs, metrics, alert thresholds, and who responds to failures.
Deliverable: One architecture diagram, a network-flow matrix (source, destination, protocol, port, justification), an RBAC assignment matrix and a brief recovery plan.
