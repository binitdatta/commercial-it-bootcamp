1. Architecture diagram

This infographic shows the full Azure Key Vault ecosystem: applications and services authenticate through Microsoft Entra ID, permissions are enforced using RBAC or access policies, and secrets / keys / certificates are delivered securely to workloads such as web apps, APIs, virtual machines, containers and pipelines.

2. What Azure Key Vault is in simple English

Think of Azure Key Vault as a high-security bank locker for your application’s most sensitive items. Instead of writing database passwords, API keys, encryption keys or TLS certificates directly into Java code, YAML files or deployment scripts, you place them inside Key Vault and let approved applications retrieve them when needed.

Why this matters: if secrets are hardcoded into a repository, emailed around, or copied across environments, they eventually leak. Key Vault reduces that risk and makes auditing, rotation and access control much easier.
Without Key VaultWith Key Vault
Passwords stored in application.ymlApplications fetch secrets securely at runtime
Developers share certificates manuallyCertificates can be centrally stored and managed
Secret rotation is painful and error-proneRotation becomes governed and auditable
Hard to know who accessed whatAccess is governed by identity and logged

A beginner mistake is to call every sensitive value a “secret.” In practice, Azure separates these object types because their lifecycles, permissions and security requirements differ.

4. Access models — how applications are allowed to use Key Vault

Preferred model: Managed Identity

For Azure-hosted workloads such as App Service, Azure Functions, Container Apps, VMs or AKS, the cleanest pattern is to assign a managed identity to the resource. That identity authenticates to Microsoft Entra ID, receives permission to the vault, and accesses secrets without storing a long-lived client secret.

Other supported model: service principal / application registration

This is still common, but it introduces another credential that must itself be protected and rotated. When possible, managed identity is simpler and safer.

ModelBest forTrade-off
Managed IdentityAzure-hosted workloadsDepends on Azure resource identity support
Service PrincipalExternal apps, local development, CI toolsNeeds secret or certificate management
User / developer identityInteractive admin workNot suitable for headless production services

5. How Azure Key Vault works step by step

  1. An admin creates a Key Vault and stores secrets, keys or certificates in it.
  2. An application or Azure resource identifies itself through Microsoft Entra ID.
  3. Azure evaluates whether that identity has Key Vault permission through RBAC and/or access policy configuration.
  4. If authorized, the workload retrieves the needed secret, certificate or key operation securely.
  5. Azure Monitor, diagnostic logs and alerts can record the activity for auditing and troubleshooting.

The diagram also shows integrations with Azure App Service, Functions, Data Factory, SQL Database, Storage, AKS and Azure DevOps pipelines. This is what makes Key Vault central to enterprise platform design rather than just another password store.

6. Spring Boot example — why your Java application cares

Imagine your Commercial IT Bootcamp reference application runs on Azure App Service or Azure Container Apps and connects to Azure Database for MySQL. Instead of embedding credentials directly in application.yml, your workload can retrieve them from Key Vault.

Unsafe pattern

spring:
  datasource:
    url: jdbc:mysql://mydb.mysql.database.azure.com:3306/bootcamp
    username: bootcamp_app
    password: VerySensitivePassword123

Safer conceptual pattern

1. Store the datasource password as a secret in Azure Key Vault.
2. Give the App Service / Container App a managed identity.
3. Grant that identity permission to read the secret.
4. Resolve the secret at runtime and inject it into the application.
Important: Key Vault improves secret handling, but it does not replace application authorization. Your Spring Security rules, Keycloak / Entra login, and database access controls still matter.

7. Security features highlighted in the diagram

  • Entra ID integration: identity is the foundation of access control.
  • RBAC and fine-grained permissions: different teams can have different levels of access.
  • Soft delete and purge protection: reduces the risk of accidental or malicious deletion.
  • Network protection: firewalls and private endpoints reduce exposure to the public internet.
  • Audit logging and alerts: security teams can review access and detect suspicious use.
  • Customer-managed keys: useful for compliance-sensitive encryption scenarios.
  • High availability: the architecture supports resilience and enterprise operations.

8. Operations, pricing awareness and best practices

Best practices

  • Prefer managed identity for Azure resources whenever possible.
  • Use RBAC or access policies based on least privilege.
  • Enable soft delete and purge protection.
  • Rotate secrets and certificates on a schedule.
  • Restrict network access using firewalls or private endpoints where appropriate.
  • Turn on monitoring, diagnostic logging and alerts.
  • Separate development, test and production vaults.
