01 · Edge delivery and protection reference architecture

This architecture starts with user requests resolving through Amazon Route 53. Requests are routed to an appropriate CloudFront edge location, where eligible cached content may be served after applicable edge security evaluation. An AWS WAF Web ACL associated with the CloudFront distribution evaluates viewer requests; permitted cache misses and non-cacheable requests can be forwarded to protected origins such as an Application Load Balancer, Amazon S3, or Amazon API Gateway.

Architecture principle: CloudFront and WAF are complementary. CloudFront focuses on content delivery, caching, and origin offload. AWS WAF focuses on Layer 7 inspection, rule-based filtering, and threat mitigation.
Important note: Route 53 resolves DNS and does not proxy HTTP/S traffic. WAF is an inspection policy associated with the CloudFront distribution, not a separate network hop between CloudFront and the origin. The infographic depicts the WAF stage conceptually. AWS Shield protection also integrates with supported resources rather than creating another packet hop.

02 · Core concepts

Amazon CloudFront

A global content delivery network that serves content from edge locations closer to users. It reduces latency, improves perceived performance, and can offload work from origins by caching static and cacheable dynamic content.

AWS WAF

A web application firewall that inspects HTTP/S requests against Web ACL rules. It can allow, block, count, challenge, or rate-limit traffic based on IPs, headers, URIs, countries, bot signals, or managed rule groups.

Protected origins

Typical CloudFront origins include Application Load Balancers, S3 buckets, and API Gateway endpoints. These origins should be protected from direct public access where possible to force traffic through CloudFront and WAF.

AWS Shield

AWS Shield Standard provides baseline DDoS protection for CloudFront, Route 53, and other services. Shield Advanced adds additional controls, visibility, and support for higher-risk environments.

03 · End-to-end request flow

Step 1 — DNS lookup: The user resolves your hostname through Route 53 and receives the CloudFront distribution alias target.
Step 2 — Nearest edge selection: The request is routed to the closest or most appropriate CloudFront edge location based on AWS edge routing logic.
Step 3 — WAF inspection: AWS WAF evaluates the request against the Web ACL. Managed rules, custom rules, bot control, IP sets, and rate-based rules can be applied.
Step 4 — Cache decision: If the content is already cached and valid, CloudFront can return it without an origin request. If not, CloudFront forwards the request to the configured origin.
Step 5 — Origin response: The origin returns content to CloudFront. Based on cache policy, the response may be stored at the edge and reused for later requests.
Step 6 — Client delivery: The user receives the response through the edge network with reduced latency and improved scalability.
Example origin protection pattern
User -> Route 53 DNS -> CloudFront [WAF Web ACL] -> ALB -> private application instances
User -> Route 53 DNS -> CloudFront [WAF Web ACL] -> API Gateway
User -> Route 53 -> CloudFront -> S3 origin

05 · Design patterns and use cases

Static website and assets

Put static assets behind CloudFront for global delivery. Use S3 as the origin and restrict direct bucket access using Origin Access Control or an equivalent secure pattern.

Web application acceleration

Use CloudFront in front of an ALB-backed application to reduce latency, terminate TLS close to the user, and absorb traffic bursts.

API protection at the edge

Place CloudFront and WAF in front of API Gateway or ALB to filter malicious requests before they reach backend APIs. Rate-based rules can reduce abuse and credential stuffing attempts.

Login and authentication protection

Protect sign-in pages and sensitive application entry points using WAF managed rules, bot protection, IP reputation lists, and challenge / CAPTCHA-based controls where appropriate.

Best practice: Keep origins as private as possible and allow only CloudFront-mediated access whenever the workload pattern permits it.

06 · Security controls and rule strategy

Common WAF controls

  • Managed rule groups for common exploits and known bad patterns.
  • Custom rules for URI, method, header, or geo-based logic.
  • Rate-based rules to slow or block abusive request volumes.
  • IP sets for allow-lists or deny-lists.
  • Bot and fraud controls where supported and appropriate.

CloudFront security features

  • HTTPS/TLS enforcement and modern viewer protocol settings
  • Signed URLs and signed cookies for private content delivery
  • Origin Access Control for S3 protection
  • Origin failover for higher availability
  • Header forwarding and cache isolation controls
Security tuning matters: Overly aggressive WAF rules can block legitimate traffic. Always test in count or monitor mode before hard blocking when possible.

07 · Operations, logs, and observability

CloudFront observability

Use CloudFront access logs, cache hit ratio metrics, origin latency indicators, 4xx/5xx trends, and CloudWatch dashboards to measure delivery efficiency and user experience.

WAF observability

Track allowed, blocked, counted, and challenged requests. Review sampled requests and WAF logs to understand false positives, attack patterns, and rule effectiveness.

End-to-end tracing

Correlate CloudFront, WAF, ALB, API Gateway, and application logs to understand the full path of a request, especially when requests are unexpectedly blocked or bypass cache.

Release discipline

Manage cache behaviors, WAF rule changes, and header policies through infrastructure-as-code so that changes are reviewable, versioned, and repeatable.

08 · Guided AWS console lab

Goal: Front a sample application or asset origin with CloudFront and protect it using AWS WAF.

Step 1: Create or identify an origin such as an ALB-backed web app, an S3 bucket, or an API Gateway endpoint.
Step 2: Create a CloudFront distribution. Configure the origin, default behavior, cache policy, and HTTPS settings.
Step 3: Create a WAF Web ACL with CloudFront as its protected resource (global scope in us-east-1). Attach one AWS managed rule group and at least one custom or rate-based rule.
Step 4: Associate the Web ACL with the CloudFront distribution.
Step 5: If using a custom domain, create a Route 53 alias record pointing to the CloudFront distribution.
Step 6: Test allowed requests, intentionally suspicious requests, and repeated request bursts. Observe CloudFront and WAF behavior.
Step 7: Review logs and metrics. Confirm that blocked traffic is visible in WAF while successful requests flow through CloudFront to the origin.
Step 8: Tune cache and WAF rules. Then clean up test resources to avoid charges if the environment is temporary.

10 · Cost and performance considerations

CloudFront pricing is influenced by data transfer out, requests, invalidations beyond free tiers, and advanced features. WAF pricing commonly depends on the number of Web ACLs, rules, and requests inspected. Managed rule groups and advanced bot protections may introduce additional cost.

Optimize cost by tuning cache behavior, reducing unnecessary origin requests, attaching only the WAF rules you truly need, and using logging strategically. Optimize performance by improving cache hit ratio, selecting the right origin architecture, and minimizing dynamic response bottlenecks.

12 · Key terms and further reading

Edge location: a CloudFront point of presence. Web ACL: the AWS WAF rule container applied to protected resources. Origin: the backend resource that CloudFront serves from. Cache policy: controls how CloudFront caches and forwards request details. Origin Access Control: a secure way to restrict direct access to S3 when using CloudFront.
