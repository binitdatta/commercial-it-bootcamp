01 · End-to-end reference architecture

The diagram demonstrates EC2 virtual machines with attached root and data volumes, independently deployed instances in two Availability Zones, and EBS snapshot/backup protection. Operational services such as CloudWatch, Systems Manager, AWS KMS, and AWS Backup provide visibility, administration, encryption, and recovery orchestration.

Important technical correction to the conceptual infographic: An EBS volume resides in one Availability Zone and normally attaches to EC2 in that same AZ. EBS itself is not a cross-AZ shared volume or an application-level replication service. EBS snapshots can be used to create restored volumes in a different AZ; cross-Region recovery requires copying snapshots. Database high availability is an independent concern. EBS snapshots are stored in AWS-managed Amazon S3 storage, not generally in your own S3 bucket.

02 · EC2 block storage fundamentals

Amazon EBS

Durable block volumes exposed as devices to EC2. The operating system handles partitioning, filesystems, mount points, and application I/O. Volume lifecycle can outlast the EC2 instance.

Root and data volumes

Root volumes hold the boot operating system. Separate data volumes help isolate application data, performance needs, and backup policies. Configure DeleteOnTermination intentionally.

AZ-scoped resources

Standard EBS volumes are AZ-specific. Independent volumes and application replication support multi-AZ deployment patterns; snapshots assist recovery and relocation.

EC2 attachment

Most EBS volumes attach to one instance at a time. Multi-Attach is an exception available for supported Provisioned IOPS SSD volumes and compatible EC2 instances in the same AZ, and requires clustered-filesystem/application coordination.

04 · EBS volume lifecycle and operating-system steps

Create: Select EBS volume type, AZ, capacity, encryption/key, and optional snapshot source.
Attach: Choose an EC2 instance in the same AZ. The device name requested in AWS may map to a different OS-level path on Nitro instances.
Prepare: Inspect the device, create a filesystem only for a new blank volume, and mount it at the chosen application directory.
Operate: Monitor CloudWatch and OS-level metrics. Add a persistent mount with filesystem UUID rather than depending on unstable device names.
Modify: Use Elastic Volumes to grow capacity or adjust supported performance settings; expand the partition and filesystem separately as needed.
Detach and delete: Stop I/O, unmount cleanly, detach, and confirm the lifecycle/retention policy before deletion.
# Linux validation example: inspect; do not format an existing data device
lsblk -f
sudo file -s /dev/nvme1n1
sudo mkfs -t xfs /dev/nvme1n1       # ONLY on a confirmed new/blank volume
sudo mkdir -p /data
sudo mount /dev/nvme1n1 /data
sudo blkid /dev/nvme1n1
 df -h /data

Device names vary by instance family, operating system, and attachment order. Prefer EC2/NVMe volume identification and filesystem UUIDs. For an existing volume, formatting destroys its data.

05 · Availability Zone boundaries and high availability

EC2 and its ordinary attached EBS volumes operate in the same AZ. EBS stores data redundantly within that AZ, but EBS by itself does not provide cross-AZ availability. For a multi-AZ service, deploy EC2 instances and EBS volumes separately in each AZ, and use application/database replication or a managed data service where appropriate.

AZ failure scenario

When a volume's AZ is unavailable, the application cannot simply mount that same EBS volume from an EC2 instance in another AZ. Instead, restore from an available snapshot or use another independently replicated application node.

Multi-Region disaster recovery

Copy EBS snapshots to the recovery Region, align encryption/key access policies, and provision new volumes and EC2 instances in a target AZ. Validate RPO/RTO under realistic recovery tests.

06 · Snapshots, restore and AWS Backup

EBS snapshots represent point-in-time backups, typically incremental after the initial snapshot. AWS stores the snapshot data in its managed S3 infrastructure. Snapshot retention can be governed using Amazon Data Lifecycle Manager or AWS Backup plans with policies and recovery points.

1. Prepare consistency: Coordinate with applications; quiesce database/file activity or use an application-consistent procedure before initiating snapshots.
2. Capture: Create a snapshot or a coordinated multi-volume snapshot set. Snapshot creation can run while an attached volume remains in service, but consistency is a separate concern.
3. Automate: Define schedules, retention, cross-account or cross-Region copies where supported, resource tags, and AWS Backup vault controls.
4. Restore: Create a new EBS volume from the snapshot in the chosen AZ, attach it to EC2, then mount/validate application data.
5. Test: Run periodic recovery tests and measure elapsed restoration and application validation time—not just snapshot success.
Snapshot ≠ immediate hot standby. A snapshot provides a recovery point. It does not keep another AZ's EC2 application continuously synchronized. For fast database failover use application-level replication or services such as Amazon RDS Multi-AZ.

07 · EBS encryption, keys and access management

AWS KMS at rest

Enable EBS encryption by default at the account/Region level and choose the required KMS key. Encrypted volumes and their snapshots remain encrypted, subject to key availability, copy, and sharing controls.

IAM least privilege

Restrict permissions such as ec2:CreateVolume, ec2:AttachVolume, ec2:CreateSnapshot, and ec2:DeleteSnapshot. Use conditions/tags and appropriate KMS key grants and policies.

Host access

EBS encryption does not replace OS-level file permissions or application authentication. Prefer Systems Manager Session Manager for management without public SSH when supported.

Governance and audit

Track volume/snapshot API operations with CloudTrail; tag data classification and retention; validate backup vaults, recovery roles, and cross-account boundaries.

08 · Performance: IOPS, throughput and latency

IOPS measures completed I/O operations per second; throughput measures bytes moved per second; latency measures time to complete an individual operation. Required throughput depends on average I/O size and IOPS, and actual volume performance is constrained by both provisioned EBS settings and EC2 instance EBS bandwidth/IOPS capability.

Example: at a mean 16 KiB I/O size, 8,000 IOPS corresponds to about 125 MiB/s of data throughput if the workload sustains that average size; real performance depends on distribution and queue depth.

10 · Guided AWS hands-on exercise

Objective: Create an encrypted gp3 data volume, attach it to EC2, safely mount it, take a snapshot, restore into another AZ, then clean up. Use a sandbox account and monitor incurred costs.

Step 1: Launch a test EC2 instance in a selected AZ with Systems Manager access, an instance role, and a verified operating system image.
Step 2: In EC2 → Elastic Block Store → Volumes, create a new encrypted gp3 volume in the same AZ as the instance. Add project and retention tags.
Step 3: Attach the data volume to the instance. Use lsblk to identify the actual device, and verify that it is new and empty before formatting.
Step 4: Create an XFS or ext4 filesystem, mount under /data, create a test file, and optionally configure an /etc/fstab mount by filesystem UUID.
Step 5: Inspect gp3 IOPS/throughput settings and CloudWatch volume metrics. Record an initial performance baseline.
Step 6: Safely quiesce writes, create an EBS snapshot, and label its workload, date, and restore purpose.
Step 7: Create another volume from the snapshot in a different AZ of the same Region. Attach it to a separate test instance in that target AZ and verify the restored file.
Step 8: Test snapshot copying to another Region if DR is in scope; ensure KMS key permissions are valid at the destination.
Step 9: Unmount and detach test data volumes, remove unused snapshots/volumes, and terminate lab EC2 resources only after validating that nothing is needed.
Lab safety: Never run mkfs against a volume containing data. Validate the target device by EBS volume ID before preparing the filesystem. Snapshots and provisioned volumes can incur charges even after instances are stopped.

12 · Cost optimization and governance

Manage cost with volume-type selection, capacity rightsizing, provisioned IOPS and throughput, retention windows, and the lifecycle of unattached volumes and stale snapshots. gp3 often allows capacity, IOPS and throughput to be configured independently. Model pricing by Region and confirm current AWS rates, especially for premium provisioned-performance families and snapshot storage.

Reduce avoidable spend

Identify unattached volumes, oversized allocations, excessive provisioned gp3 performance, unneeded snapshots, and duplicated backup policies.

Govern responsibly

Tag environment, owner, application, data classification, cost center, backup policy, and deletion eligibility; automate periodic reviews with approvals before destructive cleanup.
