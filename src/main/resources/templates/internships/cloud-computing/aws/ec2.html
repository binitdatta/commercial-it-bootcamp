01 · Multi-AZ reference architecture

This enterprise reference design places an internet-facing Application Load Balancer across two public subnets and EC2 application instances across two private subnets. Amazon RDS resides in dedicated private database subnets. Route 53 resolves the application's hostname; CloudFront and AWS WAF are optional edge services. Amazon EBS supplies persistent per-instance volumes, Amazon EFS supports shared POSIX file storage, and Amazon S3 stores objects such as backups and artifacts.

Read the illustration as a conceptual architecture: an ALB is one logical load balancer with managed nodes deployed in enabled subnets, not two independent ALBs. AWS WAF attaches to supported resources such as CloudFront or ALB and is not necessarily a separate inline network appliance. An Auto Scaling group needs an AMI/launch template and desired capacity; it does not automatically provision or manage RDS.

For production, prefer private EC2 instances without public IPv4 addresses, multiple Availability Zones, least-privilege IAM roles, an ALB for inbound web traffic, Systems Manager Session Manager for administration, and appropriate routes to NAT gateways or VPC endpoints for outbound dependencies.

02 · EC2 fundamentals and lifecycle

What EC2 provides

Amazon Elastic Compute Cloud delivers configurable virtual machine capacity in an AWS Region and Availability Zone. You select an AMI, instance type, subnet, IAM instance profile, security groups, storage, and startup configuration.

EC2 lifecycle

Instances transition through pending, running, stopping, stopped, shutting-down, and terminated. Reboot preserves the current host assignment; stop/start for EBS-backed instances usually changes the underlying host and may change an automatically assigned public IPv4 address.

AMI and user data

An Amazon Machine Image defines the boot configuration, operating system, and optional software. User-data scripts commonly bootstrap the instance at launch; use configuration management or images for repeatable builds.

Instance identity

Use an instance profile with an IAM role for short-lived AWS credentials. Avoid embedding AWS keys in AMIs, user data, or application configuration.

Cost caution: EC2 compute charges depend on instance state, purchase option, and family. EBS volumes, Elastic IP addresses/public IPv4 addresses, NAT Gateways, load balancers, and data transfer may continue to incur separate charges.

04 · VPC, subnets and security groups

Each EC2 instance has at least one elastic network interface (ENI) in a selected subnet. The subnet's route table determines whether traffic remains local, reaches a Transit Gateway, or leaves through a NAT/Internet Gateway. A security group applies stateful allow rules to its associated ENI; a network ACL applies stateless subnet-boundary rules.

06 · Load balancing and EC2 Auto Scaling

An Auto Scaling group (ASG) maintains target instance capacity and can scale across selected subnets in multiple Availability Zones. A launch template defines AMI, instance type, IAM instance profile, security group, EBS layout, and user data. The group can register instances into an ALB target group and replace unhealthy nodes.

Step 1. Build a tested AMI or deterministic bootstrap sequence.
Step 2. Create a launch template; use an instance role and required security group.
Step 3. Configure an ALB and target group, with an application-specific health-check path.
Step 4. Create an ASG across at least two AZs, attached to the target group.
Step 5. Configure target-tracking, scheduled, or step scaling using appropriate metrics.
Step 6. Validate replacement during instance termination and AZ impairment drills.

Architectural distinction: EC2 Auto Scaling scales compute instances; RDS Multi-AZ handles database availability separately. For session-based applications, externalize state into shared backing services.

08 · IAM, secrets, hardening and patch management

Identity and secrets

Attach least-privilege IAM roles to instances. Use AWS Secrets Manager or Systems Manager Parameter Store instead of embedding secrets in AMIs or environment-specific scripts.

IMDSv2

Require Instance Metadata Service Version 2 where supported, constrain hop limits, and avoid accidental exposure of instance-role credentials through SSRF or proxies.

Private management

Use Systems Manager Session Manager with proper endpoints or egress, policies, and logging. Do not expose SSH (22) or RDP (3389) broadly to the internet.

Operating system hygiene

Automate patching, baseline security configuration, EBS encryption, vulnerability management, and image refreshes. Restrict egress and use immutable deployments where practical.

09 · CloudWatch, CloudTrail and operations

CloudWatch collects standard EC2 metrics such as CPU utilization, network traffic, and instance status checks. Use the CloudWatch agent for memory, disk filesystem, and application logs; these are not all present in the default EC2 metric set. CloudTrail records relevant AWS control-plane API activity. VPC Flow Logs help investigate permitted and rejected network flows.

10 · Hands-on AWS build exercise

Lab goal: Deploy a minimal two-AZ EC2 web tier with an ALB and launch-template-driven Auto Scaling. Use a sandbox account with a budget alert; ALBs, NAT Gateways, instances, and IPv4 addresses can create charges.

1. Network. Create a VPC, two public ALB subnets, and two private app subnets. Configure routes and required endpoints or NAT for the app instances.
2. Security. Create ALB-SG (443 inbound) and App-SG (application port inbound only from ALB-SG). Prefer no public IPs on private instances.
3. Identity. Create a least-privilege instance role with required SSM permissions and any controlled application permissions.
4. Launch template. Select a suitable AMI, instance type, storage, private subnet networking, role, and bootstrap user data that serves a simple HTTP endpoint.
5. Load balancer. Create an internet-facing ALB across both public subnets, a target group with the correct port, and a health check path.
6. Auto Scaling. Create an ASG with desired capacity two, min two, and a controlled max; place instances across the private subnets and connect the target group.
7. Observe. Check ALB target health, application responses, EC2 metrics, CloudWatch agent signals if configured, and ASG activities.
8. Validate resilience. Stop or terminate one disposable test instance and verify that the group restores desired capacity.
9. Harden. Validate no public instance IP, SSM administration, least privilege, EBS encryption, and appropriate TLS termination.
10. Clean up. Remove ASG, launch template, ALB, target group, NAT Gateways, endpoints, instances, EBS volumes, and other temporary billable resources.
