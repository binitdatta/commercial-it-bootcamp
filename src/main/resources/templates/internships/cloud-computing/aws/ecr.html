01 · ECR in the container delivery architecture

In the reference architecture, CI/CD builds and scans container images, pushes them into Amazon ECR, and then Kubernetes workloads running on Amazon EKS pull those images when deployments occur. ECR sits in the software supply chain as the secure registry layer between build systems and runtime platforms.

Key idea: ECR stores container images; it does not run containers. Runtime services such as EKS, ECS, or other container platforms pull images from ECR.

02 · Core ECR concepts

Repository

A repository stores related images, usually grouped by application or service such as orders-api or web-frontend.

Image tag

Tags identify versions such as v1.2.0, main-20261015, or latest. Production teams should prefer immutable version tags over relying only on latest.

Registry authentication

Push and pull operations require authenticated access through AWS IAM-integrated mechanisms.

Security scanning

ECR can scan images for known vulnerabilities to help identify risky software components before deployment.

04 · Security, scanning, and governance

  • Grant least-privilege push/pull permissions using IAM policies.
  • Enable vulnerability scanning to identify known CVEs in image layers.
  • Use repository policies where cross-account access is required.
  • Adopt naming, tagging, and retention standards across teams.
Best practice: A clean registry is part of supply-chain security. Delete obsolete images, scan continuously, and avoid unmanaged ad hoc repositories.

05 · Authentication and access patterns

Developers and CI/CD

Build systems authenticate to ECR to push images after successful build and test pipelines.

Runtime pull access

EKS worker nodes or pod identities need the required permissions to pull images from ECR at deployment time.

Cross-account sharing

Repository policies or organizational sharing models can support central image registries serving multiple AWS accounts.

Private access patterns

Use VPC endpoints and private routing strategies when you want container pulls without broad internet exposure.

06 · Replication and lifecycle management

ECR supports cross-account and cross-region replication for resilience, locality, and organizational distribution patterns. Lifecycle policies help remove older images automatically based on tag prefixes, count, or age conditions.

CapabilityValue
Cross-region replicationReduces dependency on one region and brings images closer to workloads
Cross-account replicationSupports centralized image governance across AWS accounts
Lifecycle policiesAutomates cleanup and lowers registry sprawl
Scan on pushProvides immediate visibility into image vulnerabilities after upload

07 · ECR with Amazon EKS

In an EKS platform, ECR is typically the default image source for internal workloads. Kubernetes manifests reference ECR image URIs, and the cluster pulls those images when creating pods. This makes ECR a critical dependency in the deployment path.

Build: CI/CD builds the container image.
Scan: The image is scanned and approved for deployment.
Push: CI/CD pushes the image into ECR.
Deploy: EKS Deployment or Helm release references the ECR image tag.
Pull: Worker nodes or runtime environment pull the image from ECR.

11 · Cost and registry hygiene

ECR cost is driven mainly by image storage and data transfer. Good registry hygiene lowers cost and also improves usability: remove dead tags, archive intentionally, and replicate only where justified by business needs.
