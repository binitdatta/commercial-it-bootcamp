01 · EKS + ECR reference architecture

This end-to-end architecture starts with developers and a CI/CD pipeline building and scanning container images, storing them in Amazon ECR, and then deploying Kubernetes workloads into Amazon EKS. EKS runs a managed control plane while application pods execute on managed node groups or AWS Fargate inside private subnets. Add-ons such as the AWS Load Balancer Controller, IAM Roles for Service Accounts (IRSA), CloudWatch Container Insights, and EBS/EFS integrations round out the platform.

Architecture principle: EKS orchestrates containers; ECR stores container images. Your CI/CD pipeline typically pushes images into ECR, while EKS pulls those images when Kubernetes workloads are deployed or updated.
Important note: EKS does not eliminate Kubernetes complexity. AWS manages the control plane, but you still design networking, RBAC, storage, observability, upgrades, and workload rollout strategies.

02 · Core EKS concepts

Managed control plane

AWS manages the Kubernetes API server, etcd, scheduler, and controllers across multiple AZs for high availability and operational resilience.

Worker capacity

Application pods run on managed node groups (EC2-backed worker nodes) or AWS Fargate for serverless container execution.

Kubernetes primitives

Deployments, StatefulSets, Services, Ingress, ConfigMaps, Secrets, and Horizontal Pod Autoscalers remain central to application design.

AWS integrations

EKS integrates with IAM, VPC CNI networking, Elastic Load Balancing, EBS/EFS storage drivers, CloudWatch, and ECR.

03 · Control plane vs data plane

LayerWhat AWS managesWhat you manage
Control planeKubernetes API server, etcd, scheduler, control plane HA and patching for the managed cluster serviceCluster version lifecycle planning, add-ons, admission controls, and overall operational policy
Data planeManaged node group orchestration services or Fargate platformNode group design, instance families, pod scheduling strategy, DaemonSets, workload resources, and container runtime behavior
ApplicationsNone of the application logicContainer images, manifests, Helm charts, runtime config, secrets, scaling, and rollout safety
Typical production split
- EKS control plane: AWS-managed
- Worker nodes: managed node groups (EC2) or Fargate
- Images: stored in Amazon ECR
- Ingress: ALB/NLB via AWS Load Balancer Controller
- Logs/metrics: CloudWatch / Container Insights

04 · Networking model

EKS commonly runs in a VPC using private subnets for worker capacity and public subnets for internet-facing load balancers. The VPC CNI plugin gives pods IP addresses from VPC subnets, which provides native network reachability but requires subnet planning.

Ingress

Use the AWS Load Balancer Controller to translate Kubernetes Ingress resources or Services into ALB/NLB resources.

Service-to-service traffic

Cluster-internal communication usually travels through Kubernetes Services, CoreDNS, and pod IP networking inside the VPC.

Private vs public design

Keep worker nodes private when possible. Expose only the load balancer layer or private internal services as needed.

Network policy

Security groups, pod-level network policies, and namespace segmentation all contribute to workload isolation.

05 · Security, IAM, and RBAC

  • IAM authentication controls who can access the EKS cluster.
  • Kubernetes RBAC controls what authenticated identities can do inside the cluster.
  • IAM Roles for Service Accounts (IRSA) lets pods access AWS services without node-wide credentials.
  • Secrets management can be handled with Kubernetes Secrets, external secret providers, or AWS service integrations.
Best practice: Avoid granting broad IAM permissions to worker nodes. Prefer fine-grained permissions via IRSA for individual workloads.

06 · Storage and stateful workloads

Amazon EBS CSI

Use EBS-backed persistent volumes for block storage needs, especially for zone-local stateful workloads.

Amazon EFS

Use EFS when multiple pods need a shared file system across Availability Zones.

Databases and caches

Most production applications keep durable state in managed services such as Amazon RDS or ElastiCache rather than inside containers.

Artifact and object storage

Use Amazon S3 for assets, backups, reports, and application object storage needs.

07 · Scaling and operations

EKS can scale at multiple layers: Kubernetes Horizontal Pod Autoscaler for pods, Cluster Autoscaler or Karpenter for nodes, and managed node groups for underlying compute capacity. Monitoring usually includes CloudWatch metrics, logs, and container observability dashboards.

Scaling layerMechanismTypical signal
Pod scalingHorizontal Pod AutoscalerCPU, memory, or custom metrics
Node scalingCluster Autoscaler / KarpenterUnschedulable pods, capacity pressure
Ingress capacityALB/NLB scale behaviorTraffic demand and backend health

08 · Deployment workflow

Step 1: Developers commit application code and container definitions.
Step 2: CI/CD builds the image, runs tests, scans for vulnerabilities, and tags the image.
Step 3: The pipeline pushes the image to Amazon ECR.
Step 4: Deployment tooling updates Kubernetes manifests, Helm charts, or GitOps state.
Step 5: EKS pulls the image from ECR and creates or updates pods.
Step 6: Services and Ingress expose the workload and health checks validate readiness.

09 · Guided hands-on lab

Step 1: Create or identify an ECR repository for your application image.
Step 2: Create an EKS cluster with managed node groups across at least two Availability Zones.
Step 3: Install kubectl, eksctl or your preferred provisioning tooling, and verify cluster access.
Step 4: Push a sample application image into ECR.
Step 5: Deploy a Kubernetes Deployment and Service using the ECR image URI.
Step 6: Install the AWS Load Balancer Controller and expose the app using an Ingress or LoadBalancer Service.
Step 7: Scale the deployment and observe pod placement, node behavior, and metrics.
Step 8: Clean up the cluster and load balancer resources when finished.

11 · Cost and design tradeoffs

EKS provides a highly capable Kubernetes platform, but it introduces cost and operational complexity. Managed node groups give more control and may reduce runtime cost for steady workloads, while Fargate simplifies node operations for certain workloads at potentially higher unit cost. Logging, load balancers, NAT, and cross-AZ traffic can materially influence total cost.
