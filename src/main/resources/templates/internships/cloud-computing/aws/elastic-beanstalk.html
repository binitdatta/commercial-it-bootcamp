01 · Enterprise reference architecture

Elastic Beanstalk coordinates an application environment backed by AWS services in your AWS account. For a load-balanced production environment, an internet-facing ALB can span public subnets in two Availability Zones, while an Auto Scaling group runs application EC2 instances in private subnets. Traffic reaches the application through a target group and the instances access approved AWS services using instance profiles, VPC endpoints, or appropriate egress.

Correct architecture interpretation: A single logical ALB operates across multiple enabled subnets; the two drawn nodes are not two separately provisioned ALBs. The EC2 instances belong to one Auto Scaling group spanning the Availability Zones. RDS, S3, and other dependencies are separate integrations and are not automatically created with every Beanstalk environment.
Infrastructure responsibility: Beanstalk manages orchestration, but you remain responsible for appropriate IAM permissions, secure application configuration, database lifecycle, backup retention, platform updates, and costs.

02 · Elastic Beanstalk fundamentals

Application

Logical top-level container for environments, application versions, and saved configurations. A single application can have development, QA, and production environments.

Application version

A labeled source bundle, commonly backed by Amazon S3, that can be deployed to an environment. Versions can be reused for recovery or promoted through stages.

Environment

Running infrastructure and deployed application configuration. A web-server environment may have an ALB and ASG; a worker environment processes queued jobs.

Environment configuration

Controls instance configuration, networking, capacity, platform, health reporting, rolling updates, deployment policy, logging, and environment properties.

04 · Web-server, worker, and lifecycle environments

Single-instance versus load-balanced

A single-instance environment is useful for demos and low-cost development, but it is not an HA design. A load-balanced environment coordinates EC2 capacity with Elastic Load Balancing and Auto Scaling for scale and fault tolerance.

Worker environment

A worker environment can process background tasks from SQS through the Beanstalk worker infrastructure. It is useful for asynchronous jobs instead of direct browser traffic.

Development-to-production progression

Maintain independent environments for development, staging, and production. Version promotion and immutable deployment practices reduce drift and support repeatable releases.

05 · Application deployment lifecycle

1. Build: Create a tested Spring Boot artifact and ensure the application starts with a configurable HTTP port and externalized configuration.
2. Package: Build a valid Beanstalk source bundle, Procfile where applicable, and optional configuration files.
3. Register: Publish a new application version, typically stored in S3.
4. Deploy: Choose the target environment and its deployment policy; Beanstalk orchestrates the change.
5. Validate: Check enhanced health, ALB target health, application readiness, metrics, and logs.
6. Promote or recover: Move an approved version through environments or redeploy a prior healthy version if necessary.
./mvnw clean package -DskipTests
# Example Procfile (when the selected Java platform requires it):
web: java -jar app.jar

# Basic EB CLI workflow (after credentials and EB CLI installation):
eb init
eb create bootcamp-dev
eb deploy
 eb status
Port note: The proxy-to-application port is controlled by platform conventions and configuration. Confirm the selected Java platform's process and port requirements instead of assuming that Spring Boot's default 8080 always matches the proxy configuration.

06 · VPC networking and high availability

In a typical production architecture, the public ALB spans at least two public subnets, private EC2 instances span two or more private subnets, and any database resides in its own controlled subnet group. Configure VPC routes, subnet capacity, security groups, listener/target health checks, and outbound access explicitly.

07 · Configuration and environment properties

Use environment properties for non-secret runtime settings such as environment names, feature toggles, and API endpoints. Store secrets in purpose-built secret-management services and retrieve them with an appropriately scoped IAM role or a supported secret reference mechanism.

Saved configuration

Persist environment configuration for repeatability. Review settings that can trigger replacement or downtime before applying changes.

.ebextensions and .platform

Supply supported application/environment customization, hooks, proxy settings, and platform-specific configurations. Validate on the actual platform branch.

IAM instance profile

Provides scoped EC2 access to S3, SSM, CloudWatch, and other services. Keep environment service-role permissions separate from application runtime permissions.

External dependencies

Prefer independent databases and caches with separate lifecycle management so terminating an environment does not accidentally remove business data.

09 · Identity, security, and governance

  • Use dedicated IAM service roles for Beanstalk and least-privilege EC2 instance profiles for application workloads.
  • Terminate HTTPS on the ALB using ACM certificates; enforce HTTPS redirects where appropriate.
  • Keep application instances and data services private; tightly scope ingress from the ALB security group.
  • Restrict SSH or eliminate it using Systems Manager Session Manager where supported.
  • Protect secrets using Secrets Manager or Parameter Store, avoiding plaintext credentials in application source or build artifacts.
  • Enable CloudTrail, appropriate logging, encryption, vulnerability management, and resource tagging.

10 · Health monitoring and operations

Elastic Beanstalk reports environment health status and related events. Use enhanced health where available and correlate it with CloudWatch metrics and alarms, ALB 4xx/5xx and target response times, EC2 metrics, log streams, and application traces.

Environment health

Review degraded instance counts, request health, startup failures, and deployment events.

CloudWatch Logs

Configure log streaming/retention; correlate application failures with deployment or scaling events.

ALB target health

Use a stable readiness endpoint and verify health check path, port, expected response code, and grace periods.

Alarms

Set thresholds on error rate, response time, unhealthy hosts, elevated CPU, and exhausted capacity.

11 · Step-by-step Spring Boot hands-on lab

Goal: Deploy a simple Spring Boot REST application on Elastic Beanstalk, exercise its health checks, and validate an application-version update. Use a sandbox account with spending alerts; ALBs and EC2 instances incur charges.

Step 1: Prepare a Java 21 Spring Boot application with a /api/hello endpoint and a health/readiness endpoint.
Step 2: Build the artifact using Maven and inspect the resulting JAR.
Step 3: Open Elastic Beanstalk and create an application with a supported Corretto Java platform branch.
Step 4: Choose a single-instance sandbox to minimize cost or a load-balanced environment for multi-AZ architecture validation.
Step 5: Select the IAM service role and EC2 instance profile; verify their trust policies and permissions.
Step 6: Configure the VPC/subnets, application/process port, security groups, deployment policy, log streaming, and health check path.
Step 7: Upload the tested application bundle, monitor environment events, and wait for a healthy environment.
Step 8: Call the endpoint using the environment URL and verify application logs.
Step 9: Change the response, publish a second version, deploy with a controlled strategy, and verify updated traffic.
Step 10: Review CloudWatch and Beanstalk health; optionally redeploy an earlier version. Terminate the temporary environment and clean up unused resources.

14 · Cost optimization and operational governance

Elastic Beanstalk itself generally has no additional charge beyond the AWS resources it provisions. You pay for underlying EC2, EBS, load balancers, data transfer, logging, and other consumed services. A load-balanced environment costs more than a single-instance sandbox.

Use AWS Budgets, cost-allocation tags, suitable instance types, sensible scaling boundaries, log retention controls, and environment termination procedures. Treat data stores as independent resources and review service quotas, platform retirement notices, and patch windows.
