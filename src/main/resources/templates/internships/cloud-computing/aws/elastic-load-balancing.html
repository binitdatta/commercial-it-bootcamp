01 · End-to-end reference architecture

Route 53 resolves the application hostname to an internet-facing Application Load Balancer. The ALB accepts HTTPS on port 443 and forwards requests to healthy private application targets spread across two Availability Zones. Databases remain in private subnets; they are not load-balancer targets in this example.

A load balancer deploys nodes in enabled subnets; it is not a single EC2 instance placed in one subnet. Public ALBs require suitable public subnets in multiple AZs.

02 · Elastic Load Balancing fundamentals

Elastic Load Balancing distributes traffic across registered targets, performs target health checks, and automatically adjusts underlying load-balancing capacity. Clients reach the load balancer DNS name; application teams manage listeners, rules, target groups, health checks, and security policy rather than individual front-end addresses.

  • Listener: a protocol and port receiving connections (for example, HTTPS:443).
  • Target group: backend targets, health checks, and routing configuration.
  • Availability Zones: spread load-balancer nodes and targets across failure domains.
  • Internal vs internet-facing: scheme determines whether the load balancer is private-only or reachable from the internet.

04 · Application Load Balancer deep dive

HTTP-aware routing

Use listener rules to send /api/* to an API target group and /web/* to a web target group. Rules are evaluated by priority; the default rule acts as a fallback. Hostname matching can serve multiple domains from one ALB.

TLS and authentication

Use an HTTPS listener with an AWS Certificate Manager certificate and an approved SSL policy. An ALB can authenticate users using OIDC or Amazon Cognito; application authorization still belongs in the backend.

Target groups

Targets can be EC2 instance IDs, IP addresses, or Lambda functions, depending on the target group. Choose health-check path and success codes that reflect service readiness, not merely whether a TCP socket opens.

05 · Network Load Balancer deep dive

NLB operates at the transport layer and is appropriate for non-HTTP protocols, low-latency/high-throughput connections, and architectures requiring static front-end IP addresses. It supports TLS listeners and can pass through TCP to application-managed TLS endpoints. Features vary by listener protocol, target type, and AWS region.

  • Use a TCP listener for application-managed end-to-end TLS when appropriate.
  • Use health checks to avoid targets that cannot receive new connections.
  • Client source IP preservation depends on target type and configuration; validate requirements explicitly.
  • For static internet-facing addresses, consider one Elastic IP allocation per enabled AZ where supported.

07 · Security, networking, observability

For an internet-facing ALB, allow inbound TCP 443 from authorized clients to the ALB security group, then allow application traffic only from the ALB security group to private targets. For NLB, evaluate NLB security group support, client-IP settings, and target security group rules. Subnet NACLs remain stateless and must permit necessary return paths.

  • Monitor CloudWatch metrics such as HealthyHostCount, HTTPCode_ELB_5XX_Count, TargetResponseTime, and request counts where applicable.
  • Enable ALB access logs to S3 when request tracing and audit requirements justify them.
  • Use AWS WAF with ALB for HTTP-layer protections; WAF is not a generic feature of NLB.
  • Apply at least two AZs with enough registered healthy targets, and avoid relying on a single target.

08 · Hands-on AWS lab

  • Create VPC 10.20.0.0/16 with two public subnets (10.20.1.0/24, 10.20.2.0/24) and two private app subnets (10.20.11.0/24, 10.20.12.0/24).
  • Deploy two HTTP test services privately across AZs; permit app traffic from the ALB security group.
  • Create a target group (instance or IP targets), choose a health check such as /health, and register both targets.
  • Create an internet-facing ALB in both public subnets with HTTPS:443 and ACM certificate; configure a listener forwarding to the target group.
  • Add host/path rules for a second application or path; observe rule priority and default action.
  • Use Route 53 public hosted-zone alias record to point an application hostname to the ALB.
  • Stop one test service and verify health-check failure, routing to healthy targets, and restoration.
  • For comparison, create an NLB TCP listener targeting a TCP test endpoint, then record differences in listener behavior and front-end IPs.
