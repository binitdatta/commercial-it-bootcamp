Internet & NAT Gateways

Learn how to design inbound Internet connectivity for public-facing workloads and controlled outbound connectivity for private application tiers using an Internet Gateway (IGW), NAT Gateway, and VPC route tables.

01 · Reference architecture — two-AZ VPC

Our reference VPC uses 10.0.0.0/16 and six /24 subnets across two Availability Zones. The internet-facing Application Load Balancer (ALB) is attached to the public subnets, private EC2 instances serve application traffic, and RDS resides in isolated database subnets. Each Availability Zone has its own public NAT Gateway for availability and to reduce cross-AZ egress dependency.

Traffic intent: Internet users reach only the public ALB. Application instances initiate outbound Internet connections through same-AZ NAT Gateways. NAT Gateways do not accept unsolicited inbound Internet connections to private instances.

02 · Internet Gateway vs. NAT Gateway

Internet Gateway (IGW)

A horizontally scaled, highly available VPC attachment that provides an Internet route target for Internet-routable traffic. For IPv4, a public resource generally needs a public IPv4 address (or EIP), permissive routes and security controls, and a path through the IGW. The IGW provides the public/private IPv4 translation for eligible resources.

Public NAT Gateway

Managed outbound address translation for IPv4 traffic from private subnets. Place it in a public subnet, associate an Elastic IP, and use its NAT Gateway ID as the private subnet's default route. Its public Internet egress goes via the IGW.

Private NAT Gateway

A distinct AWS NAT Gateway connectivity type for translation toward private networks (for example, through Transit Gateway or a virtual private gateway). It is not an Internet egress substitute and does not use an Elastic IP.

Egress-only Internet Gateway

For IPv6 private workloads requiring outbound-only Internet initiation, an egress-only IGW can provide a default IPv6 route (::/0) while refusing Internet-initiated inbound connections.

Important: A subnet is "public" because its effective route table includes a route to an IGW, not simply because it contains an ALB or NAT Gateway. NAT Gateways cannot have Security Groups associated with them; use workload Security Groups and subnet NACLs instead.

Each /24 contains 256 IPv4 addresses, of which AWS reserves five, leaving 251 usable private addresses in a typical subnet. Plan sufficient headroom for ALB IP requirements, ECS task ENIs, and scaling events.

Routing precedence: AWS selects the most specific matching prefix (longest-prefix match). A more-specific S3 gateway endpoint prefix-list route or transit route may override a broad 0.0.0.0/0 NAT route where applicable.

05 · Follow the packets

  1. Customer HTTPS ingress: Browser → public DNS → ALB listener on TCP/443 via public subnets and Internet Gateway → target EC2/private app subnet. ALB security group permits approved ingress; app security group trusts ALB SG.
  2. Application outbound request: EC2 (10.0.3.x) → private subnet's 0.0.0.0/0 route → NAT Gateway in public subnet A → IGW → external API. Return packets traverse the NAT connection state back to EC2.
  3. Database connection: App (10.0.3.x) → local route → RDS private address (10.0.5.x), with DB SG allowing only app-SG on the DB port. Neither NAT nor IGW is required for VPC-local traffic.
  4. S3 retrieval with gateway endpoint: App → route to the S3 prefix list pointing at the gateway endpoint, rather than traversing a NAT Gateway. Configure endpoint policy and IAM correctly.
  5. Unsolicited external request to private EC2: No public address / inbound IGW path; the NAT Gateway does not provide inbound port forwarding to the instance.
DNS names such as an ALB alias are not equivalent to routes. DNS resolution determines addresses; route tables and security controls determine actual packet forwarding and access.

06 · High availability, failure modes, and cost

Use one public NAT Gateway in each AZ for critical private egress. Associate AZ A private application subnets with NAT A and AZ B with NAT B. A single NAT Gateway shared across AZs is a cost optimization but creates additional cross-AZ dependency and potentially cross-AZ data transfer charges.

A public NAT Gateway consumes hourly billed capacity and data-processing charges even when utilization is low. Evaluate NAT usage through CloudWatch metrics and VPC Flow Logs. S3 gateway endpoints typically avoid NAT processing on S3 traffic; interface endpoints incur their own hourly and data-processing charges, so compare the real workload patterns.

For IPv6 designs, consider native IPv6 public addressing, an egress-only IGW for outbound-only connections, or NAT64/DNS64 where IPv6-only clients must reach IPv4 destinations, subject to AWS-supported routing configurations.

07 · Security and governance controls

  • Least privilege: The ALB SG allows TCP/443 from appropriate client ranges; the app SG allows only listener target traffic from the ALB SG.
  • No public application IPs: Disable automatic public IPv4 address assignment on private application subnets and do not attach Elastic IPs to private application instances.
  • Database isolation: Restrict RDS SG to app-to-database port; keep DB route table local-only and turn off public accessibility.
  • Observability: Enable appropriate VPC Flow Logs, CloudWatch NAT metrics, ALB access logs, AWS CloudTrail, and AWS Config controls.
  • Outbound restriction: NAT provides translation, not layer-7 filtering. Apply egress Security Group restrictions, DNS controls, or managed egress filtering/firewalls as needed.

08 · AWS hands-on lab

  1. In an isolated training AWS account, choose a region with two AZs and create VPC 10.0.0.0/16.
  2. Create six /24 subnets using the address plan above. Disable public-IP assignment for private tiers.
  3. Attach an IGW to the VPC. Create a public route table with 0.0.0.0/0 → IGW; associate both public subnets.
  4. Allocate two Elastic IP addresses and create a public NAT Gateway in each public subnet.
  5. Create per-AZ private app route tables with default routes pointing at the local-AZ NAT Gateway; associate each app subnet.
  6. Create a DB route table with only the VPC local route; associate both DB subnets.
  7. Launch a test private EC2 instance with a Systems Manager-compatible access path (appropriate IAM role and SSM endpoints or permitted Internet egress).
  8. Verify outbound HTTPS from the private instance, and confirm there is no unsolicited direct Internet ingress.
  9. Introduce a temporary erroneous NAT route; observe connectivity failure, then correct the route. Inspect NAT CloudWatch metrics and VPC Flow Logs.
  10. Clean up billable NAT Gateways and Elastic IPs after the exercise; delete dependent resources in the correct order.
Cost caution: NAT Gateways and public IPv4 addresses can generate charges while allocated. Complete the cleanup step even if the lab is unfinished.
