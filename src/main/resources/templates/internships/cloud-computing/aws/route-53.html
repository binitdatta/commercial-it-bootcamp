01 · DNS reference architecture

A user first consults a recursive resolver. Route 53 authoritative nameservers return the matching DNS record from a public hosted zone; the client subsequently connects to the chosen application endpoint. Route 53 does not act as a reverse proxy in this workflow. The example uses primary and secondary regional application endpoints and failover routing with health evaluation.

DNS failover depends on resolver caching and record TTL. Health-check behavior and endpoint monitoring must be tested, not assumed to provide instantaneous recovery.

02 · DNS resolution from browser to application

  1. User enters app.example.com in a browser.
  2. Browser/operating system checks local caches, then requests resolution from a recursive DNS resolver.
  3. If not cached, recursive resolution follows the DNS delegation chain (root, TLD, authoritative nameservers).
  4. Route 53 public hosted zone returns the applicable A, AAAA, CNAME, or alias answer.
  5. Client connects directly to the returned service endpoint (e.g., an ALB or CloudFront).

Recursive DNS caches honor effective TTLs, so DNS record changes are not guaranteed to be observed immediately by all clients.

For domains registered elsewhere, configure the registrar or parent zone to delegate authoritative DNS to the Route 53 nameservers for the hosted zone. Domain registration and hosted-zone hosting are separate services and charges.

Alias versus CNAME: Route 53 alias records are an AWS extension supported for selected AWS resources and for other records in the same hosted zone. Alias A/AAAA can work at the zone apex, where CNAME cannot. Alias records pointing to certain AWS resources do not incur Route 53 query charges, subject to AWS pricing specifics.

DNS policy choices control response selection, not guaranteed per-request load balancing. Cached responses, resolver behavior, and EDNS Client Subnet can influence observed distribution.

06 · Health checks and failover

Route 53 supports health checks for supported endpoints and CloudWatch alarms, plus calculated health checks. For alias targets such as an ALB, Evaluate Target Health can use the target resource health instead of an independent Route 53 HTTP health check where supported. Configure your desired behavior explicitly.

  • Define what healthy means (for example a public HTTPS health endpoint).
  • Plan how failover behaves if every record is unhealthy.
  • Understand health-check request origins, access controls, and billing.
  • Choose TTL and validate recovery in a realistic failure simulation.
  • Use infrastructure-as-code and change review for DNS records and failover policies.

07 · DNS security and operations

Use scoped IAM roles for record changes, enable CloudTrail visibility for Route 53 API changes, and restrict hosted-zone mutations. DNSSEC signing is available for supported public hosted zones and requires correct DNSSEC delegation at the parent zone. Query logging options differ for public authoritative zones and Route 53 Resolver query logs.

  • Ensure registry/registrar controls and MFA protect domain ownership.
  • Create alarms around endpoint health and DNS changes.
  • Avoid putting sensitive internal hostnames or metadata in public zones.
  • For hybrid resolution, evaluate Route 53 Resolver inbound/outbound endpoints and rules.
  • Document zone ownership, change approvals, record TTLs, and recovery procedures.

08 · Hands-on AWS lab

  • Use a domain that you control and create a public hosted zone for it.
  • If the domain is registered elsewhere, update delegation to the Route 53 NS values and confirm authoritative answers using dig NS example.com.
  • Create an application DNS alias A record pointing to an existing ALB; add AAAA only if the target and client-facing IPv6 requirements support it.
  • Verify dig app.example.com and compare with the service endpoint behavior.
  • Create a weighted pair of test records with distinct weights; observe approximate response distribution across repeated uncached queries.
  • Set up primary/secondary endpoints and a failover record set with health evaluation; validate conditions needed to trigger failover.
  • Create a private hosted zone for an internal application hostname, associate it with a test VPC, and check resolution inside versus outside.
  • Record security, delegation, cost, and teardown findings; delete test hosted zones and unused health checks to avoid ongoing charges.
