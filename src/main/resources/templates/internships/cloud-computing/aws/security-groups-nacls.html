Security Groups & Network ACLs

01 · End-to-end reference architecture

The reference design uses one VPC (10.0.0.0/16) spanning two Availability Zones. An internet-facing Application Load Balancer (ALB) receives HTTPS, private application instances accept only ALB-originated application traffic, and RDS accepts database connections only from application instances. Each tier has a separate security group; each subnet tier can have an appropriate network ACL.

Key mental model: A packet must satisfy the applicable subnet NACLs and security-group rules, plus routing and any host firewall. An allow decision at one layer does not override a deny or missing allow at another.
Diagram scope: The example focuses on ALB → EC2 → RDS. AWS WAF is an optional web ACL associated with the ALB, not a separate network hop. NAT Gateways are intentionally omitted from the core security path: they do not support attaching Security Groups.

02 · Security Groups: stateful resource-level filtering

Where a security group applies

Security Groups attach to elastic network interfaces (ENIs) or supported resources, including EC2 and ALBs, and are configured for RDS instances. Multiple Security Groups may be associated with a supported network interface; their allow rules are aggregated.

Stateful behavior

If an inbound connection is allowed, its tracked response traffic is allowed regardless of a matching outbound rule. Likewise, responses to allowed outbound connections are automatically permitted. This is connection tracking, not a blanket exemption for unrelated traffic.

Core operating rules

  • Rules are allow-only; there is no explicit deny rule in a Security Group.
  • Every Security Group begins with no inbound allow rules; default outbound rules can permit all outbound traffic until you narrow them.
  • Reference another Security Group as an allowed source or destination when supported; this makes tier access independent of changing EC2 private IPs.
  • Changes to rules take effect without rebooting the instance; existing tracked connections can have nuanced behavior when rules change.
  • Security Groups are associated with resources/ENIs—not with subnets, Internet Gateways, or NAT Gateways.
Recommended model: ALB-SG allows HTTPS from trusted clients; App-SG allows TCP 8080 from ALB-SG; DB-SG allows TCP 3306 from App-SG. Match ports to the application's actual listener and database engine.

03 · Network ACLs: stateless subnet-level filtering

A Network ACL (NACL) is associated with one or more subnets. Each subnet must be associated with exactly one NACL at any given time. All matching ingress and egress traffic crossing a subnet boundary is evaluated against its rules, while traffic between instances within the same subnet is not filtered by that subnet's NACL.

  • Stateless: return packets must independently satisfy the opposite-direction NACL rules.
  • Rule ordering: evaluate by ascending rule number and stop at the first match, regardless of whether it allows or denies.
  • Explicit allow/deny: a matching deny blocks traffic even if the resource Security Group otherwise permits it.
  • Implicit final deny: the final * rule denies traffic that no earlier rule matches.
  • Source/destination: rules use CIDR blocks and ports/protocols rather than referencing Security Group IDs.
Ephemeral ports matter: for TCP response traffic, account for the ephemeral port range used by the participating client/platform. Ranges vary across operating systems and services. Use VPC Flow Logs and connection tests to validate the actual return path.

A custom NACL initially denies traffic until allow rules are supplied. Always distinguish a default VPC's permissive default NACL from a newly created custom NACL.

06 · Follow one HTTPS request through the controls

1Client → public ALB: DNS resolves the public endpoint. The public subnet's inbound NACL must allow TCP 443, and ALB-SG inbound permits the client's source.
2ALB → private application: the ALB opens a connection to the target on TCP 8080. Public-subnet egress and app-subnet ingress NACLs must allow the flow; ALB-SG egress and App-SG ingress must permit it.
3Application → RDS: the app opens TCP 3306. App-SG egress and DB-SG ingress govern resource access; relevant app/DB subnet NACL directions must match.
4Return traffic: the Security Groups' connection tracking allows associated response packets; each crossed subnet NACL still requires appropriate reverse-direction allowances, often to ephemeral ports.
5Log and verify: inspect ALB access logs, VPC Flow Logs and target health. A permitted security rule cannot fix a missing route, an unhealthy target or a process not listening.

07 · Production security design considerations

Availability and isolation

  • Spread ALB and application capacity across at least two AZs.
  • Keep DB instances in private isolated subnets, without direct public internet routing.
  • Use a dedicated Security Group for each tier and restrict DB ingress to the application group.
  • Apply deliberate NACL rules to public, app and DB subnets if requirements justify custom NACLs.

Operations and governance

  • Enable VPC Flow Logs for relevant VPCs/subnets/ENIs and retain logs per policy.
  • Use AWS Config, Security Hub, Firewall Manager or policy-as-code where appropriate.
  • Review unused and overly broad rules periodically.
  • Prefer IAM Session Manager or controlled access methods over open SSH/RDP ingress.

Scope boundaries: Network ACLs and Security Groups are not identity authorization systems and do not inspect application payloads. Use IAM, TLS, AWS WAF, application authorization, host hardening and database authentication as additional controls.

08 · Hands-on AWS Console lab

Prerequisites: a permitted AWS sandbox account, a VPC with public and private subnets, an ALB, an EC2 application target (or equivalent test target), and a database/test endpoint. Create resources in a sandbox and clean them up afterward to avoid charges.

1Inventory: in VPC → Subnets, note subnet CIDRs, AZs and associated route tables and NACLs.
2Create ALB-SG: in EC2 → Security Groups, allow inbound TCP 443 from intended client CIDRs; permit outbound to the application target port.
3Create App-SG: allow inbound TCP 8080 with ALB-SG as source; allow required DB and operational egress.
4Create DB-SG: allow inbound TCP 3306 only from App-SG. Do not allow 0.0.0.0/0 database ingress.
5Associate groups: attach groups to the relevant ALB, application resources and DB instance, and verify target group health.
6Inspect NACLs: identify the existing NACL for each subnet; create a new test NACL if changing rule behavior, and record original associations before modifying.
7Exercise stateless behavior: allow one required connection direction but omit its return-path rule in the test NACL; observe the timeout; then permit the correct response traffic and retest. Keep an alternate management path.
8Observe: enable and query VPC Flow Logs, confirming ACCEPT/REJECT records and correlating five-tuple, interface and time. Flow Logs cannot by themselves identify which specific rule caused a rejection.
9Restore and clean up: re-associate original NACLs, remove temporary resources, and capture the approved SG/NACL tables for documentation.

10 · Knowledge assessment

  2. Can a Security Group contain a deny rule? How does that differ from a NACL?
  3. What happens if NACL rule 100 denies a CIDR and rule 200 allows the same CIDR?
  4. Why must a custom NACL account for ephemeral return ports?
  5. Can you attach a Security Group to a NAT Gateway? Explain the appropriate controls.
  6. How can you permit database access only from the application tier without maintaining an IP allowlist?
  7. If ALB-SG permits TCP 8080 but App-SG denies it by omission, does the connection succeed?
  8. Why might a client still get a 504 even when all Security Groups appear correctly configured?
Expected outcome: You can distinguish stateful and stateless control planes, design tier-specific Security Groups, evaluate numbered NACL rules, and trace both directions of an application connection across public, app and DB subnets.
