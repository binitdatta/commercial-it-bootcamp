01 · End-to-end reference architecture

A reference VPC 10.0.0.0/16 spans two Availability Zones. Each AZ has one public subnet, one private application subnet, and one private database subnet. The Application Load Balancer accepts HTTPS at the public edge and forwards requests to application instances in private subnets.

Architecture interpretation: The ALB uses public subnets but application EC2 instances use private subnets. Database subnets normally have no internet default route. NAT gateways serve private outbound connections; they do not accept unsolicited inbound internet traffic.

02 · Subnet and routing fundamentals

VPC & subnet relationship

A VPC is a regional logical network. Each subnet occupies exactly one Availability Zone. Every subnet's IPv4 CIDR must fit inside the VPC IPv4 address range and must not overlap another subnet's range.

A subnet is public when its associated route table has a default route to an Internet Gateway; public IP addressing and security controls are separately required for internet reachability. A private subnet has no direct IGW default route.

Route table behavior

Each subnet uses exactly one effective route table: an explicit association or the VPC main route table. A route consists of destination CIDR + next-hop target. AWS selects the most-specific matching route; static and propagated-route precedence can also matter.

New VPC route tables include a local route for each VPC CIDR. Route tables govern next hops, not fine-grained authorization; security groups and NACLs implement traffic filtering.

Important: A default route to an Internet Gateway does not automatically make an EC2 instance internet-reachable. It also needs suitable public addressing and security rules. IPv6 uses separate routes and may use an egress-only Internet Gateway for outbound-only connections.

Why separate application route tables? A single route table cannot send the same 0.0.0.0/0 destination to two different NAT gateways based on which subnet initiated the request. AZ-specific route tables preserve AZ-local NAT routing.

Route-selection examples

  • 10.0.3.25 → 10.0.5.20: both addresses fall under the VPC local route; security groups still decide permission.
  • 10.0.3.25 → 8.8.8.8: private App A sends to NAT A, which reaches the IGW through its public subnet.
  • 10.0.5.20 → 8.8.8.8: no matching default route in the isolated DB table, so the packet has no internet path.

05 · End-to-end traffic flow and security

Inbound application request

  1. A client resolves the application's DNS hostname.
  2. HTTPS reaches the internet-facing ALB in public subnets.
  3. ALB security group permits inbound TCP/443.
  4. ALB forwards to application targets over the configured backend port.
  5. The application connects to RDS privately over its database port.

Outbound software update

  1. Application EC2 initiates an HTTPS request to an external endpoint.
  2. Private App A route table matches 0.0.0.0/0.
  3. NAT Gateway A translates outbound source addressing.
  4. Public subnet route points to the IGW.
  5. Response returns through established flow to the private workload.

Security boundaries

Security Groups are stateful resource-level controls. Permit ALB-to-app traffic from the ALB security group, and app-to-DB traffic from the app security group. Network ACLs are stateless subnet boundary controls and require explicit return-traffic considerations. Route tables provide path selection, not identity-based access control.

AWS WAF note: AWS WAF is associated with an Application Load Balancer (or other supported resources), rather than acting as a standalone network hop. The diagram's WAF element denotes logical request filtering.

06 · Hands-on AWS Console build exercise

Guided lab   Build a minimal functional variant of this architecture in a sandbox AWS account. Cost warning: NAT Gateways, ALBs, EC2, and RDS incur charges; delete lab resources after validation.

Step 1 — Create VPC: Open VPC Console → Your VPCs → Create VPC. Select IPv4 CIDR 10.0.0.0/16 and enable DNS support/hostnames as appropriate.
Step 2 — Create six subnets: Allocate the six CIDRs from the address plan; place A subnets in one AZ and B subnets in another.
Step 3 — Add IGW: Create an Internet Gateway, attach it to the VPC, and configure a public route table with 0.0.0.0/0 → igw-....
Step 4 — Add two NAT Gateways: Allocate Elastic IPs and place NAT A/B in their matching public subnets. Wait until both gateways become available.
Step 5 — Create route tables: Create an app route table per AZ; route each default destination to its AZ-local NAT. Associate each route table with the correct subnet.
Step 6 — Isolate DB routes: Create DB route tables with local routing only, and explicitly associate the DB subnets.
Step 7 — Deploy and test: Deploy test instances/application targets into the private app subnets, place an ALB in public subnets, and validate application-to-database connectivity as applicable.
Step 8 — Clean up: Remove ALB, EC2 instances, RDS, NAT Gateways, Elastic IPs, IGW, route-table associations, subnets, and VPC when finished.

09 · Key takeaways

Subnet design determines address allocation and AZ placement. Route-table associations determine paths. Internet Gateways support direct public routing, NAT Gateways provide private outbound IPv4 access, and security groups/NACLs enforce traffic constraints. For a resilient three-tier system, use multiple AZs, distinct subnet tiers, and deliberate route-table associations.
