1. The Git mental model — how source control really works

Git is a distributed version control system (DVCS). Each normal clone contains its own commit history and can create commits offline. A hosted service such as GitHub is a collaboration platform, not Git itself.

Working directory -- git add --> Staging index -- git commit --> Local repository ^ | | | git restore | git push +-------- git switch / restore --+ v Remote repository
ComponentMeaningUseful command
Working treeFiles currently present in your checkout, including unsaved-from-Git changes.git status
Index / staging areaThe proposed snapshot for the next commit; not the same as all changed files.git add / git diff --cached
Local repository.git object database and refs storing history.git log
CommitImmutable snapshot with metadata and one or more parents, identified by a hash.git show
BranchMovable name pointing at a commit; not a separate copy of the entire project.git branch -vv
HEADUsually a symbolic pointer to the currently checked-out branch.git symbolic-ref --short HEAD
Remote-tracking branchLocal record of a branch last observed on a remote, e.g. origin/main.git branch -r

Commits, trees, blobs and tags

Git objects include blobs (file contents), trees (directory snapshots), commits (metadata/parents/root tree) and annotated tag objects. Git's staging index constructs the tree for the next commit. A normal commit typically has one parent; a merge commit commonly has two.

Critical distinction: git add stages; git commit records locally; git push publishes to a remote. These are three different operations.

2. Install Git and configure your identity

Use a supported Git release. On macOS, install with your package manager or Xcode Command Line Tools; on Windows use Git for Windows; on Linux use your distribution's package manager.

# macOS (Homebrew)
brew install git
# Windows (PowerShell, with winget)
winget install --id Git.Git -e
# Ubuntu / Debian
sudo apt update && sudo apt install git
# Fedora
sudo dnf install git

In a new terminal, configure the identity written into future commits. This does not authenticate you to GitHub.

git --version
git config --global user.name "Intern Developer"
git config --global user.email "intern@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf input   # Typical for macOS/Linux; consider platform/team policy
# On Windows teams often choose core.autocrlf true, or enforce line endings via .gitattributes
git config --global --list --show-origin

Prefer repository-owned .gitattributes to enforce consistent line endings across platforms. Credential managers or SSH keys manage authentication; never save passwords or access tokens in tracked files.

3. Create, initialize and clone repositories

git init creates a local repository in an existing folder. git clone creates a new directory from a remote repository, copies its reachable history, and normally configures a remote called origin.

# New local repository
mkdir order-service-lab && cd order-service-lab
git init -b main
printf '# Order Service Lab\n' > README.md
git add README.md
git commit -m "docs: initialize order service lab"

# Existing project from a hosting service (run elsewhere)
git clone https://github.com/ORG/REPOSITORY.git
git -C REPOSITORY remote -v

Local vs remote: a local repository can have commits not yet pushed. A remote may contain commits you have not fetched. A branch named main in your clone and origin/main are different refs.

Lab: Run git rev-parse --show-toplevel and git status --short --branch. Explain why the .git folder must not be copied into another unrelated project's repository.

4. Everyday workflow — status, add, commit, ignore and diff

Use the smallest coherent commits possible. Inspect staged changes before committing; git add . can stage more than intended.

git status                     # Summarize modified / staged / untracked files
git status --short             # Compact M, A, ?? indicators
git diff                       # Unstaged tracked changes
git add src/main/java/Order.java
git diff --cached              # Exactly what will go into next commit
git commit -m "feat: validate order status"
git log -1 --oneline

Selective staging and .gitignore

git add -p                     # Stage selected hunks interactively
git restore --staged file.txt  # Unstage, retaining working-tree edits
git diff --check               # Find whitespace problems

# .gitignore example for a Java app
target/
.idea/
*.iml
.env
*.log

.gitignore affects untracked files, not files already tracked. To stop tracking a sensitive/generated file while keeping the local copy, first ensure its removal from Git history is handled if secrets were exposed, then use git rm --cached and commit.

5. Read commit history and investigate changes

git log --oneline --graph --decorate --all --max-count=25
git show HEAD                 # Last commit patch
git show HEAD:README.md       # File as stored in HEAD
git diff main...feature/order-validation
git blame src/main/java/Order.java
git log --follow -- README.md
git grep -n "TODO" -- src/

git diff A..B compares the two snapshots; git diff A...B compares the merge base of A/B to B. The triple-dot meaning differs between git diff and git log; check the specific command before interpreting results.

Lab: Create three distinct commits, then use git show to identify exactly which commit introduced an intentional change.

6. Branches, switching, tracking and branch hygiene

A---B---C (main) \ D---E (feature/order-validation)
git switch main
git switch -c feature/order-validation
# Edit, stage and commit changes
git branch -vv
git switch main
git branch --merged
git branch -d feature/order-validation  # Deletes safely only if merged

Create a branch per coherent work item. Choose names that communicate intent (e.g. feature/ORD-42-validation, fix/ORD-87-null-status). Switch only when the working tree is compatible with the requested checkout; commit or stash changes first.

Use git push -u origin feature/order-validation to publish a new branch and set its upstream tracking relationship.

7. Merge strategies and conflict resolution

A fast-forward merge moves a branch pointer when no separate commits diverged. A three-way merge combines two branches using their common ancestor and may create a merge commit. --no-ff requests a merge commit even when a fast-forward would be possible.

git switch main
git merge feature/order-validation     # Fast-forward or merge commit
# Or retain explicit PR feature boundary when appropriate:
git merge --no-ff feature/order-validation

When two branches change overlapping lines, Git may leave conflict markers. Resolve based on desired behavior, not simply by choosing “ours” or “theirs.”

git status                           # Lists unmerged paths
# Open conflicted files; remove <<<<<<<, ======= and >>>>>>> markers
# Run tests before completing the merge
git add src/main/java/Order.java
git merge --continue                   # Completes merge after resolving
# Or cancel an in-progress merge:
git merge --abort
Team rule: Never resolve a conflict without verifying the combined behavior and running relevant tests.

8. Rebase — linear history and its consequences

git rebase main takes commits unique to the current branch and replays their changes onto a new base. The replayed commits receive new hashes; rebase rewrites history.

Before: A---B---C (main) After: A---B---C (main) \\ \ D---E (feature) D'---E' (feature)
git fetch origin
git switch feature/order-validation
git rebase origin/main
# Resolve conflicts if prompted:
git add path/to/resolved-file
git rebase --continue
# Or undo an unfinished rebase:
git rebase --abort

Interactive rebase can reorder, squash, reword, or drop local commits:

git rebase -i HEAD~3

Rebase private work before review if your team prefers it. Avoid rebasing a shared branch other developers have based work on unless everyone coordinates. After rebasing a published feature branch, git push --force-with-lease may be required, but it can still disrupt collaborators; never force-push protected or shared branches.

MergeRebase

9. Working with remotes — fetch, pull, push and tracking

Fetch downloads remote objects and updates remote-tracking refs without automatically changing your checked-out files. Pull performs fetch plus integration (merge or rebase, depending on configuration/flags). Push sends objects and proposes remote ref updates.

git remote -v
git remote add origin https://github.com/ORG/order-service.git
git fetch origin
git branch -a
git log HEAD..origin/main --oneline   # Incoming commits relative to current HEAD
git switch main
git pull --ff-only origin main      # Rejects non-fast-forward integration
git push -u origin main             # Requires permission and permitted server rules

For feature branches, fetch first and review incoming changes before integrating. git pull --rebase is one valid team convention, but should not be used blindly on shared work.

Clarify the names: origin is merely a conventional remote alias; upstream is commonly used as the original repository when working from a fork.

10. Forking, cloning, pull requests and code review

A fork is a separate server-side repository under another account or organization. A clone is a local copy. A pull request (or merge request) is a hosting-service review workflow, not a core Git command.

Original project (upstream) --- fork on hosting service (origin) ^ ^ | PR / merge request | push feature branch +------------------- local clone ------+
# Clone your fork (replace YOUR_ACCOUNT and ORG)
git clone https://github.com/YOUR_ACCOUNT/order-service.git
cd order-service
git remote add upstream https://github.com/ORG/order-service.git
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

git switch -c feature/ORD-42-order-validation
# edit, add, test, commit
git push -u origin feature/ORD-42-order-validation
# Open a PR: YOUR_ACCOUNT:feature/... into ORG:main

Reviewers inspect the diff, test results, security implications, migration effects and maintainability. Address review feedback with additional commits or a coordinated squash. Do not merge without required approvals and passing CI checks.

Suggested intern-friendly team flow

git fetch origin
git pull --ff-only origin main
git switch -c feature/ORD-42-validation
# Implement one small improvement; run tests
git add -p
git commit -m "feat(order): validate status transitions"
git push -u origin feature/ORD-42-validation
# Open PR; obtain review; pass CI; merge using team policy
# After merging, synchronize main and delete stale local branch

Configure branch protection, required reviews, required status checks, and restricted force pushes in your repository hosting system. Decide whether PRs are merged with merge commits, squash merges, or rebases based on team policy.

12. Undoing mistakes safely — restore, reset, revert, stash and reflog

SituationRecommended operationSafety notes
Discard unstaged tracked editsgit restore pathDestructive to those local edits.
Unstage a filegit restore --staged pathWorking copy remains.
Undo a published commitgit revert <sha>Creates a new inverse commit; preserves shared history.
Move local branch to an earlier commitgit reset --soft <sha> or --mixedSoft keeps staged changes; mixed unstages them.
Discard committed and uncommitted changesgit reset --hard <sha>Destructive; never run casually.
Temporarily set work asidegit stash push -u -m "WIP"Includes untracked files with -u, not ignored ones.
Recover lost branch tipgit reflogReflog is local and retention-limited; act promptly.
git stash list
git stash show -p stash@{0}
git stash apply stash@{0}  # Keeps stash entry
git stash drop stash@{0}

git revert HEAD            # Safe history-preserving fix to a shared commit
git reflog --date=iso      # Locate prior local HEAD positions
Do not copy dangerous commands blindly: reset --hard, clean -fd, push --force, history filtering, and aggressive garbage collection can irreversibly destroy local work or disrupt teammates. Create a backup branch before recovery experiments.

13. Advanced Git skills — cherry-pick, bisect, tags, worktrees and hooks

Cherry-pick — apply a selected commit elsewhere

git switch release/1.0
git cherry-pick <commit-sha>    # Apply one change onto this branch

Useful for a targeted release hotfix; it creates a new commit identity and can cause conflicts or duplicate logical changes if misused.

Bisect — locate an introduced regression

git bisect start
git bisect bad                 # Current revision fails
git bisect good <known-good-sha>
# Test the checked-out revision, then mark good or bad repeatedly
git bisect reset

Tags and releases

git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
git tag --list

Worktrees and additional skills

git worktree add ../order-hotfix -b fix/urgent main
git worktree list
git worktree remove ../order-hotfix

Learn git submodule only when your project intentionally uses nested repositories, and avoid accidental nested .git directories. Learn Git LFS for genuinely large binary assets. Client-side hooks can help, but required checks belong in CI because local hooks can be bypassed.

14. Enterprise repository security, conventions and auditability

  • Authentication: prefer organization-approved credential managers or SSH keys; enable MFA for hosting accounts.
  • Authorization: enforce least-privilege repository access, branch protection, required reviews and separation of duties.
  • Secrets: never commit passwords, API tokens, private keys, .env or production configuration with credentials; rotate exposed secrets even after removing the file from history.
  • Supply chain: review dependency changes, use CI secret scanning and dependency scanning, pin important automation actions, and verify third-party contributions.
  • History quality: use meaningful commit titles and descriptive PRs linked to ticket identifiers (e.g. Jira issue).
  • Traceability: connect requirement → branch → commit → PR → CI run → release tag → deployed artifact.
# Example conventional commit titles
feat(order): add status validation
fix(api): return 404 for missing order
test(order): add transition cases
docs(readme): document local setup

15. Complete practical labs — simulated Order Management team

Lab A — Solo developer (20 minutes)
  1. Create a repository named order-service-lab.
  2. Add a README and orders.csv with sample order IDs and statuses.
  3. Create three atomic commits: initial README, data file, documentation update.
  4. Use git diff, git log --graph, git show, and git blame.
  5. Deliverable: screenshot or terminal output showing three commits and a clean status.
Lab B — Two developers and a merge conflict (30 minutes)
  1. Developer A creates feature/status-validation and edits a shared status definition.
  2. Developer B creates feature/order-reporting from the same base and changes the same line differently.
  3. Merge one branch into main, then merge the other to produce a conflict.
  4. Resolve with a deliberate combined result; run tests; complete merge.
  5. Deliverable: merge graph, explanation of the conflicting lines, and test evidence.
Lab C — Remote collaboration and code review (45 minutes)
  1. Create a disposable remote repository or fork under your training account.
  2. Clone it, create a feature branch, commit, and push with upstream tracking.
  3. Open a pull request; have another intern review the changes and suggest improvements.
  4. Update the branch, pass automated checks, merge using your team's selected policy.
  5. Fetch and fast-forward your local main; remove the merged feature branch.
  6. Deliverable: PR link, approval, passing checks and synchronized main.
Lab D — Rebase vs merge and safe recovery (35 minutes)
  1. Create two local branches from the same commit; add divergent commits.
  2. Merge in one disposable copy and rebase in another; compare commit hashes and graphs.
  3. Undo a newly created local commit with reset --soft; preserve staged changes.
  4. Use revert to undo a shared logical change in a safe test branch.
  5. Find a previous HEAD position with reflog.
  6. Deliverable: short written explanation of when to choose merge, rebase, reset and revert.
Lab E — Release and regression debugging (30 minutes)
  1. Create an annotated v1.0.0 tag on a known-good commit.
  2. Introduce a deliberate failing behavior in a later commit.
  3. Use git bisect to identify the first bad revision.
  4. Document the root cause and make a fix commit.
  5. Deliverable: offending commit SHA, fix SHA and passing test output.
