1. Keycloak architecture and core terminology

Keycloak is an identity and access management (IAM) server that can act as an OpenID Connect (OIDC) Provider, OAuth 2.0 Authorization Server, and SAML 2.0 Identity Provider. Applications redirect users to Keycloak for authentication rather than collecting credentials themselves.

TermWhat it does
RealmLogical security boundary containing users, clients, roles, identity providers, and policies. The built-in master realm is primarily for administration.
ClientApplication registered with Keycloak; public browser/mobile clients use PKCE, while confidential server applications authenticate with credentials when appropriate.
User & roleUser identity and role-based privileges; realm roles and client roles have different scopes.
Authentication flowDefines how users authenticate, such as username/password, MFA, federation, or social login.
OIDC discoveryPublishes endpoints and signing-key references at /.well-known/openid-configuration.
TokensID token represents an authentication event; access token authorizes API calls; refresh token supports token renewal when issued.
Typical flow: Browser → Spring Boot / SPA → Keycloak login → authorization code → token endpoint → validated identity / access token → protected application or API.

2. Prerequisites and version selection

  • macOS (Apple Silicon or Intel), Windows 10/11, or modern Linux; a terminal and a current browser.
  • For a native ZIP/TAR installation, install a Keycloak-supported JDK and check java -version. Keycloak 26 release requirements evolve; consult the version's official documentation before choosing the Java runtime.
  • For the container route, install Docker Desktop, Docker Engine, or Podman; the container includes its own Java runtime.
  • Reserve localhost:8080 for Keycloak. Your Bootcamp Spring Boot application uses 8081, so they can run simultaneously.
  • Use a recent 26.x or later stable release; match the server download and container tag to the same selected release.

Official resources: Keycloak downloads · Native server quickstart · Supported configurations.

Java 21 is supported by Keycloak 26, but the current native quickstart can recommend a newer JDK. Always check the requirements of the exact Keycloak build you download. This lesson does not assume all future Keycloak versions have identical requirements.

3. Recommended local lab: Docker or Podman

The easiest consistent setup across all three operating systems is an official Keycloak container. Pin a release tag rather than using latest for repeatable labs. The example below uses a representative 26.x tag; update it to the release selected from the official downloads page.

# Run in a terminal with Docker installed.
# Substitute a current supported release tag if needed.
docker run --name bootcamp-keycloak \
  -p 127.0.0.1:8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=ChangeThisLocalLabPassword \
  quay.io/keycloak/keycloak:26.8.0 start-dev

# In a second terminal:
docker ps
docker logs bootcamp-keycloak

# Stop and start the existing container later:
docker stop bootcamp-keycloak
docker start bootcamp-keycloak

Open http://localhost:8080/admin/ and sign in with the bootstrap administrator. Podman uses the same flags with podman in place of docker.

This is development mode only and uses an ephemeral container filesystem unless you attach durable storage. Do not place real passwords in shell history for production, and never expose this development listener to the public internet.

4. Native installation on macOS

  1. Verify the supported JDK is active: java -version. On macOS, /usr/libexec/java_home -V lists detected JVM installations.
  2. Download the Keycloak ZIP distribution from the official downloads site and extract it in ~/Development/Tools/ or another directory you control.
  3. Open Terminal and change into the extracted keycloak-<version> directory.
  4. Run the development server on loopback, then create the initial admin at the welcome page or use the bootstrap variables from the Docker example.
java -version
/usr/libexec/java_home -V
cd ~/Development/Tools/keycloak-<version>
./bin/kc.sh start-dev --http-host=127.0.0.1

# Check in another terminal:
curl -fsS http://localhost:8080/realms/master/.well-known/openid-configuration

On macOS, use zsh or bash; do not execute the Windows .bat launcher. If necessary, grant execute permission with chmod +x bin/kc.sh.

5. Native installation on Windows 10 / 11

  1. Install a supported JDK and confirm java -version in a new PowerShell session.
  2. Download the official Keycloak ZIP and extract it, for example to C:\dev\keycloak-<version>.
  3. Open PowerShell inside the extracted installation directory.
  4. Start Keycloak with kc.bat and visit http://localhost:8080 to create the local administrator.
java -version
cd 'C:\dev\keycloak-<version>'
.\bin\kc.bat start-dev --http-host=127.0.0.1

# In a second PowerShell terminal:
Invoke-RestMethod 'http://localhost:8080/realms/master/.well-known/openid-configuration'

Windows ZIP installation does not require installing Keycloak as a Windows Service. Closing the terminal stops the development server.

6. Native installation on Linux

Use your distribution's package manager to install a supported JDK, then unpack the official Keycloak TAR.GZ or ZIP file. The commands below assume you have extracted a distribution into ~/tools/.

# Ubuntu / Debian: use the appropriate supported JDK package
sudo apt update
sudo apt install openjdk-21-jdk
java -version

# Fedora example:
# sudo dnf install java-21-openjdk-devel

cd ~/tools/keycloak-<version>
./bin/kc.sh start-dev --http-host=127.0.0.1

# Verify discovery document:
curl -fsS http://localhost:8080/realms/master/.well-known/openid-configuration
If the selected Keycloak release requires a newer Java runtime, install that supported JDK instead of relying on the version used in this example.

7. First admin login and create a training realm

  1. Open http://localhost:8080/admin/ and authenticate with the bootstrap admin account or the admin created from localhost.
  2. From the realm selector, choose Create realm; use bootcamp-lab. Leave the built-in master realm for administration.
  3. Under Realm settings, inspect the issuer URLs and login/session configuration.
  4. Go to Users → Add user; create intern1, set a test password under Credentials, and turn off temporary password only for this isolated lab.
  5. Go to Realm roles → Create role and add INTERN; assign it to intern1 through Role mapping.
For a real deployment, enforce strong password policies, MFA where appropriate, least-privilege administrators, and controlled user provisioning. Lab user credentials are not production credentials.

8. OIDC hands-on lab: create a client and validate endpoints

8.1 Register a browser-based public client

  1. In bootcamp-lab, navigate to Clients → Create client and select OpenID Connect.
  2. Set Client ID to bootcamp-spa. Use a public client (Client authentication OFF) with Standard flow enabled.
  3. Under login settings, configure Valid redirect URIs for the exact origin and callback used by your local test application, e.g. http://localhost:4200/*. Set Web origins to the exact origin http://localhost:4200.
  4. Enable or require PKCE S256 for authorization code flow. Do not use Implicit flow or Resource Owner Password Credentials grant for new browser applications.

8.2 Inspect the discovery document

curl -fsS \
  http://localhost:8080/realms/bootcamp-lab/.well-known/openid-configuration

Check issuer, authorization_endpoint, token_endpoint, jwks_uri, and end_session_endpoint. The issuer should be http://localhost:8080/realms/bootcamp-lab for this local lab.

8.3 Understand token verification

OIDC tokens are not accepted because they merely decode into JSON. A Resource Server must validate the signature against the issuer's JWKS, the expected issuer, expiration, and relevant audience / authorization constraints.

TestExpected result
Discovery URLJSON metadata with correct issuer and endpoint URLs
JWKS URL from discoveryPublished signing keys suitable for verification
Browser authorization code + S256Successful login, code redemption and tokens for a correctly registered client
Wrong redirect URIRequest rejected rather than sent to an unregistered callback

9. Spring Boot 4 / Spring Security: Resource Server integration

For a REST API secured by Keycloak, the simplest integration is a Spring Security OAuth2 Resource Server that validates incoming JWTs. The following snippet assumes the appropriate Spring Boot starter dependencies are installed.

# application.yml (resource server example)
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8080/realms/bootcamp-lab
// Example: adapt imports and authorization policies to your project.
@Bean
SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .build();
}

For a server-rendered Spring MVC login, configure a separate OAuth2 Client / OIDC Login registration and an appropriate confidential client in Keycloak. Don't assume the browser public client and the server-side confidential client share the same security properties.

The default JWT resource-server configuration validates token cryptography and issuer, but application-specific role extraction, audience verification, and fine-grained authorization must be configured deliberately. In Keycloak, roles often appear in realm_access.roles or resource_access, not automatically as Spring ROLE_* authorities.

11. Troubleshooting matrix

SymptomChecks
Address already in use: 8080Check existing Keycloak/containers; switch to another mapped host port and update redirect/issuer configuration consistently.
Admin console unavailableRead terminal or container logs; check process and http://localhost:8080; verify loopback port binding.
Invalid redirect URICheck exact scheme, host, port, and callback path in Client → Valid redirect URIs.
Token issuer mismatchCompare iss and configured issuer-uri; don't mix localhost and another DNS/host alias.
401 versus 403401 indicates missing/invalid authentication; 403 generally means authenticated request lacks required authorization.
Java runtime mismatchRun java -version and compare with the exact installed Keycloak release's supported JDK versions.
Docker data disappearsUse a durable data store/volume for anything intended to survive deletion; ephemeral dev databases are not backups.
