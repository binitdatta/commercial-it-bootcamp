How Commercial IT Works

Git, Branching, Pull Requests and Team Development

Learn how professional engineering teams safely evolve one shared codebase through branches, commits, pull requests, automated checks, review, merge controls and traceable history.

Core mental model
Edit locally → stage intentionally → commit coherently → push a branch → review through a pull request → merge only after controls succeed.

Start with the collaboration problem

Twenty developers cannot safely edit “the latest copy” of an application

COMMERCIAL SCENARIO

Three engineers change the order service during the same Sprint

One adds cancellation. One fixes address validation. One changes audit logging. QA needs a reproducible build. Security needs review evidence. Operations needs to know exactly which code was released. Git provides the history and collaboration model that makes this possible.

Parallel workDevelopers need isolation without copying the whole project into disconnected folders.
HistoryThe team needs to know who changed what, when and why.
ReviewImportant changes should be inspectable before entering the shared branch.
RecoveryThe organization needs a known path to compare, revert or restore changes.
Core idea: Git is not merely a backup tool. It is the source-control foundation for collaborative engineering, traceability, automated delivery and controlled change.
Git mental model

A file moves through several states before teammates ever see it

Git becomes much easier once you understand which repository state each command changes. The commands are not magic—they move changes through a controlled sequence.

Stage Git state Typical command What it means
01 Working TreeYour editable files edit files You create, modify or delete files in your local project directory.
02 Staging AreaSelected next commit git add You deliberately choose which changes should be included in the next commit.
03 Local RepositoryRecorded local history git commit Git records the staged snapshot, author identity, timestamp, message and parent history.
04 Remote RepositoryShared collaboration git push Your local commits become available to teammates and CI/CD systems on the shared remote.
Commit A recorded snapshot with identity, timestamp, parent history and message.
Branch A movable name pointing to a line of development.
Remote A shared repository such as GitHub, GitLab or Bitbucket used for collaboration.
Essential command flow

Understand what each command changes

CommandPurposeImportant idea
git cloneCreate a local repository from a remote.You now have local history plus a working tree.
git statusSee modified, staged and untracked files.Use it constantly before committing.
git diffInspect uncommitted differences.Review your own change before asking others.
git addStage selected changes.A commit does not automatically include every changed file.
git commitRecord staged work locally.Prefer coherent, explainable commits.
git pullBring remote work into your local branch.Synchronize intentionally; know whether your team uses merge or rebase.
git pushPublish local commits to the remote.Push is not the same as merging to the protected main branch.
git logInspect commit history.History is an engineering diagnostic tool.
Branching

A branch isolates a change without isolating the engineer

A feature branch gives one piece of work a clear boundary while still preserving a common repository, shared history and a controlled path back into the team's main line of development.

Track Branch Purpose Professional practice
MAIN main Shared, protected integration branch. Represents team-approved history and should accept changes through controlled merge policies.
FEATURE feature/order-cancel Focused line of development for one coherent capability. Developers commit and push changes here, then propose merging them through a pull request.
Rule Recommended practice Why it matters
01Keep branches focusedOne coherent capability or fix is easier to understand, test, review and revert.
02Keep them reasonably short-livedLong divergence increases integration risk and the probability of merge conflicts.
03Name them meaningfullyNames such as feature/order-cancel or bugfix/refund-timeout communicate intent immediately.
04Integrate frequentlyBranches should not become permanent silos; conflicts are easier to resolve while context is fresh.
Pull requests

A pull request is a controlled conversation about a proposed change

Git can merge branches directly. A professional pull request adds explanation, review, automation, approvals, policy and evidence around that merge.

Step PR stage What happens Evidence / outcome
01Push BranchPublish your local commits to the remote repository.Remote branch available to teammates and automation.
02Open Pull RequestExplain what changed, why it changed, implementation approach and risk.Reviewable change proposal.
03CI ChecksBuild, test, scan and validate the proposed branch automatically.Machine-generated quality and security evidence.
04Peer ReviewOther engineers inspect correctness, design, maintainability, tests and failure paths.Human feedback and shared knowledge.
05ApprovalRequired reviewers confirm that merge policy and team expectations are satisfied.Explicit approval record.
06MergeThe approved change becomes part of the protected shared branch.Updated team source of truth.
GOOD PR DESCRIPTION
What

Add customer order cancellation before fulfillment.

Why

Reduce support calls and allow self-service.

How

Add REST endpoint, service policy and tests; no schema change.

Evidence

Automated tests, screenshots/API examples, Jira link and risk notes.

REVIEWER MINDSET
  • Does this implement the intended behavior?
  • Are authorization and validation correct?
  • Are failure paths handled?
  • Is the code understandable and maintainable?
  • Are tests meaningful?
  • Could this break another component?
  • Is operational evidence sufficient?
Protected branches and controls

Commercial teams protect important branches from accidental or unauthorized change

The main branch is usually treated as a governed integration point rather than a personal workspace.

Control Branch protection practice Why teams use it
01Pull Request RequiredPrevents routine direct pushes to the protected main branch.
02Approvals RequiredCreates independent review and visible accountability where appropriate.
03CI Must PassMakes builds, tests and scanning enforceable merge gates.
04Code OwnersSensitive code areas can require review from designated experts.
05Authenticated / Auditable IdentityPreserves who created and approved the change.
06History PolicyMerge, squash or rebase conventions keep repository history understandable and usable.
Merge conflicts

Git can combine independent changes — but it cannot decide business intent

<<<<<<< HEAD
if (order.canCancel()) {
    order.cancel();
}
=======
if (policyService.isCancellationAllowed(order)) {
    auditService.recordCancellation(order);
    order.cancel();
}
>>>>>>> feature/audit-cancellation

A conflict means Git cannot safely choose between overlapping edits. The engineer must understand both changes, resolve the intended final code, run tests, and then complete the merge/rebase. Never “pick ours” or “pick theirs” blindly in business-critical code.

Source-control security

A repository is part of your security boundary

Source control contains executable code, pipeline definitions, configuration and long-lived history. Treat repository governance as part of application security.

Area Security practice Why it matters
01Never Commit SecretsPasswords, API keys, tokens, private keys and cloud credentials can persist indefinitely in repository history.
02Use Least PrivilegeRepository, branch and administrative permissions should match actual job responsibilities.
03Protect Dependencies & PipelinesBuild definitions and dependency changes can alter what code is executed or deployed.
04Audit Important ChangesHistory, approvals and branch controls provide evidence for sensitive systems and investigations.
Important: Deleting a secret from the latest version of a file does not necessarily remove it from Git history. Treat an exposed secret as compromised and rotate it.

Day in the life

Git is woven into normal engineering work

Source control is not a separate administrative step at the end of coding. It is part of the engineer's normal working rhythm throughout the day.

Time Activity What the engineer is doing
9:10 AMSynchronizePull current team changes and inspect branch state before beginning work.
10:00 AMCreate Focused BranchBranch from the agreed base for the Jira story or defect.
11:30 AMCommit Coherent ProgressReview the diff, stage intentionally and write a useful commit message.
2:00 PMOpen Pull RequestDescribe intent, risk, tests and relevant work-item references.
3:00 PMRespond to ReviewDiscuss design, update code, rerun checks and resolve reviewer feedback.
4:15 PMMerge & Observe PipelineConfirm the protected shared branch and CI/CD pipeline remain healthy.
Anti-patterns

Habits that create team pain

Most source-control problems are not caused by Git itself. They come from poor change boundaries, weak review habits, bypassed controls or history that becomes difficult to understand.

Risk Anti-pattern Why it hurts the team
!Huge “Everything” CommitUnrelated changes become difficult to understand, review, diagnose or revert cleanly.
!Meaningless Commit MessagesMessages such as fix, stuff and changes destroy the diagnostic value of history.
!Direct Push to MainBypasses review and automated control points around the shared codebase.
!Long-Lived BranchWeeks of divergence create hidden assumptions, painful merges and integration risk.
!Comment Wars in Pull RequestsReview should improve the product and share knowledge, not become a contest for status.
!Secrets in the RepositoryCredentials may remain recoverable from repository history long after they disappear from the latest file.

Knowledge check

Can you reason about team source control?

1. What is the difference between git commit and git push?

Commit records staged work in your local repository. Push sends local commits to a remote repository.

2. Why does a pull request exist if Git can merge branches without one?

The PR adds collaboration and governance around the Git operation: explanation, review, automated checks, approvals, policy and auditability.

3. What does a merge conflict mean?

Git cannot automatically reconcile overlapping changes. A human must understand intent and create the correct final version.

4. Why should secrets never be committed even to a private repository?

Repositories are replicated, backed up, cloned and retained in history. Access can expand over time. Secret-management systems are designed for credentials; source control is not.
