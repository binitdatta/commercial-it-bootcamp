How Commercial IT Works

Jira and Confluence in Daily Work

Learn how commercial teams make work visible in Jira, preserve durable knowledge in Confluence, connect requirements to implementation, and maintain traceability long after a release.

Core mental model
Jira answers “What work are we doing and where is it?” Confluence answers “What do we know, why did we decide it, and how should others understand it?”
Learning objectives

By the end of this lesson, you should be able to

1
Explain the different jobs Jira and Confluence performJira manages visible work and workflow; Confluence preserves shared context, decisions and knowledge.
2
Read and write useful work itemsUnderstand epics, stories, tasks, bugs, subtasks, acceptance criteria, priorities, ownership and dependencies.
3

4
Create durable project knowledgeKnow what belongs in Confluence: requirements, architecture, ADRs, runbooks, meeting outcomes and operational knowledge.
Start with the coordination problem

A software team cannot run on memory, chat messages and hallway conversations

COMMERCIAL SCENARIO

The business asks: “Allow a customer to cancel an eligible order before shipment.”

Product discusses the rule with Operations. An architect identifies an integration dependency. A developer implements the API. Security asks about authorization. QA finds an edge case. Two months later Support asks why cancellation is blocked after fulfillment begins.

Who owns the work?Without a system of record, assignments and accountability become ambiguous.
What exactly was agreed?Chat and meetings disappear into history unless decisions are recorded.
Where is the work now?Stakeholders need visibility without interrupting engineers for status.
Why was this designed this way?Future engineers need the reasoning, not only the final code.
Core idea: Jira makes work observable. Confluence makes knowledge durable. Used together, they create traceability from business intent to implementation and operational support.
Mental model

Jira answers “What are we doing?”; Confluence answers “What do we know?”

The tools complement each other. Jira is strongest when representing work and workflow; Confluence is strongest when preserving reusable context, reasoning and team knowledge.

BAD PRACTICE Copy the entire design document into a Jira ticket.

Keep the actionable delivery item concise and link to durable design context when substantial explanation is required.

BAD PRACTICE Put every decision only in a meeting or chat thread.

Important decisions need a discoverable home that survives team turnover and time.

Jira fundamentals

Work items form a hierarchy of intent and execution

Organizations configure Jira differently, but the underlying model is consistent: large outcomes are decomposed into smaller deliverable units with enough context to understand, estimate, implement and verify.

Level Work item Example Purpose
01 Epic / Initiative-sized Outcome Self-service Order Management Represents a larger business or product outcome that will be delivered through multiple smaller items.
02 User Story / Feature Slice Customer can cancel an eligible order before shipment Expresses a focused piece of customer or business value that can be discussed, delivered and verified.
03A Task Add cancel endpoint Represents implementation work required to support the feature.
03B Task Add UI action Captures a separate implementation responsibility or work package.
03C Task Add automated tests Makes required quality work visible instead of assuming it will happen implicitly.
03D Bug Fix refund edge case Tracks incorrect behavior that must be investigated and corrected.

What makes a Jira item useful?

Field / concept What it should tell the team Weak example Better example
SummaryWhat change or problem is this?“Cancellation work”“Allow customer to cancel eligible order before shipment”
DescriptionWhy does it matter and what context is required?“Please implement.”Business rule, scope, assumptions and relevant links.
Acceptance CriteriaHow will we know behavior is correct?“Works properly.”Given/when/then or other explicit, testable conditions.
PriorityRelative business urgency or sequencing.Everything = HighestPriority reflects actual trade-offs.
AssigneeWho currently owns progressing the item?Random team memberCurrent responsible owner.
DependenciesWhat other work, system or decision can block progress?Hidden in commentsExplicit relationship and blocker visibility.
Writing useful stories

A Jira story is a conversation anchor, not a substitute for thinking

The common “As a / I want / So that” format helps teams express actor, behavior and value, but the real goal is shared understanding—not filling out a template mechanically.

AS Acustomer
I WANTto cancel an order that has not entered shipment
SO THATI can correct a purchase without contacting customer support

Acceptance criteria make intent testable

Case Scenario Observable expectation
01Allowed StateGiven the authenticated customer owns an order in CREATED or PAID state, when cancellation is requested, then the order is cancelled.
02Forbidden StateGiven an order has already shipped, when cancellation is requested, then the request is rejected with an understandable message.
03Wrong CustomerGiven Customer A attempts to cancel Customer B's order, authorization prevents the operation.
04Quality EvidenceCancellation behavior is covered by automated tests and produces appropriate operational logging.
Important: Acceptance criteria describe observable behavior. They should not unnecessarily dictate implementation details unless those details are part of an architectural or compliance constraint.
Workflow

A ticket should show the current state of the work—not become a status graveyard

A good workflow models meaningful delivery states. It gives stakeholders visibility while helping the team identify blockers, current ownership and what must happen next.

Step Status What this state should mean
01BacklogKnown work that has not yet been committed into active delivery.
02ReadyClear enough to begin, with necessary context and major blockers addressed.
03In ProgressSomeone is actively progressing the work.
04ReviewImplementation or design is being independently reviewed.
05TestBehavior is being validated against expected outcomes and quality requirements.
06DoneThe item satisfies the team's agreed completion criteria and required evidence exists.

Real organizations may use different status names and additional gates. The principle is to model meaningful state transitions, not to create dozens of administrative statuses.

Visible blockers If an API contract, environment or business decision blocks work, make the dependency explicit.
Meaningful ownership The assignee/status should reflect who can move the work forward now.
Evidence at completion Link code, tests, design, release notes or validation evidence where useful.
Confluence fundamentals

Documentation should preserve context that the code cannot explain by itself

Good documentation helps future engineers, operators, product teams and auditors understand the business context, architecture, decisions, operating model and ownership behind a system.

Area Knowledge domain Typical Confluence content
01Business & ProductProblem statements, process maps, requirements, definitions and stakeholder decisions.
02ArchitectureContext diagrams, component design, integrations, NFRs, data flows and threat considerations.
03EngineeringDevelopment conventions, API guidance, setup instructions and dependency notes.
04DeliveryRelease notes, readiness checklists, implementation plans and decision history.
05OperationsRunbooks, dashboards, alerts, troubleshooting, escalation and recovery procedures.
06Team KnowledgeOnboarding, ways of working, recurring processes, useful links and ownership.

A good page answers five questions

Question Focus What readers should learn
01Why?What problem or decision caused this document to exist?
02What?What system, process, capability or rule is being described?
03Who?Who owns it, decides, operates it or should be consulted?
04How?How does it work, integrate, fail and recover?
05When?When was the information valid, reviewed or superseded?
Architecture Decision Records

Record important decisions while the reasoning is still fresh

A lightweight Architecture Decision Record (ADR) prevents future teams from repeatedly asking, “Why did they build it this way?”

ADR field Example
StatusAccepted
DecisionUse Keycloak/OIDC for interactive authentication instead of local application passwords.
ContextThe application needs centralized authentication, role claims and an enterprise-style identity provider.
AlternativesLocal database authentication; custom token service.
ConsequencesThe application depends on IdP availability and OIDC configuration, but gains centralized identity, standard protocols and cleaner security boundaries.
Rule of thumb: document decisions that are expensive to reverse, affect multiple teams, introduce important constraints, or will be questioned later.
Traceability

Connect business intent, knowledge, code and release evidence

Traceability lets teams move from a production symptom back to the business rule, design decision, implementation change and release that produced the behavior.

Step System / source Artifact What it preserves
01BusinessNeed / outcomeWhy the capability exists and what business result is expected.
02ConfluenceRequirement & designDurable context, process, architecture and decision reasoning.
03JiraEpic / story / tasksVisible delivery work, ownership, workflow and dependencies.
04GitBranch / commit / PRExact source changes, review history and implementation evidence.
05CI/CDBuild / test / deployAutomated quality checks and which artifact reached which environment.
06OperationsMonitor / supportProduction behavior, incidents, operational ownership and feedback.
TRACEABILITY QUESTION

Six months after release, a production incident occurs. Can the team quickly answer:

Which business rule drove this behavior? Which design decision was made? Which ticket implemented it? Which code changed? Which release deployed it? Who operates the affected service?

Common failure modes

Tools do not create discipline automatically

Jira and Confluence can improve transparency and knowledge—or become bureaucracy. The difference is whether teams use them to support real decisions and delivery.

Risk Failure mode Why it damages delivery
01Ticket = Vague SentenceEngineers cannot reliably infer business intent, scope and acceptance criteria.
02Status Is FictionThe board says “In Progress” for weeks although nobody is actively progressing the item.
03Everything Is UrgentWhen every item has the highest priority, prioritization communicates nothing.
04Documentation GraveyardPages are created but never owned, reviewed, linked, maintained or retired.
05Decision by ChatA critical architectural choice disappears into a private or transient message thread.
06Tool BureaucracyThe process collects fields nobody uses instead of improving delivery, decisions or traceability.
Hands-on lab

Model a real feature before writing code

LABCreate the delivery package for “Update Shipping Address”

The customer may update the shipping address only while the order is in an allowed pre-shipment state.

1
Write the Jira story

Include user value, business context and a concise summary.

2
Write 4–6 acceptance criteria

Cover allowed state, forbidden state, wrong customer, invalid address and successful persistence.

3
Decompose the work

Create likely engineering tasks: UI, API, service policy, persistence and tests.

4
Design the Confluence page

Include business rule, sequence/workflow, API contract, security assumptions and failure behavior.

5
Create traceability

State which Jira item links to which design page and which code areas would implement it.

Deliverable: one story, acceptance criteria, task breakdown and a one-page design outline. The goal is not tool clicking; the goal is learning how commercial teams make work and knowledge explicit.

Career perspective

The difference between “ticket taker” and commercial engineer is context

A strong engineer does not blindly implement the sentence in a ticket. They understand the outcome, find missing information, surface dependencies, preserve important decisions and keep delivery evidence understandable to the rest of the organization.

Stage Typical mindset What is developing
01“Assign me a ticket.”Learning how to execute clearly defined work in the team's process.
02“I understand the acceptance criteria.”Connecting implementation to expected business behavior.
03“I can identify missing decisions and dependencies.”Thinking beyond the ticket to risk, ownership, architecture and coordination.
04“I help create organizational knowledge and traceability.”Helping the wider organization preserve context, decisions and evidence for future teams.
