How Commercial IT Works

Software Development Life Cycle

Follow one commercial software change from business intent through analysis, architecture, implementation, verification, release, production operations and continuous improvement.

Core mental model
Discover → Analyze → Design → Build → Verify → Release → Operate → Improve. The SDLC is a risk-reduction and evidence system, not just a list of phases.
Learning objectives

By the end of this lesson, you should be able to

1

2

Start with the delivery problem

A business request is not production software

COMMERCIAL SCENARIO

“Allow customers to cancel an order before fulfillment begins.”

The sentence sounds simple. But the production capability may affect customer identity, order state, inventory, refunds, audit logs, APIs, UI behavior, database transactions, security policy, testing, deployment, monitoring and support.

Wrong problemEngineering can perfectly implement the wrong business rule.
Wrong designA local code change can break integrations, security boundaries or data consistency.
Wrong releaseCorrect code can still fail because configuration, infrastructure or dependencies are wrong.
Wrong operationsA feature is incomplete if nobody can detect, diagnose or support its failure.
Core idea: The SDLC is the managed path from business intent to reliable operational capability. It exists to make assumptions, risks, decisions, quality and ownership visible.
End-to-end mental model

The SDLC is a feedback loop, not a one-way assembly line

Every stage reduces a different kind of uncertainty. Agile teams may execute these activities continuously and in small increments, while regulated or high-risk environments may require stronger gates and evidence.

Stage Lifecycle activity Primary focus What the team is trying to prove
01DiscoverBusiness needThere is a real problem or opportunity worth solving.
02AnalyzeRules & scopeThe expected behavior, boundaries, dependencies and constraints are understood.
03DesignArchitectureThe solution can fit safely into the wider application, data, security and operational landscape.
04BuildCode & configurationThe intended behavior has been implemented in a maintainable form.
05VerifyQuality & securityThe system behaves correctly, safely and predictably under expected and failure conditions.
06ReleaseControlled deploymentThe approved change can move into production repeatably and with rollback options.
07OperateObserve & supportThe capability remains healthy for real users and business processes.
08ImproveLearn & iterateProduction evidence and business feedback inform the next change.
Stage-by-stage

What actually happens at each stage

Each SDLC stage has a different purpose, different participants and different evidence. The exact names vary by organization, but the responsibilities are widely recognizable.

Stage Activity What happens Participants & evidence
01Discovery & Business RequirementClarify business outcome, affected users, value, constraints, policy and measurable success.Participants: Business, Product, SMEs, Architect.
Evidence: problem statement, epic, business rules, success criteria.
02Analysis & RefinementBreak the need into bounded behavior. Identify edge cases, dependencies, data, integrations, NFRs and acceptance criteria.Participants: Product, Architect, Engineering, QA, Security.
Evidence: refined stories, acceptance criteria, dependency map.
03Architecture & DesignDecide component boundaries, API contracts, data changes, transactions, security controls, failure handling and operational expectations.Participants: Architects, Tech Leads, Engineers, Security, Data/Platform.
Evidence: diagrams, ADRs, API design, schema changes.
04ImplementationWrite code, tests, configuration and infrastructure changes while following engineering and source-control practices.Participants: Engineers.
Evidence: commits, pull requests, automated tests, build output.
05Verification & ValidationProve the capability behaves correctly across functional, integration, security, regression and non-functional scenarios.Participants: QA, Engineers, Security, Product/UAT users.
Evidence: test results, defect closure, acceptance/UAT.
06Release & DeploymentPackage an immutable artifact, apply configuration/database changes and deploy through controlled automation.Participants: DevOps/Platform, Engineering, Release Management.
Evidence: artifact version, pipeline record, release notes, approvals.
07Production OperationsObserve health, logs, metrics and traces; respond to incidents and support real users.Participants: SRE/Operations, Support, Engineering, Product.
Evidence: dashboards, alerts, incidents, support tickets, business metrics.
08Feedback, Maintenance & RetirementCorrect defects, improve performance, address vulnerabilities, reduce technical debt and retire obsolete capabilities safely.Participants: Cross-functional team.
Evidence: backlog items, RCA actions, deprecation plan, archival/retention decisions.
Requirements and acceptance

Good delivery starts with testable behavior

Requirements should make business intent understandable and acceptance observable before implementation begins.

AS Acustomer
I WANTto cancel an eligible order
SO THATI do not receive goods I no longer need
Case Acceptance condition Expected behavior
01OwnershipCustomer may cancel only an order they own.
02Allowed StateCancellation is permitted only before the configured fulfillment boundary.
03PersistenceA successful cancellation persists the new order status and returns a clear response.
04Failure IntegrityAn invalid cancellation fails predictably without corrupting order state.
Quality is built in

Testing is not a single stage performed by QA at the end

Different test layers answer different questions and provide different kinds of confidence.

Layer Verification type What it proves
01Unit / ComponentFast developer feedback around isolated business behavior and code-level rules.
02Integration / APIDatabase, messaging, service-to-service and contract interactions behave correctly together.
03End-to-End / UATCritical user workflows and business outcomes behave as expected across the integrated system.
04Production VerificationHealth checks, synthetic checks, monitoring and business KPIs confirm the capability remains healthy after release.
Shift-left does not mean “do everything early.” It means surface risks as early as practical: testability during design, security during architecture, automated checks during development and operational readiness before release.
Promotion through environments

The same change gains confidence as it moves toward production

Environment names differ by organization. The important principle is controlled, repeatable promotion with environment-specific configuration and increasing confidence.

Step Environment Primary purpose Typical evidence / concern
01LOCALDeveloper feedbackFast iteration, unit tests and local behavior.
02DEVIntegrated developmentMultiple components work together in a shared environment.
03TEST / QAVerification & regressionFunctional, integration and regression testing against controlled builds.
04UAT / STAGEProduction-like validationBusiness acceptance, release readiness and near-production configuration validation.
05PRODReal users & businessMonitoring, supportability, auditability, business outcomes and rollback readiness.

Controlled promotion, repeatability, segregation of duties where required, and evidence that the same intended change is being promoted matter more than the exact environment names.

Common failure modes

What weak SDLC practice looks like

Weak lifecycle discipline usually appears as missing decisions, late risk discovery, uncontrolled deployment or lack of production ownership.

Risk Weak practice Why it is dangerous
!“Just Start Coding”Implementation begins before the team agrees on behavior, scope and acceptance.
!QA Is the Quality DepartmentDevelopers treat correctness as somebody else's responsibility.
!Security Review at the EndLate discovery of identity, authorization or data-protection problems causes expensive redesign.
!Manual Production ChangesUnrepeatable deployments create drift, hidden state and difficult rollback.
!“Works on My Machine”Local success is mistaken for integrated, environment-independent readiness.
!Release Equals CompletionNo one checks production health, adoption or whether the business outcome was achieved.
Hands-on lab

Create an SDLC evidence map for one application change

LABFeature: customer changes a shipping address before fulfillment

Do not code first. Walk the change through the lifecycle as a commercial team would.

1
Write the business rule

Who may change the address, until what order state, and what must happen if the change is rejected?

2
Identify impacted layers

UI, controller/API, service, persistence, security, validation, integrations and logs.

3
Write acceptance criteria

Include success, unauthorized access, invalid order state, invalid address and concurrency/error behavior.

4
Define verification

List unit, integration/API, security and UAT tests.

5
Define release evidence

Artifact version, migration/configuration needs, rollback approach, logs/metrics and production verification.

Knowledge check

Can you reason about delivery, not just development?

1. Does Agile eliminate the SDLC?

No. Agile changes how work is organized and delivered. Requirements, design, implementation, verification, release and operations still exist, often in smaller iterative slices.

2. When should security become involved?

As early as the risk requires. Identity, authorization, data sensitivity and trust-boundary decisions often need attention during refinement and design, not after coding.

3. Is production deployment the final SDLC activity?

No. Production operation, monitoring, incident response, maintenance, feedback and eventual retirement are lifecycle activities too.

4. Who owns software quality?

The delivery team collectively. QA provides specialized expertise, but Product, architecture, developers, security, platform and operations all contribute to quality.

Career perspective

Senior engineers think across the lifecycle

A junior engineer often asks, “What code should I write?” A strong commercial engineer also asks, “What problem are we solving, how will we prove it works, how will we release it safely, and how will we know when it fails?”

Stage Engineering mindset What is developing
01Implement Assigned ChangeLearn how to deliver code within established requirements and team practices.
02Understand Acceptance & DependenciesConnect implementation work to business behavior, data, integration and test expectations.
03Anticipate Lifecycle RisksReason about architecture, security, deployment, operational readiness and failure modes.
04Shape Reliable Delivery SystemsImprove how the organization designs, verifies, releases and operates software at scale.
