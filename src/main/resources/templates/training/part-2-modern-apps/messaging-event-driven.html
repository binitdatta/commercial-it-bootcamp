Messaging and Event-Driven Architecture

Understand how producers, brokers and consumers decouple systems—and why delivery guarantees, retries and idempotency become first-class design concerns.

The coupling problem

A producer should not always wait for every downstream system

SYNCHRONOUSOrder API → Payment → Inventory → EmailEach dependency extends latency and availability coupling.
ASYNCHRONOUSOrder API → Broker → ConsumersProducer can publish work/events and consumers process independently.
Mental model

Messages move through a brokered boundary

1ProducerCreates message/event
→
2BrokerRoutes, stores, delivers
→
3ConsumerProcesses independently
→
4Ack / retryCommunicate processing outcome
Queue vs pub/sub

Ask whether one worker or many subscribers need the message

Queue / competing consumers

  • Each message is normally handled by one consumer instance
  • Scale workers horizontally
  • Good for commands/work distribution

Topic / publish-subscribe

  • Multiple independent subscribers can receive an event
  • Good for broadcasting facts
  • Each subscriber owns its processing/retry semantics
Events vs commands

Name messages according to what they mean

EVENTOrderShippedA fact that already happened. Multiple consumers may react.
COMMANDSendShipmentEmailAn instruction asking a specific capability to perform work.
Good event: describes a business fact in past tense and carries enough identity/context for consumers to act without guessing.
Delivery semantics

Distributed delivery is about trade-offs, not magic guarantees

At-most-onceMay lose, avoids redelivery.
At-least-onceRetries reduce loss but duplicates are possible.
Effectively-once outcomeOften achieved through idempotent processing/deduplication, not by assuming transport perfection.
Acknowledgment

Acknowledge only after the business effect is safe

1ReceiveBroker delivers message
→
2ProcessValidate + apply business logic
→
3Persist effectCommit durable state
→
4AcknowledgeTell broker processing succeeded
Retries and dead letters

Not every failure should retry forever

Transient failureDependency timeout
→
Backoff + retryBound attempts
→
Still failingStop hot loop
→
DLQ / parking lotPreserve for investigation
Poison message: a permanently bad payload can consume unlimited capacity if retried without a limit.
Idempotent consumers

Assume a message can arrive more than once

DEDUPLICATION IDEA
messageId = "evt-7f1d..."

if processed_message.contains(messageId):
    acknowledge()
    return

apply_business_change()
record_processed(messageId)
commit()
acknowledge()

The exact pattern varies, but duplicate delivery must not double-charge, double-ship or create duplicate records.

Ordering

Global ordering is expensive; define the ordering you actually need

Per orderEvents for the same order may need sequence preservation.
Across all ordersUsually unnecessary and limits parallelism.
Partitioning keyRoute related messages consistently when the broker supports it.
Message contracts

Events are APIs that travel through a broker

EVENT EXAMPLE
{
  "eventId": "2f80...",
  "eventType": "OrderShipped",
  "occurredAt": "2026-09-06T16:42:11Z",
  "orderId": 98765,
  "customerId": 42,
  "shipmentId": "SHP-6001",
  "schemaVersion": 1
}

Treat event schema evolution seriously. Producers and consumers may be deployed independently and may not upgrade at the same time.

Dual-write problem

Database commit + message publish can fail between systems

Business transactionUpdate order + insert outbox row in one DB commit
→
Outbox publisherReads unpublished rows
→
BrokerPublishes event reliably
→
Mark publishedTrack delivery attempt/outcome

The transactional outbox is one common pattern for avoiding an inconsistent state where the database changes but the event is never published.

Anti-patterns

Do not use messaging merely because it sounds modern

Async everythingSimple request/response becomes harder to reason about.
No idempotencyRetries create duplicate business effects.
Infinite retriesPoison messages consume capacity.
No ownershipDLQ fills while nobody is accountable.
Huge event payloadsConsumers become coupled to oversized contracts.
Hidden temporal couplingConsumers incorrectly assume another consumer already ran.
Hands-on lab

Design the OrderShipped event flow

  1. Define the event name and minimum payload.
  2. Identify three independent consumers.
  3. Choose a partition/routing key if ordering by order is required.
  4. Define retry policy for a transient email-provider outage.
  5. Define idempotency for the loyalty-points consumer.
  6. Explain what operations should do with messages moved to a dead-letter queue.
Knowledge check

Can you reason about asynchronous failure?

Queue vs topic?

Queue distributes work among consumers; pub/sub allows independent subscribers to receive an event.

Why idempotency?

At-least-once delivery can redeliver messages.

Why DLQ?

Stop infinite retry and preserve failed messages for controlled investigation/reprocessing.

Why outbox?

Reduce inconsistency between committing database state and publishing the corresponding event.

Career perspective

The difference between a demo and a production event-driven system is usually found in duplicates, retries, ordering, schema evolution, observability and recovery.
