REST APIs, HTTP Methods, Status Codes and JSON

Learn to read, design and troubleshoot the HTTP contracts that connect web clients, mobile apps, microservices, partners and enterprise integrations.

Learning objectives

By the end of this lesson, you should be able to

1
Read an API contractURL, method, headers, request body, response body and status.
2
Choose appropriate HTTP methodsGET, POST, PUT, PATCH and DELETE according to operation semantics.
3
Interpret status codesDistinguish success, client problems, authorization failures, conflicts and server failures.
4
Work with JSON safelyUnderstand types, nested objects, arrays, validation and backward compatibility.
The API contract

An API is an agreement between systems

CLIENTRequestMethod + URL + headers + optional body
→
SERVERResource / operationValidate → authorize → execute
→
CLIENTResponseStatus + headers + optional body
Core idea: Good API design makes outcomes predictable for callers. A technically valid JSON response is not enough if clients cannot tell what happened or what to do next.
Resources and URLs

REST-style APIs commonly model nouns as resources

GET /api/ordersCollectionList orders
GET /api/orders/123Individual resourceRead order 123
POST /api/ordersCollection commandCreate an order
PATCH /api/orders/123Partial updateModify selected fields
DELETE /api/orders/123Resource commandDelete/cancel depending on domain semantics

Real enterprise APIs often include action-oriented endpoints when domain operations do not map cleanly to CRUD. REST is a design style, not a rule that every business operation must pretend to be a simple database row edit.

HTTP methods

The method communicates intent

MethodTypical meaningSafe?Idempotent?
GETRetrieve representationYesYes
POSTCreate or invoke non-idempotent processingNoNot inherently
PUTReplace/update a resource representation at known URINoYes by semantics
PATCHPartially modify a resourceNoDepends on patch semantics
DELETERemove a resourceNoYes by semantics
Do not use GET for state-changing operations. Browsers, crawlers, caches and proxies assume GET is safe to repeat.
Request anatomy

A request has more than a JSON body

CREATE ORDER REQUEST
POST /api/orders HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json
X-Correlation-Id: 4d9f...

{
  "customerId": 42,
  "items": [
    {"productId": 1001, "quantity": 2}
  ]
}
Method + pathTarget operation
AuthorizationCaller security context
Content-TypeFormat of request body
AcceptDesired response format
Correlation IDTrace request across systems
Response anatomy

The status code and body should tell the same story

CREATE ORDER RESPONSE
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/98765

{
  "id": 98765,
  "status": "CREATED",
  "customerId": 42,
  "total": 49.98
}

A strong contract lets a caller determine success from the status code, locate the new resource where appropriate, and parse a stable response representation.

HTTP status codes

Use the status family first, then the specific code

2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection / caching301, 302, 304
4xxClient-side/request problem400, 401, 403, 404, 409, 422, 429
5xxServer-side failure500, 502, 503, 504
CodeUseExample
400 Bad RequestMalformed/invalid request structureRequired JSON field missing or invalid format
401 UnauthorizedAuthentication is missing/invalidExpired or absent bearer token
403 ForbiddenAuthenticated but not allowedUser lacks required role/permission
404 Not FoundTarget resource does not exist / is not exposedUnknown order ID
409 ConflictRequest conflicts with current resource stateAttempt to cancel an already shipped order
429 Too Many RequestsRate limit exceededCaller is throttled
500 Internal Server ErrorUnexpected server failureUnhandled application error
503 Service UnavailableTemporarily unable to serveOverload/maintenance/dependency protection
JSON data model

JSON is simple enough to read, strict enough to break integrations

JSON TYPES
{
  "orderId": 98765,        // number
  "customer": "Alice",    // string
  "paid": true,            // boolean
  "notes": null,           // null
  "items": [ ... ],        // array
  "shipping": { ... }      // object
}
Names mattercustomerId changing to customer_id can break callers.
Types matter42 and "42" are not the same JSON type.
Null vs. absent mattersClients may interpret them differently.
Additive change is saferAdding optional fields is generally easier to evolve than removing/renaming required fields.
Error contracts

Do not make clients scrape human prose to understand failures

STRUCTURED ERROR
HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "code": "policy_denied",
  "message": "Order cannot be cancelled after shipment",
  "orderId": 12345,
  "correlationId": "4d9f..."
}
Machine-readable codeStable value clients can branch on.
Human-readable messageUseful context without leaking secrets.
Correlation identifierConnects the client-visible failure with logs/traces.
Retries and idempotency

Distributed systems retry. Your API must define what a repeated request means.

1. Client sends payment requestServer processes it.
→
2. Response is lostClient sees timeout.
→
3. Client retriesWill the customer be charged twice?

For operations that must tolerate retries, APIs often use idempotent method semantics, unique business keys or idempotency keys so a repeated delivery does not repeat the side effect.

API security

Authentication answers who; authorization answers whether

TLSProtect API traffic in transit.
AuthenticationValidate caller identity/token.
AuthorizationEnforce role/scope/resource ownership.
Input validationReject invalid/untrusted data.
Rate limitingControl abuse and overload.
Audit / observabilityRecord significant activity without leaking sensitive data.
Never trust a user-supplied customer ID as authorization. The server must verify that the authenticated principal is actually allowed to access that customer's resource.

Knowledge check

Choose the contract intentionally

Unknown order ID?

Typically 404 Not Found.

Valid user, wrong permission?

403 Forbidden.

Cancel request against SHIPPED order?

409 Conflict is often a strong fit because current state prevents the operation.

Successful creation?

201 Created is conventional when a resource is created.
