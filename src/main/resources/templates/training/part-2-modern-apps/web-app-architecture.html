Start with the architecture problem

A production web application is rarely “a website connected to a database”

COMMERCIAL SCENARIO

Customer cancels an order

The browser renders the screen, identity establishes who the user is, an API receives the request, service logic validates cancellation policy, a database updates state, an event may notify fulfillment, logs capture evidence and monitoring detects failures. Each responsibility belongs somewhere.

Core idea: Architecture is the deliberate placement of responsibilities and boundaries so the system can evolve, scale, secure and operate without becoming one inseparable mass.

Layer 2 — Edge

The edge is the controlled front door before application code

DNSMaps application name to reachable endpoint.
CDNCaches static or cacheable content closer to users.
WAFApplies web-traffic filtering and protection policies.
Load balancer / gatewayRoutes traffic across healthy application instances.

Not every application uses every edge component. The pattern matters: Internet-facing concerns are commonly separated from business code.

Frontend / presentation layer

The UI owns interaction, not authoritative business truth

The frontend should

  • Render data for users.
  • Collect and validate basic input.
  • Manage interaction state.
  • Call backend APIs or submit server-rendered forms.
  • Provide accessible, responsive feedback.

The frontend should not be trusted to

  • Enforce authorization by hiding buttons only.
  • Own authoritative pricing or cancellation policy.
  • Store server secrets.
  • Replace backend validation.
  • Directly manipulate production databases.
Security rule: Anything delivered to the browser is under the user's control. Backend systems must revalidate identity, authorization and business rules.

Data layer

Databases protect durable system state

SchemaTables, columns, types, constraints and relationships.
TransactionsKeep related changes consistent.
IndexesImprove access paths for important queries.
IntegrityKeys and constraints prevent invalid states.
Backup / recoveryProtect the ability to restore durable state.
SecurityCredentials, network access, encryption and least privilege.
Architectural distinction: The database is an implementation component. The business owns concepts such as Customer, Order and Product; the database stores representations of those concepts.

Architecture patterns

Do not memorize logos; recognize structural choices

MonolithUI/API/business logic commonly packaged and deployed together. Can be simple and effective.
Layered monolithSingle deployable with disciplined internal boundaries such as controller/service/repository.
MicroservicesMultiple independently deployable services around bounded capabilities, with additional distributed-system complexity.
ServerlessFunctions and managed services reduce server management but introduce platform-specific execution and integration patterns.
Do not infer maturity from architecture fashion. A well-designed modular monolith can be safer and easier to operate than poorly designed microservices.

Knowledge check

Can you place responsibility in the correct layer?

Where should “customer may cancel only before shipment” live?

Authoritative backend business logic, not only JavaScript.

Where should HTTP 404 vs. 409 be selected?

At the HTTP/API boundary, informed by service outcomes.

Why have a repository layer?

To isolate persistence operations from higher-level business logic.

Is a WAF a replacement for secure code?

No. It is an additional edge control, not a substitute for application security.
