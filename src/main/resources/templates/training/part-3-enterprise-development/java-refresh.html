Core Java types

Know what each type is trying to communicate

classState + behavior; common for entities and services.
interfaceContract that enables substitution and decoupling.
recordCompact immutable data carrier; excellent for DTOs.
enumClosed set of named values such as order status.
annotationMetadata consumed by frameworks/tools.
generic typeType-safe reusable abstraction such as List<Order>.
Object-oriented design

Use OO concepts to express boundaries, not to maximize inheritance

EncapsulationProtect invariants behind methods.
AbstractionExpose what callers need, hide implementation detail.
PolymorphismDifferent implementations behind a common contract.
CompositionBuild behavior from collaborating objects; usually preferred to deep inheritance.
Modern Java example

A small domain type can carry a lot of intent

JAVA 21 · DOMAIN + DTO
public enum OrderStatus { CREATED, PAID, FULFILLING, SHIPPED, DELIVERED, CANCELLED }

public record OrderSummary(Long id, OrderStatus status, BigDecimal total) {}

public final class OrderPolicy {
    public boolean canCancel(OrderStatus status) {
        return switch (status) {
            case CREATED, PAID, FULFILLING -> true;
            default -> false;
        };
    }
}
Collections

Choose the data structure that matches the business meaning

List<T>Ordered sequence; duplicates allowed.
Set<T>Uniqueness is important.
Map<K,V>Lookup by key.
Commercial rule: if uniqueness matters to the domain, communicate it explicitly rather than depending on callers to remember.
Streams and lambdas

Streams describe transformations—but readability still wins

FILTER → MAP → COLLECT
List<Long> paidOrderIds = orders.stream()
    .filter(order -> order.getStatus() == OrderStatus.PAID)
    .map(Order::getId)
    .toList();

Use streams where the data flow is obvious. A deeply nested stream pipeline is not automatically better than a clear loop.

Failure handling

Exceptions are part of your application contract

Validation failureBad external input; usually translate to 4xx.
Business exceptionRequest is syntactically valid but violates a rule.
System failureDatabase/network/runtime issue; log with context and fail safely.
Anti-pattern: catching Exception, logging nothing useful and continuing as if the operation succeeded.
Nullability and Optional

Absence should be explicit at important boundaries

Risky ambiguity

Customer findById(...) — can this return null?

Explicit absence

Optional<Customer> findById(...) — caller must consider missing data.

Commercial coding discipline

Prefer code that makes illegal or surprising states harder to create

Immutable DTOsReduce accidental mutation.
Small methodsEasier to reason about and test.
Meaningful namesDomain language beats abbreviations.
Constructor invariantsReject impossible state early.
Single responsibilityKeep business logic out of controllers.
TestsProtect behavior while refactoring.
Reference application

Trace ordinary Java through the Bootcamp e-commerce application

  1. Open an entity and identify fields, constructors/getters and enum usage.
  2. Open a service and identify injected collaborators.
  3. Find a repository generic declaration and explain both type parameters.
  4. Find a controller method and identify parameter types and return type.
  5. Find one lambda, stream, Optional or collection usage and explain why it is used.
Common failure modes

Java knowledge is not the same as production engineering

God classesToo many responsibilities in one type.
Deep inheritanceBehavior becomes hard to trace.
Mutable shared stateCreates concurrency and reasoning problems.
Stringly typed domainsStatuses and identifiers lose type safety.
Swallowed exceptionsFailures disappear until users report them.
Premature clevernessNovel code hurts maintainability.
Hands-on lab

Read before you write

  1. Choose one e-commerce request such as viewing an order.
  2. Trace the Java call path from controller to repository.
  3. Write down every class/interface/enum encountered.
  4. Identify one collection and one generic type.
  5. Identify where an exception could originate and where it should be translated.
  6. Explain the flow to another engineer without opening the code.
Knowledge check

Can you read Java as design?

Record vs class?

Records are excellent concise immutable data carriers; classes are appropriate when identity, lifecycle or richer behavior is needed.

List vs Set?

Use Set when uniqueness is part of the meaning; List when ordering/duplicates are valid.

Why interfaces?

They define contracts and enable substitution, testing and decoupling.

Why avoid catching everything?

It hides failure semantics and can leave the system in an unknown state.

Career perspective

Commercial Java fluency is the ability to change existing systems safely

The strongest junior engineers are not those who memorize the most syntax. They can enter an unfamiliar codebase, build a correct mental model, ask good questions and make a small change without creating new risk.
