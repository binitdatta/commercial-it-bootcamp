The composition problem

Large applications should not manually construct their entire object graph

Manual construction

new OrderService(new OrderRepository(...), new PaymentClient(...), ...)

Container-managed composition

Declare dependencies; Spring resolves and wires them at startup.

Spring beans

A bean is an object whose lifecycle is managed by Spring

DiscoveryComponent scanning or configuration.
ConstructionSpring invokes constructor/factory method.
Dependency resolutionRequired collaborators are supplied.
InitializationPost-processing/lifecycle callbacks run.
UseBean participates in application work.
ShutdownManaged cleanup can occur.
Component stereotypes

Annotations communicate architectural intent

@ComponentGeneric Spring-managed component.
@ServiceBusiness/application service role.
@RepositoryPersistence boundary and exception translation intent.
@ControllerServer-side MVC web endpoint.
@RestControllerHTTP API endpoint returning response bodies.
@ConfigurationExplicit bean and infrastructure configuration.
Constructor injection

Required dependencies should be visible in the constructor

PREFERRED DEPENDENCY INJECTION
@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentClient paymentClient;

    public OrderService(OrderRepository orderRepository,
                        PaymentClient paymentClient) {
        this.orderRepository = orderRepository;
        this.paymentClient = paymentClient;
    }
}
Why this matters: required dependencies are explicit, fields can be final, objects are easier to unit test and invalid partially-initialized states are harder to create.
Dependency resolution

What if multiple beans implement the same interface?

Single implementationSpring can resolve by type.
@PrimaryDefault choice among candidates.
@QualifierRequest a specific named/qualified bean.
Profiles/configSelect implementations by environment or configuration.
Scope and state

Most service beans are singletons—so do not store per-request mutable state in them

Critical: a singleton Spring service may serve many requests concurrently. Local variables are fine; mutable instance fields used as request/session state can create cross-user data corruption and concurrency bugs.
Explicit configuration

Not every object comes from component scanning

@CONFIGURATION + @BEAN
@Configuration
public class ClientConfiguration {
    @Bean
    Clock applicationClock() {
        return Clock.systemUTC();
    }
}

Factory methods are useful for third-party types, infrastructure clients and objects whose creation requires explicit configuration.

Failure modes

Dependency injection can still be abused

Field injectionHides required dependencies and complicates testing.
Huge constructorsOften signal a class with too many responsibilities.
Circular dependenciesUsually reveal confused boundaries.
Service locatorPulling beans manually hides dependencies again.
Mutable singleton stateCreates concurrency defects.
Annotation cargo cultUsing stereotypes without understanding role boundaries.

Knowledge check

Do you understand the container?

IoC vs DI?

IoC is the broader inversion of control; DI is the mechanism of supplying dependencies from outside the object.

What is a bean?

An object managed by the Spring container.

Why constructor injection?

It makes required dependencies explicit, immutable and testable.

Why is singleton state risky?

The same bean instance can serve concurrent requests.
