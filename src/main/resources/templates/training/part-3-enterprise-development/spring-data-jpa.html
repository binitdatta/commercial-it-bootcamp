Repository abstraction

A repository expresses persistence operations around an aggregate/entity

SPRING DATA REPOSITORY
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByCustomerIdOrderByCreatedAtDesc(Long customerId);
    Optional<Order> findByIdAndCustomerId(Long id, Long customerId);
}
saveCreate/update entity.
findByIdRead by identifier.
findAllRead collection—use carefully.
deleteRemove entity.
Query strategies

Choose the simplest query mechanism that remains clear

Derived queryMethod name expresses simple predicates/order.
@Query JPQLExplicit entity-oriented query.
Native SQLUse when DB-specific SQL is truly justified.
Specification / criteriaUseful for dynamic filter composition.
ProjectionFetch only the shape needed by a use case.
PaginationBound collection reads.
Entity mapping

Entities model persistent identity and lifecycle

@Entity@Id@GeneratedValue@Column@ManyToOne@OneToMany@Enumerated
Do not confuse: a JPA entity is a persistence model. It is not automatically the best JSON API contract or UI DTO.

Persistence context

Managed entities are tracked during a transaction

LoadEntity becomes managed.
ModifyJava object state changes.
Dirty checkingHibernate detects relevant changes.
Flush/commitSQL updates synchronize state.
Relationships and fetching

Object navigation can trigger database work

@ManyToOneMany children reference one parent.
@OneToManyParent exposes a collection of children.
LAZYLoad relationship when needed—within a valid context.
EAGERLoad immediately; can over-fetch dramatically.
The N+1 problem

A simple Java loop can accidentally produce hundreds of SQL queries

1 queryLoad 100 orders
+
100 queriesLazy-load customer for each
=
101 queriesLatency + DB load

Use fetch joins, entity graphs, projections or appropriately shaped queries based on the use case. Do not “fix” everything by making all relationships eager.

Concurrency

Two users can update the same row at the same time

Optimistic locking

Version column detects conflicting updates at commit.

Pessimistic locking

Database lock reserves access; useful selectively but can reduce concurrency.

Anti-patterns

Repository convenience can hide serious database mistakes

findAll in productionUnbounded reads create memory/latency problems.
Entity as API DTOPersistence changes leak into clients.
Lazy load outside transactionRuntime failures or accidental session extension.
N+1 queriesDatabase hammered by object navigation.
No indexesRepository query looks clean while SQL scans tables.
Long transactionsLocks/resources held longer than necessary.
Hands-on lab

Trace repository behavior in the Bootcamp app

  1. Open every repository interface and identify its entity and ID type.
  2. Find one derived query method and translate its name into SQL intent.
  3. Trace one service method that performs a write.
  4. Identify the correct transaction boundary.
  5. Inspect one entity relationship and predict when SQL is issued.
  6. Identify one query that should be paginated or indexed in a larger production system.
Knowledge check

Can you see through the abstraction?

What does JpaRepository provide?

A Spring Data repository abstraction with common CRUD, paging and sorting behavior.

Where should a business transaction live?

Usually around the service/use-case boundary rather than individual repository calls.

What is dirty checking?

Hibernate detects modifications to managed entities and synchronizes them at flush/commit.

Why does N+1 happen?

Repeated relationship navigation can issue one additional query per parent row.
