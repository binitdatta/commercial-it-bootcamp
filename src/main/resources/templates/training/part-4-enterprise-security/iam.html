Architecture mental model

Trace every security decision

1. Request
User/client initiates an operation.
→
2. Identity
Establish the principal and authentication context.
→
3. Credential
Token, assertion, session or proof crosses a boundary.
→
4. Validation
Verify cryptography, issuer, audience, time and context.
→
5. Authorization
Policy decides whether the requested action is allowed.
Commercial scenario

Authentication is only the beginning

A signed-in customer requests an order. The system must establish identity, validate the security credential, authorize access to that specific order, protect sensitive data, and create useful audit evidence. A successful login alone does not make the operation safe.

Failure modes

What breaks in real systems

Wrong trust assumptions

Trusting browser input, token claims or network location without server-side validation.

Over-privilege

Users or services receive broader permissions than the business operation requires.

Credential leakage

Secrets, tokens or private keys enter Git, logs, tickets or screenshots.

Lifecycle gaps

Access remains after role changes, offboarding, key rotation or session revocation.

Reference application

Connect the lesson to Spring Boot + Keycloak

Trace Browser → Spring Security → Keycloak → authenticated principal → authorization decision → controller/service. Locate the relevant configuration in the Bootcamp application and explain which component is responsible for each security decision.

Hands-on lab

Prove that you understand the flow

  1. Draw the actors and trust boundaries.
  2. Identify the credential or protocol message crossing each boundary.
  3. List the validations the receiving component must perform.
  4. Identify one attack or configuration failure for each boundary.
  5. Map the result to the Bootcamp Keycloak/Spring Security implementation.
Knowledge check

Explain, don't memorize

  1. What problem does Identity and Access Management solve?
  2. Which parties participate and what does each trust?
  3. What must be cryptographically or logically validated?
  4. Where does authentication end and authorization begin?
  5. What would you log for investigation without leaking credentials?
Lesson recap

Security is explicit trust plus continuous validation

Commercial engineers should reason about identity, credentials, policy, cryptography, lifecycle and auditability as one system.

Career perspective

Security fluency makes you a stronger engineer and architect

You do not need to be a penetration tester to design secure software. You do need to recognize trust boundaries, ask the right IAM questions, validate assumptions and collaborate effectively with security specialists.
