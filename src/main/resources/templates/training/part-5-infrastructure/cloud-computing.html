PART V · LESSON 30

Cloud Computing Fundamentals

Understand compute, storage, managed databases, identity and shared responsibility across major clouds.

LEARNING OBJECTIVES

By the end of this lesson, you should be able to

Explain the mental model
Describe the major components and why commercial systems need them.
Trace a real workload
Connect the concept to the Spring Boot E-Commerce reference platform.
Diagnose common failures
Use evidence and layer-by-layer reasoning instead of guessing.
Work safely
Recognize security, configuration and operational boundaries.
01 · CORE TOPIC

Cloud is an operating model

Cloud computing provides on-demand infrastructure and managed services through APIs with metered consumption. The important skill is understanding capabilities and responsibility boundaries—not memorizing one vendor catalog.

02 · CORE TOPIC

IaaS, PaaS and SaaS

IaaS gives more operating-system control and responsibility. PaaS abstracts more runtime operations. SaaS delivers the finished application. Choosing a higher abstraction can reduce undifferentiated operational work but also changes portability and control.

03 · CORE TOPIC

Compute choices

Virtual machines, containers, managed container platforms, application platforms, serverless functions and Kubernetes each expose different scaling, patching, startup and operational characteristics.

04 · CORE TOPIC

Storage and databases

Distinguish object, block and file storage. Distinguish relational databases from NoSQL and caching. Managed databases shift patching/backups/HA mechanics toward the provider while schema, access, data quality and application behavior remain your responsibility.

05 · CORE TOPIC

Identity and shared responsibility

Use cloud IAM for human and workload identities, least privilege and auditable access. The provider secures the cloud infrastructure; customers remain responsible for significant portions of configuration, identity, applications and data.

06 · CORE TOPIC

Availability, elasticity and cost

Design across failure domains when business requirements justify it. Scaling is not free: understand utilization, data transfer, managed-service pricing, idle resources and the relationship between architecture decisions and recurring cost.

07 · CORE TOPIC

AWS, Azure and Google Cloud mapping

Learn capabilities conceptually first: compute, object storage, managed SQL, IAM, load balancing, DNS, secrets and monitoring exist across major providers even though product names and implementation details differ.

08 · CORE TOPIC

Reference application lab

Place the Bootcamp into a cloud architecture: managed application runtime/container platform, managed MySQL-compatible database, external identity provider, secrets service, centralized logs, DNS/TLS and an internet-facing edge.

WORKING DEMONSTRATION

Connect the lesson to something you can inspect

Client / User
Browser or API client
Network / Edge
DNS, TLS, routing, filtering
Application
Spring Boot workload
Managed Data
Database, storage, secrets

The objective is not command memorization. Predict what should happen, execute or inspect, observe evidence, and explain the result in terms of the architecture.

FAILURE MODES

Troubleshoot by layer

Configuration
Wrong address, port, variable, credential, image, route or environment assumption.
Connectivity / runtime
Process down, dependency unreachable, health check failing or resource exhausted.
Security
Permission, firewall, certificate, secret or identity boundary blocks the operation.
HANDS-ON LAB

Explain before you change

  1. Draw the components involved in the reference application for this lesson.
  2. Identify one configuration value and where it comes from.
  3. Identify one failure that would produce an application error and one that would prevent connectivity entirely.
  4. Collect evidence using the tools introduced above.
  5. Write a five-sentence incident note: symptom, scope, evidence, root cause hypothesis and next action.
KNOWLEDGE CHECK

Can you reason about it?

Question 1: What responsibility belongs to this layer, and what responsibility belongs somewhere else?
Question 2: What evidence would distinguish an application bug from an infrastructure/configuration failure?
Question 3: What would you inspect before restarting or changing production?
LESSON RECAP

Infrastructure becomes manageable when you can trace boundaries

Know what runs where, how components communicate, where configuration comes from, what protects the boundary and which evidence proves each hypothesis.

CAREER PERSPECTIVE

Application engineers do not need to be infrastructure administrators

They do need enough infrastructure fluency to deploy responsibly, communicate with platform and operations teams, diagnose their side of an incident, and avoid treating every production problem as somebody else's problem.
