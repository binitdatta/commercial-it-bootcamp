PART V · LESSON 28

Docker and Containers

Package an application and understand images, containers, ports, volumes and environment variables.

LEARNING OBJECTIVES

By the end of this lesson, you should be able to

Explain the mental model
Describe the major components and why commercial systems need them.
Trace a real workload
Connect the concept to the Spring Boot E-Commerce reference platform.
Diagnose common failures
Use evidence and layer-by-layer reasoning instead of guessing.
Work safely
Recognize security, configuration and operational boundaries.
01 · CORE TOPIC

Why containers exist

A deployable application needs code, runtime, libraries and configuration assumptions. Containers package a predictable user-space environment so the same image can move through developer, test and production environments.

02 · CORE TOPIC

Image vs. container

An image is an immutable packaged template built from layers; a container is a running instance of an image. Rebuilding an image creates a new artifact; restarting a container does not rebuild it.

03 · CORE TOPIC

Dockerfile mental model

FROM selects a base, WORKDIR establishes context, COPY adds artifacts, RUN builds layers, EXPOSE documents a port and ENTRYPOINT/CMD defines startup behavior. Prefer small, reproducible, non-root production images.

04 · CORE TOPIC

Ports and networking

The application listens on a container port while Docker can publish it to a host port. Understand why localhost inside a container refers to that container—not automatically to your Mac or another container.

05 · CORE TOPIC

Volumes and persistence

Container writable layers are disposable. Use volumes or external managed storage for state that must survive container replacement. Databases should not depend on an ephemeral application container filesystem.

06 · CORE TOPIC

Configuration and secrets

Inject environment-specific configuration at runtime rather than baking DEV/PROD values into an image. Do not place passwords, private keys or tokens in Dockerfiles, image layers or source control.

07 · CORE TOPIC

Lifecycle and diagnostics

Use docker build, images, run, ps, logs, exec, inspect, stop and rm. Diagnose whether a problem is image build, startup, port mapping, runtime configuration, dependency connectivity or application logic.

08 · CORE TOPIC

Reference application lab

Package the Bootcamp JAR into an image, run it with a published port, pass database/Keycloak configuration externally, inspect logs and explain what must change when dependencies run outside the container.

WORKING DEMONSTRATION

Connect the lesson to something you can inspect

docker build -t commercial-it-bootcamp . docker run --rm -p 8081:8081 commercial-it-bootcamp docker ps docker logs <container> docker exec -it <container> sh

The objective is not command memorization. Predict what should happen, execute or inspect, observe evidence, and explain the result in terms of the architecture.

FAILURE MODES

Troubleshoot by layer

Configuration
Wrong address, port, variable, credential, image, route or environment assumption.
Connectivity / runtime
Process down, dependency unreachable, health check failing or resource exhausted.
Security
Permission, firewall, certificate, secret or identity boundary blocks the operation.
HANDS-ON LAB

Explain before you change

  1. Draw the components involved in the reference application for this lesson.
  2. Identify one configuration value and where it comes from.
  3. Identify one failure that would produce an application error and one that would prevent connectivity entirely.
  4. Collect evidence using the tools introduced above.
  5. Write a five-sentence incident note: symptom, scope, evidence, root cause hypothesis and next action.
KNOWLEDGE CHECK

Can you reason about it?

Question 1: What responsibility belongs to this layer, and what responsibility belongs somewhere else?
Question 2: What evidence would distinguish an application bug from an infrastructure/configuration failure?
Question 3: What would you inspect before restarting or changing production?
LESSON RECAP

Infrastructure becomes manageable when you can trace boundaries

Know what runs where, how components communicate, where configuration comes from, what protects the boundary and which evidence proves each hypothesis.

CAREER PERSPECTIVE

Application engineers do not need to be infrastructure administrators

They do need enough infrastructure fluency to deploy responsibly, communicate with platform and operations teams, diagnose their side of an incident, and avoid treating every production problem as somebody else's problem.
