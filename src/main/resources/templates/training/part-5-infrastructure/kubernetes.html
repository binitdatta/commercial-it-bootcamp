PART V · LESSON 29

Kubernetes Fundamentals

Recognize pods, deployments, services, ingress, configuration and secrets without becoming a cluster administrator.

LEARNING OBJECTIVES

By the end of this lesson, you should be able to

Explain the mental model
Describe the major components and why commercial systems need them.
Trace a real workload
Connect the concept to the Spring Boot E-Commerce reference platform.
Diagnose common failures
Use evidence and layer-by-layer reasoning instead of guessing.
Work safely
Recognize security, configuration and operational boundaries.
01 · CORE TOPIC

Why orchestration exists

Running one container manually is easy. Production platforms need scheduling, replacement, scaling, service discovery, configuration rollout and health management across many workloads and machines.

02 · CORE TOPIC

Cluster mental model

A cluster contains control-plane capabilities and worker nodes. Kubernetes schedules Pods onto nodes and continuously reconciles actual state toward the desired state declared in API objects.

03 · CORE TOPIC

Pod and Deployment

A Pod is the basic execution unit. A Deployment manages replicated stateless Pods and rolling updates. Do not treat an individual Pod as a permanent server; Pods are replaceable.

04 · CORE TOPIC

Service and Ingress

A Service gives a stable network identity to changing Pods. Ingress or a gateway exposes HTTP(S) routes into the cluster. Trace traffic as client → edge/load balancer → ingress/gateway → service → pod.

05 · CORE TOPIC

ConfigMaps and Secrets

Separate configuration from images. ConfigMaps hold non-sensitive configuration; Secrets are the Kubernetes object for sensitive values, but production security also requires encryption, RBAC and often an external secrets system.

06 · CORE TOPIC

Health, scaling and resources

Readiness determines whether a Pod should receive traffic; liveness can trigger restart; startup probes protect slow starts. Requests/limits influence scheduling and resource isolation. Horizontal scaling adds replicas when appropriate.

07 · CORE TOPIC

Operational commands

Use kubectl get, describe, logs, exec and events as evidence-gathering tools. Start broad, identify the failing object, then inspect state, events, logs, networking and configuration.

08 · CORE TOPIC

Reference application lab

Model the Bootcamp as a Deployment and Service. Identify where the image, port, environment variables, readiness endpoint, replica count and external database/Keycloak addresses belong.

WORKING DEMONSTRATION

Connect the lesson to something you can inspect

kubectl get pods kubectl get deployments,services kubectl describe pod <pod> kubectl logs <pod> kubectl get events --sort-by=.metadata.creationTimestamp

The objective is not command memorization. Predict what should happen, execute or inspect, observe evidence, and explain the result in terms of the architecture.

FAILURE MODES

Troubleshoot by layer

Configuration
Wrong address, port, variable, credential, image, route or environment assumption.
Connectivity / runtime
Process down, dependency unreachable, health check failing or resource exhausted.
Security
Permission, firewall, certificate, secret or identity boundary blocks the operation.
HANDS-ON LAB

Explain before you change

  1. Draw the components involved in the reference application for this lesson.
  2. Identify one configuration value and where it comes from.
  3. Identify one failure that would produce an application error and one that would prevent connectivity entirely.
  4. Collect evidence using the tools introduced above.
  5. Write a five-sentence incident note: symptom, scope, evidence, root cause hypothesis and next action.
KNOWLEDGE CHECK

Can you reason about it?

Question 1: What responsibility belongs to this layer, and what responsibility belongs somewhere else?
Question 2: What evidence would distinguish an application bug from an infrastructure/configuration failure?
Question 3: What would you inspect before restarting or changing production?
LESSON RECAP

Infrastructure becomes manageable when you can trace boundaries

Know what runs where, how components communicate, where configuration comes from, what protects the boundary and which evidence proves each hypothesis.

CAREER PERSPECTIVE

Application engineers do not need to be infrastructure administrators

They do need enough infrastructure fluency to deploy responsibly, communicate with platform and operations teams, diagnose their side of an incident, and avoid treating every production problem as somebody else's problem.
