PART V · LESSON 27

Linux and Command-Line Skills

Become comfortable with the commands and diagnostics common in servers, containers and CI jobs.

LEARNING OBJECTIVES

By the end of this lesson, you should be able to

Explain the mental model
Describe the major components and why commercial systems need them.
Trace a real workload
Connect the concept to the Spring Boot E-Commerce reference platform.
Diagnose common failures
Use evidence and layer-by-layer reasoning instead of guessing.
Work safely
Recognize security, configuration and operational boundaries.
01 · CORE TOPIC

Why Linux matters in commercial IT

Most production runtimes, containers, build agents and cloud workloads expose Linux concepts. You do not need to become a Linux administrator, but you must be able to navigate a host, inspect a process, read logs, understand permissions and collect evidence before escalating.

02 · CORE TOPIC

Filesystem and navigation

Learn /, /home, /etc, /var, /tmp and /opt; absolute vs. relative paths; pwd, ls, cd, mkdir, cp, mv, rm, find and du. Treat the filesystem as an operational map rather than a collection of mysterious directories.

03 · CORE TOPIC

Files, text and logs

Use cat, less, head, tail, grep, sort, uniq, wc and pipes. A commercial engineer often diagnoses a failure by reducing thousands of log lines to the few records associated with a request, timestamp, user or correlation ID.

04 · CORE TOPIC

Processes and system resources

Understand PID, foreground/background processes, signals, ps, top, kill, df, free and uptime. Distinguish an application failure from CPU pressure, memory exhaustion, disk exhaustion or a dead process.

05 · CORE TOPIC

Permissions and identity

Read rwx permissions, owner/group, chmod, chown, sudo and least privilege. Never solve an access problem by casually making files world-writable.

06 · CORE TOPIC

Network diagnostics

Use curl, ping where permitted, dig/nslookup, ss/netstat and traceroute concepts. Separate DNS failure, connection refusal, TLS failure and HTTP application failure.

07 · CORE TOPIC

Shells, environment variables and automation

Understand PATH, export, environment variables, exit codes, quoting, redirection and simple shell scripts. Environment variables are common for runtime configuration but secrets still require appropriate secret-management controls.

08 · CORE TOPIC

Reference application lab

From Terminal, call the running Spring Boot application with curl, inspect the HTTP status and headers, locate the Java process, identify the listening port, and use logs to correlate one request end-to-end.

WORKING DEMONSTRATION

Connect the lesson to something you can inspect

pwd ls -lah ps aux | grep java curl -i http://localhost:8081/ lsof -i :8081 tail -f application.log

The objective is not command memorization. Predict what should happen, execute or inspect, observe evidence, and explain the result in terms of the architecture.

FAILURE MODES

Troubleshoot by layer

Configuration
Wrong address, port, variable, credential, image, route or environment assumption.
Connectivity / runtime
Process down, dependency unreachable, health check failing or resource exhausted.
Security
Permission, firewall, certificate, secret or identity boundary blocks the operation.
HANDS-ON LAB

Explain before you change

  1. Draw the components involved in the reference application for this lesson.
  2. Identify one configuration value and where it comes from.
  3. Identify one failure that would produce an application error and one that would prevent connectivity entirely.
  4. Collect evidence using the tools introduced above.
  5. Write a five-sentence incident note: symptom, scope, evidence, root cause hypothesis and next action.
KNOWLEDGE CHECK

Can you reason about it?

Question 1: What responsibility belongs to this layer, and what responsibility belongs somewhere else?
Question 2: What evidence would distinguish an application bug from an infrastructure/configuration failure?
Question 3: What would you inspect before restarting or changing production?
LESSON RECAP

Infrastructure becomes manageable when you can trace boundaries

Know what runs where, how components communicate, where configuration comes from, what protects the boundary and which evidence proves each hypothesis.

CAREER PERSPECTIVE

Application engineers do not need to be infrastructure administrators

They do need enough infrastructure fluency to deploy responsibly, communicate with platform and operations teams, diagnose their side of an incident, and avoid treating every production problem as somebody else's problem.
