Data Lakes and Lakehouse Concepts

Understand object storage, raw and curated zones, medallion architecture, open table formats and why lakehouses emerged.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Describe the major components, data boundaries, responsibilities and trade-offs using correct commercial terminology.

Reason about production data

Identify data quality, lineage, security, freshness, failure and operational concerns instead of treating analytics as isolated code.

Connect business to data

Translate a business question into sources, transformations, analytical structures and measurable outputs.

Apply it hands-on

Use the Bootcamp e-commerce system as a realistic source and design the next analytical layer around it.

Start with the business problem

Enterprises need economical storage for large volumes of structured, semi-structured and unstructured data without forcing everything into a warehouse schema on arrival.

Data engineering exists to move from operational records to governed, trustworthy information without losing meaning, lineage or control.

Commercial principle: A data platform is successful when consumers can trust what the data means, where it came from, how fresh it is and who owns it.
Core concepts

Vocabulary you should be able to use correctly

Data Lake
Scalable object-storage-based repository for raw and curated data in many formats.
Object Storage
Cloud storage organized as objects rather than database blocks; ideal for large analytical datasets.
Bronze / Raw
Source-aligned data preserved with minimal transformation and strong lineage.
Silver / Curated
Validated, standardized, deduplicated and conformed data suitable for broad analytical reuse.
Gold / Serving
Business-oriented datasets optimized for dashboards, KPIs, ML features or downstream products.
Lakehouse
A data-lake architecture enhanced with table metadata, transactional guarantees, governance and warehouse-like query behavior.
End-to-end operating model

Follow the data from source to consumer

1Ingest to raw

Land immutable or replayable source data with ingestion metadata.

2Register metadata

Catalog datasets, ownership, schema, classification and lineage.

3Clean to curated

Standardize types, resolve duplicates, apply quality rules and conform reference data.

4Build serving models

Create business-ready tables for BI, ML or application consumption.

5Optimize physical layout

Partition, compact files and maintain table metadata to reduce scan cost.

6Secure and govern

Apply least privilege, encryption, masking, retention and sensitive-data controls.

7Observe data products

Measure freshness, quality, volume, lineage breaks and consumer impact.

Commercial scenario

Think in business outcomes, not technology names

A supply-chain company receives ERP tables, supplier spreadsheets, logistics events, PDFs and IoT telemetry. A warehouse alone is a poor landing zone for all of it. A lake stores heterogeneous source data, while curated and gold layers provide governed analytical products.

Business question

What decision, KPI, risk or operational action needs better information?

Data contract

What does each field mean, how fresh must it be, and which system is authoritative?

Operational ownership

Who responds when data is late, incomplete, duplicated, inaccessible or wrong?

Reference application

Connect the lesson to the Bootcamp e-commerce platform

Imagine exporting the Bootcamp e-commerce order data as daily Parquet files into object storage. Design Bronze, Silver and Gold datasets and state what transformation or governance happens in each layer.

Operational source
Spring Boot services, JPA entities and MySQL transaction tables represent the system running the business.
Data platform
Pipelines, storage, transformations, cataloging and analytical compute turn operational records into reusable data products.
Consumers
BI dashboards, analysts, ML models, operational alerts and other applications consume governed outputs.
Governance and security

The data layer inherits enterprise responsibilities

Classification
Know PII, financial, confidential and regulated fields.
Least privilege
Separate ingestion, transformation, administration and consumer access.
Lineage
Trace important outputs back to source systems and transformation logic.
Retention
Keep data only as long as business, legal and recovery needs require.
Common failure modes

What inexperienced teams often get wrong

Data swamp

Files are stored without ownership, cataloging, naming standards, quality expectations or consumers.

Tiny-file explosion

High file counts create excessive metadata and query overhead.

Partition mistakes

Over-partitioning or poor partition keys cause inefficient scans and operational complexity.

No lifecycle policy

Raw and intermediate data accumulates indefinitely, increasing cost and risk.

Hands-on lab

Practice on a commercial-style problem

Design a three-layer medallion layout for customer, order and product data. Include storage paths, file/table format, partition strategy, data-quality checks, PII controls and one Gold dataset.

Deliverable: Produce a one-page design showing sources, processing stages, ownership, quality controls, security boundaries, operational evidence and final consumer value.
Knowledge check

Can you reason about the data system?

  1. Which system is authoritative for the business fact and why?
  2. What could make the data technically valid but business-wrong?
  3. How will you detect late, missing, duplicate or malformed data?
  4. Which information is sensitive and who should be able to access it?
  5. How can a consumer trace an output back to its origin?
  6. What happens operationally when this pipeline or data product fails?
Lesson recap

Five things to remember

1. A lake is more than cheap storage.
2. Raw data preserves replayability.
3. Curated layers create reusable quality.
4. Lakehouses add table semantics and reliability.
5. Governance must span every layer.
Career perspective

Strong engineers understand the data lifecycle, not only SQL or tools

As responsibility grows, you are expected to understand data ownership, business meaning, architecture, quality, security, cost and production behavior across the complete path from source to decision.
