Streaming and Near-Real-Time Data

Understand events, streams, brokers, event time, windows and how operational activity becomes fresh analytical data.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Describe the major components, data boundaries, responsibilities and trade-offs using correct commercial terminology.

Reason about production data

Identify data quality, lineage, security, freshness, failure and operational concerns instead of treating analytics as isolated code.

Connect business to data

Translate a business question into sources, transformations, analytical structures and measurable outputs.

Apply it hands-on

Use the Bootcamp e-commerce system as a realistic source and design the next analytical layer around it.

Start with the business problem

Daily batch processing is too slow when decisions depend on what happened seconds or minutes ago.

Data engineering exists to move from operational records to governed, trustworthy information without losing meaning, lineage or control.

Commercial principle: A data platform is successful when consumers can trust what the data means, where it came from, how fresh it is and who owns it.
Core concepts

Vocabulary you should be able to use correctly

Event
An immutable statement that something happened: OrderPlaced, PaymentAuthorized or ShipmentDeparted.
Stream
An ordered or partially ordered flow of events processed continuously.
Broker / Log
Infrastructure that durably receives, partitions and delivers event records to consumers.
Event Time
When the business event actually occurred, which may differ from processing or arrival time.
Window
A bounded interval used to aggregate an otherwise unbounded stream.
Watermark
A mechanism for reasoning about late-arriving events and when a time window can be considered sufficiently complete.
End-to-end operating model

Follow the data from source to consumer

1Produce business event

The operational system emits a meaningful event after state changes.

2Ingest durably

A broker stores the event with partition, offset/key and retention semantics.

3Deserialize and validate

Consumers check schema, required fields and compatibility.

4Transform / enrich

Join reference data, derive fields, filter or route events.

5Aggregate by window

Compute rolling counts, rates, totals or anomaly signals.

6Persist serving state

Write outputs to analytical stores, caches, dashboards or feature stores.

7Monitor lag and quality

Track consumer lag, late events, throughput, failures and end-to-end freshness.

Commercial scenario

Think in business outcomes, not technology names

A retailer wants a dashboard showing orders, payment failures and inventory risk within two minutes. Events flow from transactional services through a streaming platform into near-real-time aggregates while the nightly warehouse process remains the source for certified financial reporting.

Business question

What decision, KPI, risk or operational action needs better information?

Data contract

What does each field mean, how fresh must it be, and which system is authoritative?

Operational ownership

Who responds when data is late, incomplete, duplicated, inaccessible or wrong?

Reference application

Connect the lesson to the Bootcamp e-commerce platform

Extend the Bootcamp e-commerce mental model so OrderCreated and OrderCancelled events are published after transaction commit. Design consumers for a live order-rate dashboard and a low-inventory alert.

Operational source
Spring Boot services, JPA entities and MySQL transaction tables represent the system running the business.
Data platform
Pipelines, storage, transformations, cataloging and analytical compute turn operational records into reusable data products.
Consumers
BI dashboards, analysts, ML models, operational alerts and other applications consume governed outputs.
Governance and security

The data layer inherits enterprise responsibilities

Classification
Know PII, financial, confidential and regulated fields.
Least privilege
Separate ingestion, transformation, administration and consumer access.
Lineage
Trace important outputs back to source systems and transformation logic.
Retention
Keep data only as long as business, legal and recovery needs require.
Common failure modes

What inexperienced teams often get wrong

Treating streaming as instant batch

A continuously running system has different state, ordering, retry and recovery concerns.

Ignoring event time

Late records produce incorrect windows when processing time is used blindly.

Non-idempotent sinks

Consumer retries duplicate side effects or analytical records.

No replay strategy

A bug is fixed but the team cannot rebuild derived state from retained events.

Hands-on lab

Practice on a commercial-style problem

Design a near-real-time pipeline for orders. Define event schema, partition key, retention, two consumers, a five-minute metric, late-event handling, idempotency strategy and recovery/replay plan.

Deliverable: Produce a one-page design showing sources, processing stages, ownership, quality controls, security boundaries, operational evidence and final consumer value.
Knowledge check

Can you reason about the data system?

  1. Which system is authoritative for the business fact and why?
  2. What could make the data technically valid but business-wrong?
  3. How will you detect late, missing, duplicate or malformed data?
  4. Which information is sensitive and who should be able to access it?
  5. How can a consumer trace an output back to its origin?
  6. What happens operationally when this pipeline or data product fails?
Lesson recap

Five things to remember

1. Streaming serves freshness-sensitive use cases.
2. Events describe business facts.
3. Event time matters.
4. Consumers must tolerate replay.
5. Batch and streaming often coexist.
Career perspective

Strong engineers understand the data lifecycle, not only SQL or tools

As responsibility grows, you are expected to understand data ownership, business meaning, architecture, quality, security, cost and production behavior across the complete path from source to decision.
