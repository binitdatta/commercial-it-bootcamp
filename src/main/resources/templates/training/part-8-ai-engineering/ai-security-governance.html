AI Security and Governance

Treat AI risk controls as architecture: identity, data minimization, prompt-injection defenses, tool authorization, model governance, audit, evaluation and human accountability.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Use accurate AI terminology and place probabilistic model behavior inside normal enterprise application boundaries.

Separate AI from authority

Identify what the model may interpret or generate versus what deterministic systems must authorize and execute.

Recognize failure modes

Reason about hallucination, data exposure, tool misuse, unreliable automation, cost and operational failure.

Design a controlled implementation

Connect AI components to IAM, APIs, data, observability, testing and human governance.

Start with the engineering problem

AI introduces new probabilistic behavior, but it still runs inside existing enterprise security, privacy, compliance and operational obligations.

The durable skill is not memorizing model brands. It is knowing where probabilistic AI belongs, where it does not belong, and how to surround it with mature software-engineering controls.

Commercial principle: AI should increase the capability of an enterprise system without weakening identity, authorization, data integrity, auditability or operational control.
Core concepts

Vocabulary that matters in production

Prompt Injection
Untrusted content attempts to influence model behavior or override application intent.
Data Exfiltration
Sensitive data is disclosed through prompts, retrieved context, model output or tool results.
Model Risk
Risk arising from inaccurate, unstable, biased, unsafe or poorly understood model behavior.
AI Policy Enforcement
Deterministic controls applied before, during and after model execution.
Evaluation / Red Teaming
Systematic testing of quality, abuse cases, jailbreaks, tool misuse and failure behavior.
Human Accountability
A named person or organizational role remains responsible for consequential decisions and approvals.
End-to-end flow

Follow one request through the architecture

1Classify use case

Determine business value, data sensitivity, user population, autonomy and consequence level.

2Authenticate and authorize

Bind every request and tool call to trusted identity and least-privilege policy.

3Minimize data

Send only the information required for the task; redact or tokenize sensitive fields where practical.

4Constrain capabilities

Use allow-listed models, retrieval sources, tools, parameters and network destinations.

5Validate behavior

Apply content, schema, groundedness, policy and business-rule checks around model output.

6Audit and monitor

Record user, purpose, model, prompts where appropriate, sources, tools, policy decisions and outcome.

7Govern lifecycle

Approve models/use cases, manage versions, evaluate changes, handle incidents and retire unsafe workflows.

Commercial scenario

Move from demo thinking to enterprise thinking

An internal HR assistant can answer policy questions but must not expose another employee's compensation data. RAG filtering, API authorization and data minimization enforce the boundary; a system prompt alone is insufficient.

Identity
Who is asking, what organization/tenant are they in, and what are they permitted to do?
Authority
Which deterministic service owns the business fact or action?
Evidence
What logs, traces, retrieved sources, tool results and policy decisions prove what happened?
Reference application

Connect AI to the Bootcamp Spring Boot platform

For the Bootcamp order assistant, require Keycloak identity, user-scoped order APIs, allow-listed tools, prompt/response handling rules, auditable tool calls, evaluation tests and human approval before any high-impact operation.

Keycloak
Identity, authentication and trusted claims.
Spring Security
Deterministic access enforcement at application/API boundaries.
Services / APIs
Authoritative business operations exposed as governed capabilities.
MySQL
Transactional state remains in the system of record.
Production controls

What surrounds the model

IAM & policy
SSO, roles/attributes, tenant boundaries and purpose-aware authorization.
Evaluation
Representative test sets for quality, safety, groundedness and tool correctness.
Observability
Trace model calls, retrieval, tools, latency, cost, errors and decisions.
Human governance
Approval and accountability for consequential actions and exceptions.
Common failure modes

Where AI systems fail when engineering discipline is missing

Prompt as policy engine

Natural-language instructions replace deterministic access controls.

Logging everything

Sensitive prompts and retrieved data are copied into ordinary telemetry without classification.

One-time model approval

Teams fail to reevaluate when models, prompts, tools or provider behavior change.

No incident playbook

The organization cannot rapidly disable a tool, model, data source or workflow after unsafe behavior.

Hands-on lab

Apply the concept to the reference system

Create an AI threat model for the Bootcamp assistant. Cover identity, prompt injection, unauthorized retrieval, tool abuse, sensitive logging, model/provider dependency, cost abuse, output risk, human approval and incident shutdown controls.

Deliverable: Produce a one-page implementation design with architecture, trust boundaries, allowed capabilities, validation, failure handling, observability and acceptance criteria.
Knowledge check

Can you defend the design?

  1. Which component owns the authoritative business fact?
  2. What can the model decide, and what must deterministic policy decide?
  3. How is user identity carried into retrieval and tool execution?
  4. What failure could produce a fluent but unsafe result?
  5. How would you test this before production?
  6. What evidence would an operator or auditor need after an incident?
Lesson recap

Five things to remember

1. AI security extends enterprise security.
2. Authorization stays deterministic.
3. Minimize sensitive data.
4. Tools need least privilege and audit.
5. Governance must cover the full lifecycle.
Career perspective

AI-era engineers still need strong software-engineering foundations

The engineer who understands IAM, APIs, data, distributed systems, observability, testing and business workflows can use AI far more effectively than someone who knows prompting alone. The AI layer magnifies both good architecture and bad architecture.
