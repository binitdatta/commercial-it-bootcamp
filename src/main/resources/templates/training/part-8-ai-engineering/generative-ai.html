Generative AI Fundamentals

Build a correct mental model of foundation models, tokens, context windows, prompting, inference, hallucination, evaluation and where Generative AI fits in enterprise systems.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Use accurate AI terminology and place probabilistic model behavior inside normal enterprise application boundaries.

Separate AI from authority

Identify what the model may interpret or generate versus what deterministic systems must authorize and execute.

Recognize failure modes

Reason about hallucination, data exposure, tool misuse, unreliable automation, cost and operational failure.

Design a controlled implementation

Connect AI components to IAM, APIs, data, observability, testing and human governance.

Start with the engineering problem

Teams often treat an LLM as a database, search engine, rules engine and autonomous decision-maker at the same time. That produces brittle systems and misplaced trust.

The durable skill is not memorizing model brands. It is knowing where probabilistic AI belongs, where it does not belong, and how to surround it with mature software-engineering controls.

Commercial principle: AI should increase the capability of an enterprise system without weakening identity, authorization, data integrity, auditability or operational control.
Core concepts

Vocabulary that matters in production

Foundation Model
A large pretrained model that can be adapted through prompting, retrieval, fine-tuning or tools.
Token
The model's processing unit. Inputs and outputs are tokenized, which affects limits, cost and latency.
Context Window
The finite amount of prompt, retrieved content and conversation history the model can consider in one request.
Inference
Running the trained model to generate an output from a prompt.
Temperature / Sampling
Controls how deterministic or varied generation is. Lower values are usually preferred for structured enterprise workflows.
Hallucination
A fluent but unsupported or incorrect output. It is a system-design risk, not merely a wording problem.
End-to-end flow

Follow one request through the architecture

1User intent

A user asks a question, requests content, or initiates a workflow.

2Application context

The application adds system instructions, identity context, policy constraints and relevant conversation state.

3Grounding

Trusted enterprise data may be retrieved from documents, databases or APIs when the task requires factual context.

4Model inference

The LLM predicts an output based on the information inside its active context.

5Validation

Application code checks structure, policy, citations, allowed values, confidence signals or tool results.

6Response / action

The user receives an answer, or the system proceeds to a governed tool/action layer.

7Evaluation

Teams measure quality, safety, groundedness, cost and latency over representative test cases.

Commercial scenario

Move from demo thinking to enterprise thinking

A support employee asks, “Why was order 49281 delayed?” The model should not invent the answer from its training. The application must retrieve authoritative order, shipment and exception data, then let the model explain the facts in useful language.

Identity
Who is asking, what organization/tenant are they in, and what are they permitted to do?
Authority
Which deterministic service owns the business fact or action?
Evidence
What logs, traces, retrieved sources, tool results and policy decisions prove what happened?
Reference application

Connect AI to the Bootcamp Spring Boot platform

Treat the Bootcamp Spring Boot e-commerce application as the deterministic system of record. An LLM can explain or summarize order data, but the order service, database and authorization layer remain authoritative.

Keycloak
Identity, authentication and trusted claims.
Spring Security
Deterministic access enforcement at application/API boundaries.
Services / APIs
Authoritative business operations exposed as governed capabilities.
MySQL
Transactional state remains in the system of record.
Production controls

What surrounds the model

IAM & policy
SSO, roles/attributes, tenant boundaries and purpose-aware authorization.
Evaluation
Representative test sets for quality, safety, groundedness and tool correctness.
Observability
Trace model calls, retrieval, tools, latency, cost, errors and decisions.
Human governance
Approval and accountability for consequential actions and exceptions.
Common failure modes

Where AI systems fail when engineering discipline is missing

Model as system of record

The LLM is asked to remember business facts that actually live in transactional applications.

Prompt-only security

Instructions such as 'do not show other users' data' are treated as authorization controls.

Unbounded context

Large amounts of irrelevant content are pushed into prompts, increasing latency, cost and confusion.

No evaluation set

Teams judge quality from a few demos instead of repeatable representative tests.

Hands-on lab

Apply the concept to the reference system

Write three prompts for the same e-commerce question: a weak prompt, a better grounded prompt, and an enterprise prompt that includes identity, retrieved facts, output schema and explicit uncertainty behavior.

Deliverable: Produce a one-page implementation design with architecture, trust boundaries, allowed capabilities, validation, failure handling, observability and acceptance criteria.
Knowledge check

Can you defend the design?

  1. Which component owns the authoritative business fact?
  2. What can the model decide, and what must deterministic policy decide?
  3. How is user identity carried into retrieval and tool execution?
  4. What failure could produce a fluent but unsafe result?
  5. How would you test this before production?
  6. What evidence would an operator or auditor need after an incident?
Lesson recap

Five things to remember

1. LLMs generate; they do not inherently know your live enterprise state.
2. Context is finite and expensive.
3. Grounding reduces unsupported answers.
4. Authorization belongs outside the model.
5. Evaluation must be systematic.
Career perspective

AI-era engineers still need strong software-engineering foundations

The engineer who understands IAM, APIs, data, distributed systems, observability, testing and business workflows can use AI far more effectively than someone who knows prompting alone. The AI layer magnifies both good architecture and bad architecture.
