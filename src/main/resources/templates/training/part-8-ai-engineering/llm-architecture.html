LLM Application Architecture

Understand the complete enterprise stack around an LLM: channels, backend-for-frontend, IAM, orchestration, model gateway, tools, data, observability and governance.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Use accurate AI terminology and place probabilistic model behavior inside normal enterprise application boundaries.

Separate AI from authority

Identify what the model may interpret or generate versus what deterministic systems must authorize and execute.

Recognize failure modes

Reason about hallucination, data exposure, tool misuse, unreliable automation, cost and operational failure.

Design a controlled implementation

Connect AI components to IAM, APIs, data, observability, testing and human governance.

Start with the engineering problem

A production AI application is not 'frontend → model API'. The model is one component inside a much larger secured software architecture.

The durable skill is not memorizing model brands. It is knowing where probabilistic AI belongs, where it does not belong, and how to surround it with mature software-engineering controls.

Commercial principle: AI should increase the capability of an enterprise system without weakening identity, authorization, data integrity, auditability or operational control.
Core concepts

Vocabulary that matters in production

AI Application Layer
The user-facing UI or API that owns sessions, user experience and application behavior.
BFF / API Gateway
A policy-aware backend boundary for authentication, rate limits, routing, telemetry and client-specific orchestration.
LLM Gateway
A controlled abstraction over one or more model providers for routing, policy, quotas, cost and observability.
Orchestrator
Coordinates prompts, retrieval, tools, state, branching, retries and approvals.
Tool / Skill Registry
An allow-listed catalog of deterministic capabilities the model may request.
AI Observability
Tracing of prompts, model calls, retrieval, tools, latency, cost, policy decisions and outcomes.
End-to-end flow

Follow one request through the architecture

1Authenticate

The application verifies user identity and obtains trusted claims from the enterprise IdP.

2Authorize request

Application policy determines whether the user may access the requested business capability.

3Classify and route

The AI layer identifies intent, risk, model requirements and whether retrieval or tools are needed.

4Ground / execute

Approved retrieval sources and tools obtain authoritative context or perform deterministic actions.

5Model reasoning

The LLM interprets context, chooses from allowed options and composes language or structured output.

6Policy enforcement

Outputs and requested actions are validated before they affect enterprise systems.

7Observe and audit

The platform records trace IDs, model usage, tools, source lineage and user-visible outcome.

Commercial scenario

Move from demo thinking to enterprise thinking

A company has ten departmental assistants. Rather than duplicating IAM, rate limiting, logging, model credentials and governance ten times, each frontend routes through shared platform services while departmental teams retain domain-specific UX and skills.

Identity
Who is asking, what organization/tenant are they in, and what are they permitted to do?
Authority
Which deterministic service owns the business fact or action?
Evidence
What logs, traces, retrieved sources, tool results and policy decisions prove what happened?
Reference application

Connect AI to the Bootcamp Spring Boot platform

Extend the Bootcamp architecture horizontally: Browser → Spring UI/API → Security → AI Orchestrator → LLM Gateway → Approved Tools → OrderService/MySQL. The AI layer does not bypass Spring Security or domain services.

Keycloak
Identity, authentication and trusted claims.
Spring Security
Deterministic access enforcement at application/API boundaries.
Services / APIs
Authoritative business operations exposed as governed capabilities.
MySQL
Transactional state remains in the system of record.
Production controls

What surrounds the model

IAM & policy
SSO, roles/attributes, tenant boundaries and purpose-aware authorization.
Evaluation
Representative test sets for quality, safety, groundedness and tool correctness.
Observability
Trace model calls, retrieval, tools, latency, cost, errors and decisions.
Human governance
Approval and accountability for consequential actions and exceptions.
Common failure modes

Where AI systems fail when engineering discipline is missing

Direct browser-to-model calls

Secrets, governance and enterprise data access are pushed into an uncontrolled client.

Every team builds its own gateway

Cost controls, logging and security become inconsistent.

Model directly queries databases

The model is given excessive authority and becomes tightly coupled to internal schemas.

No separation of reasoning and execution

A probabilistic model is allowed to make consequential changes without deterministic controls.

Hands-on lab

Apply the concept to the reference system

Draw a horizontal architecture for an enterprise order assistant. Include browser, IdP, BFF, policy, LLM gateway, orchestrator, RAG, tools, Spring APIs, MySQL, logs, metrics, audit and a human-approval point.

Deliverable: Produce a one-page implementation design with architecture, trust boundaries, allowed capabilities, validation, failure handling, observability and acceptance criteria.
Knowledge check

Can you defend the design?

  1. Which component owns the authoritative business fact?
  2. What can the model decide, and what must deterministic policy decide?
  3. How is user identity carried into retrieval and tool execution?
  4. What failure could produce a fluent but unsafe result?
  5. How would you test this before production?
  6. What evidence would an operator or auditor need after an incident?
Lesson recap

Five things to remember

1. The model is only one layer.
2. Identity and policy remain deterministic.
3. Tools expose bounded capabilities.
4. Gateways centralize model controls.
5. Auditability spans the entire request.
Career perspective

AI-era engineers still need strong software-engineering foundations

The engineer who understands IAM, APIs, data, distributed systems, observability, testing and business workflows can use AI far more effectively than someone who knows prompting alone. The AI layer magnifies both good architecture and bad architecture.
