LLM Tool and Function Calling

Understand how models request deterministic functions, APIs and enterprise skills without receiving unrestricted authority.

Learning objectives

By the end of this lesson, you should be able to

Explain the architecture

Use accurate AI terminology and place probabilistic model behavior inside normal enterprise application boundaries.

Separate AI from authority

Identify what the model may interpret or generate versus what deterministic systems must authorize and execute.

Recognize failure modes

Reason about hallucination, data exposure, tool misuse, unreliable automation, cost and operational failure.

Design a controlled implementation

Connect AI components to IAM, APIs, data, observability, testing and human governance.

Start with the engineering problem

Language models are good at interpreting intent but weak substitutes for deterministic business APIs, calculations and state transitions.

The durable skill is not memorizing model brands. It is knowing where probabilistic AI belongs, where it does not belong, and how to surround it with mature software-engineering controls.

Commercial principle: AI should increase the capability of an enterprise system without weakening identity, authorization, data integrity, auditability or operational control.
Core concepts

Vocabulary that matters in production

Tool
A bounded callable capability exposed to the model, usually backed by deterministic application code.
Function Schema
A structured definition of tool name, description, arguments and expected types.
Tool Selection
The model chooses an approved capability based on user intent and available tool descriptions.
Argument Validation
Application code validates model-generated parameters before execution.
Execution Boundary
The application, not the model, invokes the real API or function.
Tool Result
Structured output returned to the model for interpretation or the next controlled step.
End-to-end flow

Follow one request through the architecture

1Receive request

The user asks in natural language.

2Determine capability

The model identifies whether a tool is needed and selects from the allow-list.

3Produce arguments

The model returns structured parameters conforming to the declared schema.

4Validate policy

Application code checks identity, authorization, argument constraints and business rules.

5Execute tool

A deterministic service/API performs the read or action.

6Inspect result

The result is returned to the AI layer, potentially driving another step.

7Respond and audit

The model explains the result while the platform records the tool execution.

Commercial scenario

Move from demo thinking to enterprise thinking

A customer asks to cancel an order. The model may select cancel_order(orderId), but Spring Security and OrderService still verify ownership and cancellation policy before any database change occurs.

Identity
Who is asking, what organization/tenant are they in, and what are they permitted to do?
Authority
Which deterministic service owns the business fact or action?
Evidence
What logs, traces, retrieved sources, tool results and policy decisions prove what happened?
Reference application

Connect AI to the Bootcamp Spring Boot platform

Expose Bootcamp skills such as get_order, list_orders and cancel_order as thin wrappers over existing secured Spring services. The model never receives JDBC credentials and never bypasses service-layer policy.

Keycloak
Identity, authentication and trusted claims.
Spring Security
Deterministic access enforcement at application/API boundaries.
Services / APIs
Authoritative business operations exposed as governed capabilities.
MySQL
Transactional state remains in the system of record.
Production controls

What surrounds the model

IAM & policy
SSO, roles/attributes, tenant boundaries and purpose-aware authorization.
Evaluation
Representative test sets for quality, safety, groundedness and tool correctness.
Observability
Trace model calls, retrieval, tools, latency, cost, errors and decisions.
Human governance
Approval and accountability for consequential actions and exceptions.
Common failure modes

Where AI systems fail when engineering discipline is missing

Tool descriptions too broad

The model cannot reliably choose between overlapping or ambiguous capabilities.

Trusting generated arguments

Model output is treated as safe input without validation.

Overpowered tools

One generic SQL or shell tool grants far more capability than the use case requires.

No idempotency

Retries accidentally repeat financial or state-changing operations.

Hands-on lab

Apply the concept to the reference system

Define JSON-style schemas for get_order and cancel_order. Then document authorization checks, business validation, error contract, idempotency behavior and the audit fields captured for each call.

Deliverable: Produce a one-page implementation design with architecture, trust boundaries, allowed capabilities, validation, failure handling, observability and acceptance criteria.
Knowledge check

Can you defend the design?

  1. Which component owns the authoritative business fact?
  2. What can the model decide, and what must deterministic policy decide?
  3. How is user identity carried into retrieval and tool execution?
  4. What failure could produce a fluent but unsafe result?
  5. How would you test this before production?
  6. What evidence would an operator or auditor need after an incident?
Lesson recap

Five things to remember

1. Models request tools; applications execute them.
2. Tool schemas are contracts.
3. Authorization occurs before execution.
4. Prefer narrow capabilities.
5. State-changing tools need stronger controls.
Career perspective

AI-era engineers still need strong software-engineering foundations

The engineer who understands IAM, APIs, data, distributed systems, observability, testing and business workflows can use AI far more effectively than someone who knows prompting alone. The AI layer magnifies both good architecture and bad architecture.
