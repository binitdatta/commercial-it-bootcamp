Technical Documentation

Learn how engineers create durable documentation for architecture, APIs, operations, decisions and onboarding without producing stale document dumps.

Learning objectives

By the end of this lesson, you should be able to

Think beyond your immediate task

Understand the broader business, architecture, team and operational consequences of engineering decisions.

Communicate decisions clearly

Explain intent, trade-offs, risk and evidence to both technical and non-technical stakeholders.

Use professional engineering controls

Apply review, documentation, security, quality and ownership practices consistently.

Operate as part of a team

Recognize that commercial software is a shared organizational product, not an individual coding exercise.

Start with the professional problem

When important knowledge exists only in meetings, chat or one person's memory, systems become harder to change and incidents take longer to resolve.

Professional engineering is the discipline of making good technical decisions in a business, team and production context.

Commercial principle: Seniority is not only deeper coding skill. It is broader judgment, better communication, stronger risk awareness and the ability to improve outcomes across team boundaries.
Core concepts

Vocabulary and mental models

README
Repository-level guidance for purpose, setup, local development, testing and common workflows.
Architecture Diagram
A visual explanation of components, boundaries, data flows and dependencies.
ADR
A concise record of an important architecture decision and its consequences.
Runbook
Operational instructions for diagnosing or executing a known production procedure.
API Contract
Documented request, response, error, authentication and compatibility behavior.
Living Documentation
Documentation maintained alongside the system and updated as part of change.
Professional workflow

How experienced engineers approach the work

1Identify audience

Write for the person who must use, operate, integrate or modify the system.

2Document purpose

State what the system or component does and why it exists.

3Show architecture

Explain boundaries, dependencies, data flows and trust relationships.

4Capture operational knowledge

Add startup, deployment, monitoring, backup and troubleshooting guidance.

5Link decisions

Connect ADRs, issues, code and architecture so context remains discoverable.

6Version with change

Update documentation in the same delivery flow as the code.

7Retire obsolete content

Mark or remove outdated material rather than letting contradictory guidance accumulate.

Commercial scenario

Apply judgment in a real team context

A new engineer must support a service after the original developer leaves. With a clear README, architecture diagram, API contract, runbook and ADRs, onboarding takes days instead of weeks.

Reference application

Use the Bootcamp platform as the working example

Improve the Bootcamp repository README so a new engineer can create MySQL, import the Keycloak realm, run Spring Boot, understand roles, access the training pages and troubleshoot common startup failures.

Business
What outcome or policy is the system serving?
Architecture
What boundaries and dependencies shape the solution?
Engineering
How is the change implemented, tested and reviewed?
Operations
How will the team deploy, observe, support and recover it?
Common failure modes

What weak professional practice looks like

Documentation as afterthought

Teams postpone documentation until knowledge has already been lost.

Screenshot-only guidance

Instructions depend on transient UI states and become obsolete quickly.

No ownership

Everyone assumes someone else will maintain the document.

Duplicated truth

The same configuration or procedure is copied into many places and drifts.

Hands-on lab

Practice the professional skill

Create a documentation map for the Bootcamp: README, architecture overview, security guide, API guide, operations runbook, ADR folder and troubleshooting guide. Define owner and update trigger for each.

Deliverable: Produce something another engineer or stakeholder could actually use: a decision record, review checklist, documentation map, discovery artifact, communication pack or threat model.
Knowledge check

Can you explain the reasoning?

  1. What is the business or engineering outcome being protected?
  2. Which decision or responsibility boundary matters most?
  3. What evidence would another engineer need to trust the work?
  4. What could fail after this reaches production?
  5. Who else needs to understand or approve the decision?
  6. How will future team members recover the context?
Lesson recap

Five things to remember

1. Documentation preserves organizational memory.
2. Write for a concrete audience.
3. Operational docs matter as much as design docs.
4. Decisions need rationale.
5. Docs should change with the system.
Career perspective

Professional judgment is what makes technical depth valuable at scale

As you progress from Engineer to Senior Engineer, Tech Lead, Architect, Manager or specialist, your leverage increasingly comes from helping many people make better decisions—not merely writing more code yourself.
